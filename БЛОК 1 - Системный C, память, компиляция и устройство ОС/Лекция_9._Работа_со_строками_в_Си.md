# Лекция 9: Работа со строками в Си (C-Strings)

В предыдущих лекциях мы изучили массивы, указатели, функции и структуры. Мы знаем, как компьютер хранит целые и дробные числа и как обращаться к ячейкам памяти напрямую. Теперь мы переходим к глубокому изучению работы с текстовой информацией.

В Лекции 8, когда мы создавали структуру человека и писали `student.name = "Алексей";`, а затем выводили это имя на экран через спецификатор `%s` в `printf`, мы уже использовали строки. На тот момент мы приняли эту работу как удобную абстракцию. В этой лекции мы полностью снимем завесу тайны, детально разберем физическое устройство строк в оперативной памяти (ОЗУ), поймем, почему в Си нет встроенного типа для строк, и изучим классические функции для работы с ними.

## Подглава 9.1: Почему в Си нет типа данных String?

В современных высокоуровневых языках (таких как Python, Java или C++) строка является полноценным самостоятельным типом данных. Там можно легко складывать строки знаком плюс (`s3 = s1 + s2`) или сравнивать их обычным равенством (`if (s1 == s2)`). В языке Си ничего этого делать напрямую нельзя. Почему?

На физическом уровне процессор компьютера умеет оперировать только числами. Любой символ, который вы видите на экране, — это всего лишь визуальное отображение числового кода, хранящегося в памяти.

### Символьный тип данных char
Для хранения одного символа в Си используется тип данных `char`. Он занимает в памяти ровно **1 байт** (8 бит). Это позволяет закодировать 2^8 = 256 различных значений.

Связь между числами в ОЗУ и буквами на экране описывается стандартами кодирования. Исторически самым важным из них является таблица **ASCII** (American Standard Code for Information Interchange). Согласно этой таблице:
*   Символ `'A'` физически хранится в памяти как число `65`.
*   Символ `'a'` хранится как число `97`.
*   Символ `'0'` (текстовая цифра ноль) хранится как число `48`.
*   Символ пробела `' '` хранится как число `32`.

> ℹ️ Таблица ASCII содержит только 128 символов (латиница, цифры, знаки препинания). Кириллица кодируется иначе: в кодировке UTF-8 каждая русская буква занимает **2 байта**, поэтому `strlen("Алексей")` вернёт 14, а не 7. Чтобы не отвлекаться на это, в примерах лекции строки записаны латиницей.

Когда мы пишем в коде `char letter = 'A';`, компилятор Си просто берет число `65` и записывает его в выделенный байт ОЗУ.

### Строка как массив символов
Поскольку отдельный символ занимает всего 1 байт, любая текстовая строка — это просто последовательность символов, расположенных в памяти друг за другом. Иными словами, **строка в Си — это массив элементов типа `char`, который заканчивается нулевым байтом** (о нём — в следующей подглаве).

Именно поэтому в Си нет ключевого слова `String`. Любая строка — это низкоуровневая структура данных, собранная из простейших элементов `char` вручную.

## Подглава 9.2: Концепция нуль-терминатора (\0)

Если строка — это просто массив символов, то как компьютер понимает, где именно она заканчивается? 

В обычном целочисленном массиве мы обязаны отдельно хранить и передавать его размер. Но со строками такой подход сделал бы код крайне громоздким. Разработчики языка Си нашли элегантное и простое решение: они ввели специальный маркер конца строки — **нуль-терминатор** (или нулевой символ).

**Нуль-терминатор** записывается в коде как **`'\0'`**. 
*   Физически в оперативной памяти это байт, все 8 бит которого равны нулю (число `0`).
*   Не путайте его с символом `'0'` (символьным нулем), который в ASCII кодируется числом `48`. Нуль-терминатор `'\0'` — это именно числовой ноль `0`.

### Как это выглядит в памяти?
Допустим, мы хотим сохранить в памяти слово `"Hello"`. Это слово состоит из 5 букв. Однако в ОЗУ под него будет выделено **6 байт**:

```text
Индекс массива:   [  0  ] [  1  ] [  2  ] [  3  ] [  4  ] [  5  ]
Символ:           [ 'H' ] [ 'e' ] [ 'l' ] [ 'l' ] [ 'o' ] [ '\0']
Число в ОЗУ:      [  72 ] [ 101 ] [ 108 ] [ 108 ] [ 111 ] [  0  ]
```

Когда мы передаем строку в функцию `printf` со спецификатором `%s`, мы передаем туда всего лишь адрес самого первого символа (в данном случае буквы `'H'`). Функция `printf` берет этот адрес и запускает последовательный обход памяти символ за символом. Как только она доходит до байта со значением `0`, она понимает: *«Строка окончена, чтение завершено»*. Все символы, которые могут лежать в памяти дальше этого нуля, функцией просто игнорируются.

**Важнейшее правило системного программиста:** При выделении памяти под строку всегда резервируйте **на 1 байт больше**, чем длина текста, чтобы в конце гарантированно поместился нуль-терминатор. Если этого не сделать, строка превратится в неуправляемый поток данных, и программа начнет читать «мусор» из соседних ячеек ОЗУ, пока случайно не наткнется на нулевой байт.

## Подглава 9.3: Два способа создания строк и их различия в ОЗУ

В языке Си создать строку можно двумя принципиально разными способами. Они определяют, в какой именно области оперативной памяти будет лежать ваш текст и можно ли его изменять.

### Способ 1: Указатель на строковый литерал (Read-Only память)
```c
char *str = "Hello";
```
*   **Как это устроено в ОЗУ:** Компилятор берет неизменяемую строку `"Hello"` и помещает её в специальный сегмент постоянных данных программы (сегмент `.rodata` — Read-Only Data). Сам указатель `str` (размером 8 байт на 64-битной системе) создается на стеке и хранит физический адрес начала этой строки в сегменте констант.
*   **Связь с Лекцией 8:** Именно этот способ мы использовали в структуре `person`, когда объявляли поле `char *name` и присваивали ему значение `"Алексей"`. Запись `student.name = "Алексей";` не копировала текст буквы за буквой. Она просто записывала в поле `name` (указатель) 8-байтовый адрес места в сегменте `.rodata`, где лежит слово `"Алексей"`.
*   **Можно ли изменить:** **Нет.** Попытка изменить символ напрямую (например, написать `str[0] = 'M';`) по стандарту Си — неопределённое поведение. На типичной системе это приведёт к аварийному завершению программы операционной системой — ошибке сегментации (Segmentation Fault). Операционная система защищает сегмент `.rodata` от записи.
*   **Совет:** чтобы компилятор сам не давал вам случайно изменить такой текст, указатель на литерал принято объявлять с ключевым словом `const` (запрет изменения): `const char *str = "Hello";`. Тогда запись `str[0] = 'M';` вызовет **ошибку компиляции**, а не падение программы во время работы.

### Способ 2: Изменяемый массив символов (Стек вызовов)
```c
char str[] = "Hello";
```
*   **Как это устроено в ОЗУ:** Компилятор создает на Стеке вызовов локальный массив символов `str` размером ровно 6 байт (5 букв плюс нуль-терминатор). При запуске функции он копирует буквы `'H'`, `'e'`, `'l'`, `'l'`, `'o'` и `'\0'` из сегмента констант на ваш стек.
*   **Можно ли изменить:** **Да.** Поскольку этот массив физически лежит во фрейме стека вашей текущей функции, вы можете свободно перезаписывать любые его элементы:
    ```c
    str[0] = 'M'; // Теперь в массиве на стеке хранится слово "Mello"
    ```

Мы также можем явно указать размер массива с запасом:
```c
char str[20] = "Hello";
```
В этом случае в стеке выделится ровно 20 байт. Первые 6 байт займут символы слова `"Hello"` и нуль-терминатор, а оставшиеся 14 байт автоматически заполнятся нулями. Мы можем безопасно расширять эту строку в процессе работы программы, пока её длина не превысит 19 символов (один байт всегда должен оставаться зарезервирован под маркер `'\0'`).

### Физическая визуализация: как эти строки лежат в ОЗУ

Давайте заглянем внутрь оперативной памяти компьютера и сравним эти два способа графически. Допустим (адреса условные, в реальной программе стек лежит в старших адресах), сегмент констант `.rodata` начинается с адреса `0x4000`, а текущий фрейм стека нашей функции находится в районе адреса `0x1000`.

```text
СЕГМЕНТ ПОСТОЯННЫХ ДАННЫХ (.rodata)           ФРЕЙМ СТЕКА ВЫЗОВОВ (Stack Frame)
(Доступен только для чтения)                  (Доступен для чтения и записи)

[Адрес 0x4000]:                               Для Способа 1 (char *str = "Hello"):
+---------------------------------------+     +---------------------------------------+
| 'H' | 'e' | 'l' | 'l' | 'o' | '\0'    |     | Переменная str (указатель)            |
+---------------------------------------+     | Размер: 8 байт                        |
                                              | Хранит адрес: 0x4000                  |
                                              +---------------------------------------+
                                                 ^ указывает на .rodata (0x4000)

                                              Для Способа 2 (char str[] = "Hello"):
                                              +---------------------------------------+
                                              | Переменная str (локальный массив)     |
                                              | Размер: 6 байт                        |
                                              | Данные на стеке:                      |
                                              | 'H' | 'e' | 'l' | 'l' | 'o' | '\0'    |
                                              +---------------------------------------+
```

### Главные физические выводы из схемы:

1.  **Расположение указателя (`char *str`):**  
    На самом стеке лежит только крошечная переменная-указатель `str` (8 байт), которая хранит число `0x4000`. Сам текст `"Hello"` лежит далеко в сегменте `.rodata`. Когда вы пытаетесь написать `str[0] = 'M';`, процессор пытается записать байт по адресу `0x4000` в защищённую область памяти, аппаратура сообщает об этом операционной системе, и та завершает программу (сигнал SIGSEGV).
2.  **Расположение массива (`char str[]`):**  
    Никакого указателя на стеке нет! Весь текст `"Hello"` вместе с нуль-терминатором скопирован непосредственно во фрейм стека и занимает там ровно 6 байт. Вызов `str[0] = 'M';` физически перезаписывает самый первый байт этого локального кадра стека. Поскольку стек принадлежит вашей функции, ОС разрешает эту операцию без каких-либо предупреждений.

### Анатомия стекового фрейма: взаимное расположение локальных переменных в ОЗУ

Чтобы понять, как локальные переменные уживаются друг с другом в оперативной памяти и как их соседство влияет на безопасность программы, давайте детально заглянем внутрь стекового фрейма нашей функции.

Допустим, внутри функции у нас объявлены две локальные переменные — числовой ключ и массив символов:

```c
int secret_key = 12345;
char buffer[8] = "Admin";
```

Когда компилятор выделяет память под эти локальные переменные, он распределяет их в памяти стека вызовов согласно следующим физическим законам:

1. **Направление роста стека:** Стек вызовов процессора растет **сверху вниз** (от более высоких адресов памяти к более низким).
2. **Порядок размещения переменных:** Стандарт Си не определяет, в каком порядке компилятор расставит локальные переменные, и реальные компиляторы могут менять порядок (например, ставить массивы ближе к концу кадра для защиты). Для наглядности примем типичную учебную схему: переменные, объявленные в коде первыми, размещаются на стеке первыми (по более высоким адресам), а объявленные ниже по тексту — следом (по более низким адресам).
3. **Направление записи в массив:** Хотя сам стек растет вниз, запись данных в любые массивы (включая строки) всегда идет стандартно — **слева направо** (от младших индексов к старшим, то есть **снизу вверх, от низких адресов к высоким**).

Давайте визуализируем стековый фрейм этой функции в оперативной памяти:

```text
Высокие адреса ОЗУ (вверху схемы)
   |
   +--------------------------------------+
   | Предыдущий фрейм стека (вызывающий)  |
   +--------------------------------------+
   | Адрес возврата (Return Address)      |
   +--------------------------------------+
   | Переменная: secret_key (4 байта)     |  <- адрес 0x1008
   +--------------------------------------+
   | Массив: buffer (8 байт)              |  <- адрес 0x1000
   +--------------------------------------+
   |
Низкие адреса ОЗУ (сюда растёт стек)
```

#### Механизм физического соседства и перекрытия:
* Массив `buffer` начинается по адресу `0x1000` (байты с 0 по 7).
* Сразу за ним по адресу `0x1008` (байты с 8 по 11) лежит переменная `secret_key`.
* Когда мы пишем данные в `buffer`, заполнение идет вверх по адресам: сначала записывается байт 0 (`0x1000`), затем байт 1 (`0x1001`) ... и так до байта 7 (`0x1007`).
* Если мы без проверки запишем строку, которой для хранения нужно больше 8 байт (то есть строку из 8 и более символов: с учётом нуль-терминатора ей нужно 9 и более байт), то лишние байты физически выйдут за пределы `buffer` и **напрямую перезапишут ячейки ОЗУ с адресами `0x1008`–`0x100B`**, где лежит `secret_key`.
* Процессор не знает о границах переменных — он просто послушно запишет байты по адресам. В результате число `12345` в переменной `secret_key` будет стерто и заменено символами из конца записываемой строки.

Этот механизм физического соседства критически важен. В системном программировании любая ошибка в расчете границ массива приводит к тому, что вы начинаете невольно уничтожать или модифицировать соседние данные. О том, к каким катастрофическим уязвимостям это приводит и как этим пользуются хакеры, мы подробно поговорим в **Подглаве 9.6**.

## Подглава 9.4: Работа со строками через указатели

Поскольку имя массива в выражениях превращается в адрес его первого элемента (мы разбирали связь массивов и указателей в Лекциях 4 и 6), мы можем легко перемещаться по строке с помощью арифметики указателей.

Давайте напишем простую функцию, которая выводит строку на экран по одному символу, используя только указатель и знание о нуль-терминаторе:

```c
#include <stdio.h>

void print_characters(char *ptr) {
    // Цикл работает, пока мы не дойдем до нуль-терминатора (значение *ptr не станет равным 0)
    while (*ptr != '\0') {
        printf("%c ", *ptr); // Выводим текущий символ
        ptr++;               // Сдвигаем адрес в указателе на следующий байт памяти
    }
    printf("\n");
}

int main() {
    char message[] = "C-String";
    print_characters(message); // Передаем адрес начала массива. Выведет: C - S t r i n g
    return 0;
}
```

В условии `while (*ptr != '\0')` мы проверяем значение в ОЗУ по адресу `ptr`. Поскольку `'\0'` равен числовому нулю `0`, это условие в Си можно записать еще короче и профессиональнее: `while (*ptr)`. Цикл автоматически остановится, когда по адресу в указателе окажется нулевой байт.

## Подглава 9.5: Функции стандартной библиотеки `<string.h>`

Поскольку строки в Си не являются полноценными объектами, мы не можем склеивать их через оператор `+` или сравнивать через `==`. Для выполнения любых манипуляций со строками в Си существует стандартная библиотека `<string.h>`. Давайте разберем четыре фундаментальные операции:

### 1. Подсчет длины строки: strlen
Функция `strlen` вычисляет количество символов в строке **без учета нуль-терминатора**.

```c
#include <stdio.h>
#include <string.h>

int main() {
    char text[] = "System";
    size_t length = strlen(text); // Вернет 6 (тип size_t — беззнаковое целое)
    printf("Длина строки: %zu\n", length); 
    return 0;
}
```
*   **Физическая суть:** Под капотом `strlen` — это простой цикл, который идет от переданного адреса и считает шаги, пока не встретит `0`. Сложность этой операции составляет **O(N)**, где N — длина строки. Это значит, что для длинных строк функция работает дольше, так как ей приходится каждый раз физически пробегать по всем символам в ОЗУ. Поэтому не вызывайте `strlen` в условии цикла (`for (i = 0; i < strlen(s); i++)`): длина будет пересчитываться на каждом шаге, и цикл станет квадратичным. Сохраните её в переменную до цикла.

### 2. Сравнение строк: strcmp и strncmp
Почему строки в Си нельзя сравнивать через привычный оператор `==`?
Если мы напишем `if (str1 == str2)`, компилятор сравнит не буквы внутри строк, а **их физические адреса в памяти** (ведь имя массива — это адрес). Даже если в обоих массивах лежат идентичные слова `"Hello"`, они расположены по разным адресам в ОЗУ, и проверка `==` всегда вернет ложь. (Для двух *указателей* на одинаковые литералы результат вообще не определён стандартом, поскольку компилятор вправе хранить одинаковые литералы в одном месте.)

Для сравнения содержимого используется функция `strcmp`:
```c
#include <stdio.h>
#include <string.h>

int main() {
    char s1[] = "Apple";
    char s2[] = "Apple";

    if (strcmp(s1, s2) == 0) {
        printf("Строки абсолютно идентичны!\n");
    }
    return 0;
}
```
*   `strcmp(s1, s2)` посимвольно сравнивает коды символов. Она возвращает `0`, если строки полностью совпадают, **отрицательное число**, если `s1` меньше `s2` (в алфавитном порядке по кодам), и **положительное**, если `s1` больше. Конкретные значения не определены, поэтому сравнивайте результат только с нулём: `== 0`, `< 0`, `> 0`.
*   **`strncmp(s1, s2, n)`** сравнивает не больше первых `n` символов (и останавливается раньше, если встретит `'\0'`). Она удобна для проверки **префикса** строки, а также когда строка может быть не завершена нулём в пределах известного размера буфера:
    ```c
    if (strncmp("Hello World", "Hello", 5) == 0) {
        printf("Строка начинается с Hello\n");
    }
    ```
    Это не «более безопасный `strcmp`» вообще: для корректных строк с нуль-терминатором обычный `strcmp` безопасен.

### 3. Объединение строк: strcat и strncat
Конкатенация (склеивание) строк выполняется с помощью функции `strcat`. Она берет символы из второй строки и дописывает их в конец первой, автоматически затирая её старый нуль-терминатор и ставя новый в самом конце.

```c
#include <stdio.h>
#include <string.h>

int main() {
    char buffer[20] = "Super"; // Массив с запасом памяти!
    char addition[] = "C";

    strcat(buffer, addition); // Склеиваем строки
    printf("Результат: %s\n", buffer); // Выведет "SuperC"
    return 0;
}
```

Функция `strcat` **не проверяет**, поместится ли результат в первый массив: это обязанность программиста. Что будет, если места не хватит, показано в подглаве 9.6.

### 4. Запись форматированного текста в строку: sprintf и snprintf
Функция `printf` выводит текст на экран, а `sprintf` записывает тот же форматированный результат **в массив символов** (и сама ставит `'\0'`). Это удобный способ собрать строку из чисел и текста.

```c
#include <stdio.h>

int main() {
    char message[32];
    char *name = "Ivan";
    int age = 27;

    sprintf(message, "%s is %d", name, age); // ОПАСНО: границы буфера не проверяются
    printf("%s\n", message);                 // Выведет: Ivan is 27
    return 0;
}
```

`sprintf` не знает размера массива `message`: если результат окажется длиннее, произойдёт такое же переполнение буфера, как у `strcat`. Поэтому в реальном коде используйте **`snprintf`**: она принимает размер буфера и записывает **не больше** `size - 1` символов плюс нуль-терминатор.

```c
snprintf(message, sizeof(message), "%s is %d", name, age);
```

Функция `snprintf` возвращает длину текста, который получился бы без ограничения. Если это число больше или равно размеру буфера, результат был обрезан.

## Подглава 9.6: Смертельная опасность переполнения буфера (Buffer Overflow)

В системном программировании на Си вы полностью управляете памятью, но это накладывает колоссальную ответственность. Самой распространенной ошибкой новичков и одновременно главной уязвимостью в истории программного обеспечения является **переполнение буфера (Buffer Overflow)**.

Давайте посмотрим на опасный код:
```c
char buffer[10] = "Hello";
char addition[] = " Long Text, Very Long Text";
strcat(buffer, addition); // ОШИБКА! Катастрофа в ОЗУ
```
Массив `buffer` может вместить максимум 9 символов и 1 обязательный нуль-терминатор. Но функция `strcat` слепо копирует всю длинную строку `addition` в конец `buffer`. 

### Что физически происходит в ОЗУ при переполнении?
Функция `strcat` не знает размер массива `buffer`, она видит только его стартовый адрес. Поэтому она начнет записывать символы дальше 10-го байта. При этом она **физически сотрет (перезапишет)** все данные, которые лежали в памяти следом за массивом на стеке вызовов.

Как мы детально разобрали в **Подглаве 9.3**, при переполнении буфера записываемые символы начинают выходить за физические рамки выделенного массива и двигаться вверх по адресам стека, затирая всё на своём пути:
1.  **Значения соседних локальных переменных** (как мы наглядно увидели на примере переменной `secret_key`, лежащей на стеке сразу над массивом `buffer`).
2.  **Фрейм стека текущей функции** и данные управления.
3.  **Адрес возврата (Return Address)** из функции, который лежит выше локальных переменных (по более высоким адресам). Подмена этого адреса позволяет злоумышленнику передать управление своему коду.

> ℹ️ Современные компиляторы и операционные системы добавляют защиту (канарейки стека, запрет исполнения кода в стеке, рандомизацию адресов), поэтому такая атака сложнее, но ошибки переполнения остаются одной из главных причин уязвимостей.

### Решение: контролировать размер записи

Функции `strcpy` и `strcat` не проверяют границы массива, поэтому в реальном коде их стараются не использовать. Что применять вместо них:

* **`strncat(dest, src, n)`** дописывает не более `n` символов из `src` и **всегда** ставит в конце `'\0'`. Важно: `n` — это лимит *дописываемых символов*, а не размер всего буфера. Поэтому место под терминатор нужно оставить самим: лимит равен `sizeof(buffer) - strlen(buffer) - 1`.
* **`strncpy`** использовать осторожно: если исходная строка не короче `n`, она **не ставит** `'\0'` в конце, и получается «строка» без терминатора. Для копирования проще и надёжнее `snprintf(dest, sizeof(dest), "%s", src)`.
* **`snprintf`** (подглава 9.5) — универсальный безопасный способ собрать строку.

Пример склейки со стандартной формулой лимита:

```c
char buffer[20] = "Hello";
char addition[] = " World";
strncat(buffer, addition, sizeof(buffer) - strlen(buffer) - 1);
```

Однако даже эта формула таит в себе скрытые ловушки, которые могут привести к уязвимостям.

#### Опасность 1: Целочисленное переполнение и беззнаковая арифметика
Тип возвращаемого значения функций `strlen` и оператора `sizeof` — это **`size_t`** (беззнаковое целое число). В беззнаковой арифметике Си результат вычитания не может быть отрицательным. 
Если по какой-то причине (например, из-за повреждения памяти или отсутствия нуль-терминатора) окажется, что текущая строка длиннее, чем размер буфера (`strlen(buffer) >= sizeof(buffer)`), то математически выражение должно вернуть отрицательное число. Но на физическом уровне произойдет **целочисленное переполнение в меньшую сторону (underflow)**.
В беззнаковой арифметике Си переход «ниже нуля» называется **заворотом (wraparound)**: выражение типа `10 - 15 - 1` превратится в колоссальное положительное число (например, `18 446 744 073 709 551 610`). Передав этот «лимит» в `strncat`, мы получим катастрофическое переполнение буфера, стерев всё на стеке.

#### Опасность 2: sizeof от указателя вместо массива
Если в будущем вы передадите буфер в функцию и попытаетесь внутри неё вычислить `sizeof(buffer)`, то оператор вернет не размер массива, а **размер указателя** (всегда 8 байт на 64-битной архитектуре). Это сломает всю математику расчёта.

```c
void append_text(char *buffer, char *addition) {
    // sizeof(buffer) здесь равен 8 (размер указателя), а не размеру массива из main!
    strncat(buffer, addition, sizeof(buffer) - strlen(buffer) - 1);
}
```

Правильное решение: размер массива считают там, где он объявлен, и передают в функцию отдельным параметром (`size_t buffer_size`).

#### Надёжный шаблон расчёта лимита
Чтобы защититься от заворота беззнакового типа, разделяют шаги и используют тернарный оператор (`условие ? значение_если_истина : значение_если_ложь`):

```c
// 1. Вычисляем текущую длину строки и физический размер буфера (buffer — массив в этой же функции)
size_t used = strlen(buffer);
size_t cap = sizeof(buffer);

// 2. Рассчитываем оставшееся место с защитой от переполнения
size_t remaining = (used < cap) ? (cap - used - 1) : 0;

// 3. Безопасно склеиваем строки строго в рамках лимита
strncat(buffer, addition, remaining);
```

Если строка каким-то образом уже превысила размер буфера (`used >= cap`), условие `used < cap` вернет ложь, `remaining` станет равен ровно `0` и функция `strncat` не допишет ни одного символа, а значит, запись за пределы буфера не произойдёт.

## Подсказки к задачам

*   **Подсказка к задаче 1:** Для безопасного расчета используйте шаблон с защитой от заворота беззнакового типа `size_t` (здесь `sizeof(first_name)` даёт размер всего массива, потому что массив объявлен в этой же функции):
    ```c
    size_t used = strlen(first_name);
    size_t cap = sizeof(first_name);
    size_t remaining = (used < cap) ? (cap - used - 1) : 0;
    strncat(first_name, last_name, remaining);
    ```
    Не забудьте подключить заголовочный файл `<string.h>` для доступа к функциям `strlen` и `strncat`.
*   **Подсказка к задаче 2:** Передайте имя массива в качестве первого аргумента функции: `count_char(text, 'm')`. Внутри функции используйте цикл `while (*str)` для движения по памяти. Таким образом, данные, выходящие за пределы массива `buffer`, начнут напрямую перетирать переменные, которые были объявлены в стеке ранее и лежат по более высоким адресам (так принято в учебной модели лекции; реальный компилятор может расставить переменные иначе).
