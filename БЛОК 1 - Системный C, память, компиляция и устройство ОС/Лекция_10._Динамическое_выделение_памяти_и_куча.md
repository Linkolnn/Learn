# Лекция 10: Динамическое выделение памяти и куча (Heap)

В предыдущих лекциях мы изучили, как переменные хранятся на стеке вызовов (автоматическая память) и как они создаются в сегментах постоянных данных (статическая память). Мы увидели, что стек вызовов — это упорядоченная, быстрая, но жестко ограниченная область памяти. 

Однако в реальных программах мы сталкиваемся со следующими проблемами:
1.  **Неизвестный размер данных заранее:** Как написать программу для обработки файла, размер которого мы узнаем только в момент запуска? Если выделить массив фиксированного размера на стеке (например, `char buffer[1000]`), то файл большего размера приведет к переполнению буфера, а файл меньшего размера заставит программу впустую расходовать память.
2.  **Время жизни переменных:** Переменные на стеке уничтожаются автоматически при выходе из функции. Но что делать, если функция должна создать сложную структуру данных (например, загрузить профиль игрока) и передать её дальше по программе для постоянной работы?

Для решения этих задач в языке Си существует механизм управления **динамической памятью**, которая физически размещается в особой области ОЗУ — **Куче (Heap)**.

---

## Подглава 10.1: Стек против Кучи (Stack vs Heap) на физическом уровне

Чтобы понять, как устроена куча, давайте взглянем на то, как операционная система организует виртуальное адресное пространство нашей программы в оперативной памяти (ОЗУ).

### Анатомия памяти запущенного процесса

Когда вы запускаете программу, операционная система выделяет под неё единый виртуальный непрерывный блок адресов. Этот блок делится на несколько специализированных сегментов:

```text
Высокие адреса ОЗУ (вверху памяти)
   |
   +------------------------------------+
   |  Стек вызовов (Stack)              |  <- Растет СВЕРХУ ВНИЗ (в сторону младших адресов)
   +------------------------------------+
   |  (Свободное пространство)          |
   |                                    |
   +------------------------------------+
   |  Куча (Heap)                       |  <- Растет СНИЗУ ВВЕРХ (в сторону старших адресов)
   +------------------------------------+
   |  Сегмент BSS (Неиниц. стат.данные) |
   +------------------------------------+
   |  Сегмент DATA (Инициализир. данные)|
   +------------------------------------+
   |  Сегмент CODE / TEXT (Код программы)|
   +------------------------------------+
   |
Низкие адреса ОЗУ (внизу памяти)
```

Как видно из схемы:
*   **Стек вызовов (Stack)** берет свое начало у самой границы адресного пространства (на высоких адресах) и при каждом вызове функции расширяется **вниз** (в сторону уменьшения адресов).
*   **Куча (Heap)** начинается сразу после сегментов статических данных программы и растет **вверх** (в сторону увеличения адресов).

Стек и куча «растут» навстречу друг другу. В современных операционных системах между ними находится колоссальное виртуальное пространство, поэтому их физическое столкновение практически исключено.

### Сравнительная таблица физических свойств стека и кучи

| Свойство | Стек вызовов (Stack) | Куча (Heap) |
| :--- | :--- | :--- |
| **Управление памятью** | Автоматическое (компилятор сам выделяет и удаляет фреймы функций при входе и выходе). | Ручное (программист обязан сам запрашивать и освобождать каждый байт памяти). |
| **Физический порядок** | Строгий порядок LIFO (Last In, First Out). Память выделяется последовательно. | Хаотичный. Память выделяется в виде разрозненных блоков в любых доступных местах. |
| **Скорость работы** | Невероятно высокая. Процессору достаточно сдвинуть значение регистра указателя стека (RSP). | Ниже стека. Требуется работа менеджера памяти, поиск свободного блока и обращение к ОС. |
| **Лимит по размеру** | Жестко ограничен операционной системой (обычно около 8 мегабайт). Превышение вызывает Stack Overflow. | Практически не ограничена. Лимитируется только объемом физической планки ОЗУ и файла подкачки. |
| **Время жизни данных** | Привязано к области видимости. Переменные уничтожаются сразу при выходе из функции. | Не привязано к функциям. Память живет до тех пор, пока программист явно не вызовет функцию очистки. |

## Подглава 10.2: Роль операционной системы и системные вызовы

Когда вашей программе требуется выделить блок памяти на куче, она не может сделать это напрямую, так как физическая память является общим ресурсом компьютера и строго охраняется ядром операционной системы (ОС).

Поэтому процесс выделения динамической памяти всегда строится на взаимодействии трех участников:
1.  **Ваш код на Си** — запрашивает блок памяти определенного размера.
2.  **Аллокатор (Менеджер памяти из стандартной библиотеки Си)** — библиотека, которая живет внутри вашей программы. Она берет на себя рутину по поиску свободных участков памяти и наведению порядка в куче.
3.  **Ядро операционной системы** — выделяет физические страницы памяти по запросу аллокатора.

### Как это работает на низком уровне:
Если аллокатору внутри вашей программы не хватает памяти для выполнения вашего запроса, он делает специальный **системный вызов (System Call)** к ядру операционной системы (например, `brk`, `sbrk` или `mmap` в Linux). 

Ядро ОС находит свободные физические страницы памяти, добавляет их в таблицу страниц вашего процесса и «прикрепляет» этот новый объем к куче вашей программы.

Поскольку системные вызовы — это очень «дорогая» и медленная операция для процессора (требующая переключения контекста процессора в режим ядра), аллокатор работает хитро. Он запрашивает у ОС память большими кусками (например, по несколько мегабайт за раз), а затем сам, без участия ОС, быстро нарезает эти куски на мелкие части по запросам вашего кода.

## Подглава 10.3: Утечки памяти (Memory Leaks) — системный кошмар

Поскольку куча полностью управляется программистом вручную, на вас ложится строгая обязанность: **каждый байт, который вы выделили в куче, должен быть возвращен обратно системе**.

Если вы забыли освободить выделенную память, возникает опаснейшее явление — **утечка памяти (Memory Leak)**.

### Физический смысл утечки памяти
Давайте рассмотрим, что происходит в ОЗУ на физическом уровне при утечке:

1.  Мы просим аллокатор выделить нам блок под массив из 1000 целых чисел в куче. Аллокатор находит свободное место и возвращает нам адрес этого блока (например, `0x5000`). Мы сохраняем этот адрес в указатель `int *ptr = 0x5000`.
2.  В процессе работы функции мы переписываем этот указатель другим адресом (например, `ptr = &x;`) или просто выходим из функции, на стеке которой был создан этот указатель `ptr`.
3.  **Физическая катастрофа:** Сам указатель `ptr` (переменная на стеке) прекратил свое существование. Но выделенный блок памяти в куче по адресу `0x5000` остался помеченным в таблицах менеджера памяти как **«занятый»**.
4.  У нас больше нет адреса `0x5000` (мы потеряли «ключ» от ячейки), поэтому мы физически не можем обратиться к этой памяти или освободить её. Она мертвым грузом висит в ОЗУ.

```text
  НА СТЕКЕ (Локальные переменные)           НА КУЧЕ (Динамическая память)
  
  [ ptr (хранит адрес 0x5000) ] ---------> [ Адрес 0x5000: блок 4000 байт ] (Занят)
               |
      (указатель стерт из стека 
       при выходе из функции)
               |
               v
  [ ptr больше не существует ]             [ Адрес 0x5000: блок 4000 байт ] (Занят навсегда!)
                                            <- Адрес потерян, освободить невозможно!
```

Если программа работает пару секунд (например, утилита командной строки), утечка памяти не успеет навредить системе, так как операционная система полностью забирает всю выделенную виртуальную память процесса обратно при его завершении.

Но если вы пишете фоновую программу, которая должна работать месяцами (веб-сервер, база данных, операционная система или игра):
*   Программа будет постепенно, мегабайт за мегабайтом, отбирать у системы свободную ОЗУ.
*   Компьютер начнет сильно тормозить, так как ОС будет вынуждена постоянно использовать медленный жесткий диск в качестве виртуальной памяти (свопинг).
*   Когда свободная память закончится полностью, сработает защитный механизм ядра Linux — **OOM Killer (Out Of Memory Killer)**. Он принудительно убьет процесс вашей программы, чтобы спасти всю операционную систему от мертвого зависания.

## Подглава 10.4: Выделение памяти через malloc

Для базового выделения памяти в куче используется функция **`malloc`** (Memory Allocation), которая объявлена в стандартном заголовочном файле **`<stdlib.h>`**.

### Синтаксис функции
```c
void *malloc(size_t size);
```

Эта функция принимает один аргумент — **размер выделяемой памяти в байтах** (`size_t` — это беззнаковый целочисленный тип), и возвращает значение типа **`void *`**.

### Что такое универсальный указатель `void *`?
В языке Си тип **`void *`** — это особый универсальный указатель. Он представляет собой «чистый адрес» в памяти без привязки к конкретному типу данных.
*   В Си указатель типа `void *` **автоматически и безопасно приводится к любому другому типу указателя** без какого-либо явного приведения типов. 
*   Писать явное приведение типов (например: `int *arr = (int *)malloc(...)`) в современном Си не нужно и считается плохим тоном (это C++-изм, который в чистом Си может скрыть опасные ошибки компиляции, если вы забыли подключить `<stdlib.h>`).

### Безопасное выделение памяти: оператор `sizeof`
Никогда не пишите размеры типов вручную цифрами (например, `4` для `int` или `8` для `double`). На разных аппаратных архитектурах размеры типов различаются. Всегда используйте оператор `sizeof`:

```c
#include <stdlib.h>

int main() {
    // Выделяем память под ОДНО целое число (4 байта)
    int *p = malloc(sizeof(int));

    // Выделяем память под динамический массив из 10 целых чисел (40 байт)
    int *arr = malloc(10 * sizeof(int));
}
```

### Смертельная ловушка: обязательная проверка на NULL

Выделение памяти в куче — это операция, которая **может завершиться ошибкой**. Если в системе физически закончилась оперативная память, или вы запросили слишком гигантский блок, аллокатор не сможет выполнить ваш запрос.

В случае неудачи функция `malloc` возвращает специальное значение **`NULL`** (нулевой указатель, физически указывающий на запрещенный адрес `0x0`).

**Золотое правило системного программиста:** Каждый раз после вызова `malloc` (или любой другой функции выделения памяти) вы обязаны проверить результат на `NULL`, прежде чем совершать какие-либо операции с указателем.

```c
int *arr = malloc(10 * sizeof(int));

// ПРОВЕРКА ОБЯЗАТЕЛЬНА!
if (arr == NULL) {
    // Память не выделилась. Мы обязаны корректно завершить работу или сообщить об ошибке.
    fprintf(stderr, "Критическая ошибка: не удалось выделить память на куче!\n");
    return 1; 
}

// Теперь мы можем безопасно работать с памятью
arr[0] = 42; 
```

Что произойдет, если проигнорировать эту проверку? Если память не выделилась, в `arr` запишется адрес `0x0`. При первой же попытке записать туда число (`arr[0] = 42`) процессор попытается разыменовать нулевой адрес. Операционная система немедленно пресечет эту операцию и жестко закроет программу с ошибкой **Segmentation Fault** (ошибка сегментации).

## Подглава 10.5: Освобождение памяти через free

Чтобы вернуть динамическую память операционной системе, используется функция **`free`** из заголовочного файла **`<stdlib.h>`**.

### Синтаксис функции
```c
void free(void *ptr);
```
Она принимает указатель на стартовый адрес блока памяти, который ранее был выделен через `malloc` (или другие функции выделения).

### Физический смысл работы free
Когда вы вызываете `free(arr)`:
1.  Аллокатор находит в своих внутренних таблицах блок, начинающийся по адресу `arr`, и помечает его как «свободный».
2.  **Важно:** Функция `free` **не зануляет и не стирает физические данные в ОЗУ** по этому адресу в целях экономии производительности. Символы или числа продолжают физически лежать в ячейках памяти, пока этот блок не будет выделен заново и поверх него не запишут новые данные.
3.  **Важно:** Функция `free` **не изменяет значение самого указателя `arr`**! Переменная-указатель `arr` на стеке по-прежнему хранит тот самый старый адрес в куче.

### Смертельная ловушка: Висячий указатель (Dangling Pointer)
Указатель, который хранит адрес памяти, которая уже была освобождена с помощью `free`, называется **висячим (или диким) указателем (Dangling Pointer)**.

```c
int *arr = malloc(5 * sizeof(int));
// ... работа с массивом ...
free(arr); // Память освобождена!

// Но arr ВСЁ ЕЩЕ хранит старый адрес!
printf("Адрес в arr: %p\n", (void *)arr); // Выведет старый адрес

arr[0] = 99; // УЖАСНАЯ ОШИБКА! Обращение к освобожденной памяти
```

Попытка обратиться к памяти через висячий указатель приводит к **неопределенному поведению (Undefined Behavior)**:
*   Программа может не вылететь сразу, так как этот адрес все еще принадлежит виртуальному пространству процесса.
*   Но эта память уже может быть выделена аллокатором под другие важные переменные вашей программы. Записывая данные в `arr[0]`, вы начнете незаметно и хаотично портить чужие переменные в ОЗУ, порождая труднонаходимые баги.

### Профессиональный стандарт очистки
Чтобы полностью обезопасить программу, всегда приучайте себя **занулять указатель сразу же после вызова `free`**:

```c
free(arr);
arr = NULL; // Теперь указатель гарантированно чист!
```

В языке Си вызов `free(NULL)` является абсолютно безопасной операцией, которая просто ничего не делает. Поэтому, если вы случайно вызовете `free` повторно для уже обнуленного указателя, программа не сломается. 

А попытка ошибочно записать данные в `arr[0] = 99` после зануления приведет к мгновенному и легко диагностируемому вылету (Segmentation Fault), вместо скрытого повреждения данных в ОЗУ.

## Подглава 10.6: Безопасные альтернативы и изменение размеров: calloc и realloc

Стандартная библиотека Си предоставляет еще две мощные функции для более тонкой и безопасной работы с динамической памятью.

### 1. Безопасное выделение с очисткой: `calloc`

Функция `malloc` выделяет память, но оставляет в ней «мусор» — любые старые числовые значения, которые лежали в этих ячейках ОЗУ ранее. Если вы случайно прочитаете данные из такого массива до инициализации, логика программы сломается.

Для гарантированного зануления памяти используется функция **`calloc`** (Cleared Allocation).

#### Синтаксис функции:
```c
void *calloc(size_t num, size_t size);
```
Она принимает два аргумента:
1.  `num` — количество элементов в массиве.
2.  `size` — размер одного элемента в байтах.

```c
// Выделяем память под 10 чисел типа int и ГАРАНТИРОВАННО зануляем все байты
int *arr = calloc(10, sizeof(int));
```

#### В чем физическое отличие от malloc?
*   `malloc` просто находит свободный блок и отдает его адрес. Все байты блока содержат случайный мусор.
*   `calloc` находит свободный блок, а затем физически заполняет каждый его байт нулевыми битами. Программа получает абсолютно чистый массив, где все элементы равны `0`.
*   *Примечание:* Из-за физического зануления байт функция `calloc` может работать чуть медленнее, чем `malloc`, но безопасность данных практически всегда стоит этой микроскопической потери производительности.

---

### 2. Динамическое масштабирование: `realloc`

Что делать, если мы выделили массив на 10 элементов, но в процессе работы программы поняли, что данных пришло больше и нам требуется расширить его до 20 элементов?

Для изменения размера уже выделенного блока динамической памяти существует функция **`realloc`** (Re-allocation).

#### Синтаксис функции:
```c
void *realloc(void *ptr, size_t new_size);
```
Она принимает указатель на старый блок `ptr` и новый желаемый размер в байтах `new_size`.

#### Как realloc работает под капотом (три физических сценария):

Когда вы запрашиваете изменение размера блока с адресом `ptr` до `new_size`, менеджер памяти анализирует кучу и выбирает один из трех путей:

*   **Сценарий 1: Расширение «на месте» (In-place Expansion).**  
    Если сразу за вашим текущим блоком в куче лежит свободный нераспределенный участок ОЗУ достаточного размера, менеджер памяти просто «прирезает» этот свободный хвост к вашему массиву. Адрес начала блока `ptr` при этом **не меняется**.
*   **Сценарий 2: Перенос и копирование (Move & Copy).**  
    Если соседнее место в куче уже занято другими переменными, расширить блок на месте физически невозможно. Тогда менеджер памяти:
    1.  Находит в куче совершенно новое свободное место, способное вместить `new_size` байт.
    2.  Физически копирует все старые данные из прежнего блока в этот новый блок.
    3.  **Автоматически освобождает (вызывает `free`) старый блок памяти.**
    4.  Возвращает вам **совершенно новый адрес ОЗУ** начала нового блока.
*   **Сценарий 3: Ошибка выделения.**  
    Если нового свободного места в куче нет, функция возвращает `NULL`. При этом **старый блок памяти остается абсолютно целым и валидным по прежнему адресу** — данные в нем не повреждаются и не удаляются.

#### Смертельная ловушка при использовании `realloc`

Самая популярная ошибка новичков — записывать результат изменения размера напрямую в тот же указатель:

```c
int *arr = malloc(10 * sizeof(int));
// ...

// ТАК ПИСАТЬ КАТЕГОРИЧЕСКИ НЕЛЬЗЯ!
arr = realloc(arr, 100 * sizeof(int)); 
```

**Почему это катастрофа?**  
Если в куче не окажется свободного места под 100 элементов, функция `realloc` вернет `NULL` и запишет его в переменную `arr`. 
*   Старый блок памяти на 10 элементов остался жив и занят.
*   Но мы стёрли его адрес в указателе `arr`, заменив его на `NULL`.
*   Результат: мы получили мгновенную и неизбежную **утечку памяти**, а также полностью потеряли доступ к нашим старым данным!

#### Профессиональный и безопасный стандарт масштабирования:
Для изменения размера всегда используйте **временный промежуточный указатель**:

```c
int *arr = malloc(10 * sizeof(int));
// ...

// 1. Записываем результат во временный указатель
int *temp = realloc(arr, 100 * sizeof(int));

// 2. Проверяем, удалось ли расширение
if (temp == NULL) {
    // Ошибка! Но старый arr все еще жив. Мы можем безопасно спасти данные.
    fprintf(stderr, "Ошибка изменения размера! Старые данные сохранены.\n");
    // ... обработка ошибки ...
} else {
    // 3. Переприсваиваем указатель только в случае успеха
    arr = temp;
}
```
