## 💡 Глоссарий ключевых терминов лекции

> 📌 **1. Сетевая декомпозиция (Network Layering)**
> * **Что это:** Архитектурный принцип разделения сложных сетевых коммуникаций на независимые иерархические уровни, где каждый уровень решает строго определённую задачу и предоставляет сервис вышестоящему уровню.

> 📌 **2. Модель OSI (Open Systems Interconnection)**
> * **Что это:** 7-уровневая эталонная теоретическая модель сетевого взаимодействия, разработанная Международной организацией по стандартизации (ISO) в 1984 году.

> 📌 **3. Стек протоколов TCP/IP**
> * **Что это:** Практическая 4-уровневая концептуальная модель и семейство сетевых протоколов, на которых построен современный глобальный Интернет (Application, Transport, Internet, Network Access).

> 📌 **4. Инкапсуляция (Encapsulation) и Деинкапсуляция (Decapsulation)**
> * **Что это:** **Инкапсуляция** — процесс добавления служебных заголовков (Headers) и концевиков (Trailers) к данным при их спуске с верхних уровней сети на нижние. **Деинкапсуляция** — обратный процесс извлечения полезных данных (Payload) при подъёме от физического уровня к приложению.

> 📌 **5. PDU (Protocol Data Unit — Блок данных протокола)**
> * **Что это:** Название порции данных на конкретном уровне сети: Данные (L5-L7) → Сегмент/Датаграмма (L4) → Пакет (L3) → Кадр (L2) → Биты/Сигналы (L1).

> 📌 **6. MAC-адрес (Media Access Control Address)**
> * **Что это:** Уникальный 48-битный (6-байтовый) физический адрес сетевого адаптера, зашиваемый производителем в ПЗУ карточки (OUI + уникальный номер). Пример: `00:1A:2B:3C:4D:5E`.

> 📌 **7. Протокол ARP (Address Resolution Protocol)**
> * **Что это:** Сетевой протокол, работающий на стыке L2 и L3 уровней (L2.5), предназначенный для определения L2 MAC-адреса узла по его известному L3 IP-адресу. Инкапсулируется непосредственно в кадр Ethernet (EtherType `0x0806`).

> 📌 **8. Домен коллизий (Collision Domain) и Широковещательный домен (Broadcast Domain)**
> * **Домен коллизий:** Сегмент сети, в котором при одновременной передаче двух узлов происходит наложение (коллизия) сигналов.
> * **Широковещательный домен:** Сегмент сети, в пределах которого широковещательный кадр (`FF:FF:FF:FF:FF:FF`) доставляется всем подключенным узлам данного сегмента/VLAN.

## Подглава 23.1: Зачем нужна сетевая декомпозиция?

Если бы разработчики сетевого ПО писали программы так, чтобы веб-браузер напрямую управлял электрическим напряжением на сетевой карте, любая смена типа кабеля (например, переход с витой пары на Wi-Fi или оптику) требовала бы полной перезаписи всего веб-браузера!

Идея разделения сети на независимые уровни развивалась с ранних сетей (ARPANET) и была формализована Международной организацией по стандартизации (ISO) в модели OSI (1984 год). Главные принципы **многоуровневой абстракции**:
1. Каждый уровень решает **узкую задачу** (например, L3 — маршрутизация, L4 — взаимодействие между процессами/портами).
2. Верхние уровни не знают о деталях реализации нижних (браузеру всё равно, отправляется ли HTTP-запрос по Wi-Fi, Ethernet или 5G).
3. Изменения на одном уровне не затрагивают соседние уровни, если интерфейс взаимодействия сохранён.

Передача данных в сети происходит по цепочке: при отправке данные приложения оформляются в TCP/UDP-сегменты, IP-пакеты и Ethernet-кадры, которые затем преобразуются физическим уровнем в электрические импульсы, оптические сигналы или радиоволны.

## Подглава 23.2: Сравнение моделей OSI (7 уровней) и TCP/IP (4 уровня)

Модель **OSI** является теоретическим стандартом и удобной эталонной структурой, а модель **TCP/IP** — реально работающим практическим стеком современного Интернета.

| Уровень OSI | Название уровня OSI | PDU | Уровень TCP/IP | Основные функции и протоколы |
| :--- | :--- | :--- | :--- | :--- |
| **L7** | **Application (Прикладной)** | Data (Данные) | **Application Layer** (Прикладной: L5-L7) | Сетевые сервисы приложений (`HTTP`, `HTTPS`, `DNS`, `SSH`, `FTP`) |
| **L6** | **Presentation (Представительский)** | Data (Данные) | **Application Layer** (Прикладной: L5-L7) | Кодирование, сжатие, шифрование (`TLS/SSL`, `ASCII`, `UTF-8`, `JPEG`) |
| **L5** | **Session (Сеансовый)** | Data (Данные) | **Application Layer** (Прикладной: L5-L7) | Управление сессиями и диалогами (`RPC`, `NetBIOS`, `SOCKS`) |
| **L4** | **Transport (Транспортный)** | Segment / Datagram | **Transport Layer** (Транспортный: L4) | Доставка между процессами (порты). **TCP** — надёжная доставка с контролем порядка и ошибок; **UDP** — ненадёжная датаграммная доставка без соединения (`TCP`, `UDP`) |
| **L3** | **Network (Сетевой)** | Packet (Пакет) | **Internet Layer** (Межсетевой: L3) | Глобальная IP-адресация узлов, маршрутизация (`IP`, `ICMP`, `IPsec`) |
| **L2** | **Data Link (Канальный)** | Frame (Кадр) | **Network Access Layer** (Сетевой доступ: L1-L2) | Доставка кадров в локальной сети по MAC-адресам (`Ethernet`, `Wi-Fi 802.11`, `ARP`) |
| **L1** | **Physical (Физический)** | Bits (Биты) | **Network Access Layer** (Сетевой доступ: L1-L2) | Передача сырых бит через физическую среду (электричество, свет, радио) |

## Подглава 23.3: Процесс инкапсуляции и деинкапсуляции данных

При отправке сообщения данные проходят сквозь сетевой стек сверху вниз (инкапсуляция) и снизу вверх при приёме (деинкапсуляция).

```text
[ Прикладной уровень (L7-L5) ] ──> Данные (Data)
                                          │  Инкапсуляция (отправка)
[ Транспортный уровень (L4)  ] ──> [ TCP/UDP Header | Data ]                 <── Сегмент / Датаграмма
                                          │
[ Сетевой уровень (L3)      ] ──> [ IP Header | TCP/UDP Header | Data ]      <── IP-Пакет
                                          │
[ Канальный уровень (L2)    ] ──> [ Ethernet Header | IP | TCP/UDP | Data | FCS ] <── Ethernet-Кадр
                                          │
[ Физический уровень (L1)   ] ──> 01011010110100101011...                   <── Биты по кабелю / эфиру
```

### Разделение обязанностей при деинкапсуляции (приём):
1. **Сетевая карта (NIC):** принимает физический сигнал (L1), декодирует биты и проверяет защитную контрольную сумму кадра **FCS (Frame Check Sequence / CRC32)** на уровне L2. Если FCS совпала, сетевая карта отбрасывает FCS и передаёт кадр через DMA/прерывание в драйвер сетевой карты операционной системы.
2. **Драйвер сетевой карты и сетевой стек ядра ОС:** разбирают L2 Ethernet-заголовок (EtherType), затем L3 IP-заголовок (IP-адрес назначения), затем L4 TCP/UDP-заголовок (порт назначения и контрольную сумму), после чего очищенная полезная нагрузка (Payload) передаётся в пользовательский процесс приложения.

## Подглава 23.4: Канальный уровень (L2). Кадр Ethernet II, MAC-адреса и ARP

На канальном уровне данные передаются внутри одной локальной сети (LAN) с помощью **MAC-адресов**.

### 1. Структура кадра Ethernet II
Кадр Ethernet II имеет следующую структуру:

```text
+-------------------+------------------+------------------+---------------------+---------------+
| Dest MAC (6 байт) | Src MAC (6 байт) | EtherType (2 б)  | Payload (46-1500 б) | FCS (4 байта) |
+-------------------+------------------+------------------+---------------------+---------------+
```

* **Dest MAC / Src MAC:** 6-байтовые физические адреса получателя и отправителя.
* **EtherType:** указывает тип вложенного L3-протокола (`0x0800` — IPv4, `0x0806` — ARP, `0x86DD` — IPv6).  
  * *Тегирование 802.1Q (VLAN):* При использовании 802.1Q 4-байтовый тег вставляется между Src MAC и основным EtherType. При этом поле сразу за Src MAC принимает значение `0x8100` (TPID), за которым следуют 2 байта TCI (VLAN ID и приоритет), а уже за ними — исходный EtherType.
* **Payload (Полезная нагрузка):** имеет переменную длину от 46 до 1500 байт (MTU). Минимальный размер полезной нагрузки равен **46 байтам** (чтобы итоговый кадр без FCS составлял не менее 60 байт, а с FCS — 64 байта). Если данные короче 46 байт (как ARP-пакет размером 28 байт), они дополняются нулевыми байтами (**Padding**).
* **FCS (Frame Check Sequence):** 4-байтовая контрольная сумма CRC32. *Примечание:* В дампах Wireshark FCS обычно отсутствует, так как сетевая карта проверяет и отбрасывает FCS до передачи кадра в операционную систему.

---

### 2. Протокол ARP (Address Resolution Protocol)
Компьютер знает IP-адрес получателя (например, `192.168.1.5`), но для отправки Ethernet-кадра сетевая карта **обязана знать его физический MAC-адрес**. Для решения этой задачи служит протокол ARP, работающий на стыке L2 и L3 уровней (L2.5).

```text
[ Узел A (192.168.1.2) ]                                           [ Узел B (192.168.1.5) ]
        │                                                                   │
        │ ──1. ARP Request (Broadcast: "Кто имеет 192.168.1.5? Скажите 1.2") ─> │ (Всем узлам VLAN)
        │                                                                   │
        │ <──2. ARP Reply (Unicast: "192.168.1.5 находится на MAC B") ───────│ (Только узлу A)
```

1. **ARP Request (Широковещательный):** Отправляется на MAC-адрес `FF:FF:FF:FF:FF:FF`. Все узлы данного сегмента локальной сети / VLAN получают запрос, но отвечает только владелец искомого IP.
2. **ARP Reply (Адресный / Unicast):** Узел B отвечает напрямую узлу A и сообщает свой MAC-адрес.
3. **ARP-Кэш:** Узел A сохраняет пару `IP -> MAC` в своей локальной таблице со временем жизни (TTL), чтобы не отправлять ARP-запросы перед каждым пакетом.

---

### 3. Коммутаторы (Switches) vs Концентраторы (Hubs)

* **Концентратор (Hub — L1):** работает на физическом уровне. Поступающий электрический сигнал с одного порта транслируется на все остальные порты без анализа адресов. Вся сеть образует **один домен коллизий** и **один широковещательный домен**.
* **Коммутатор (Switch — L2):** работает на канальном уровне. Обучается по входящим кадрам и строит **таблицу MAC-адресов** (`MAC -> Порт`). Передаёт unicast-кадры с известным MAC-адресом строго на нужный порт (а при неизвестном MAC-адресе получателя или Broadcast рассылает кадр на все порты). Каждый активный порт коммутатора образует **отдельный домен коллизий**, но вся сеть сегмента/VLAN остаётся **одним широковещательным доменом**.
* **Маршрутизатор (Router — L3):** объединяет разные IP-сети. Разделяет как домены коллизий, так и **широковещательные домены** (широковещательные кадры L2 через роутер не проходят).

## Подглава 23.5: Практикум работы с сетевым анализатором Wireshark

Wireshark — это основной инструмент сетевого инженера и разработчика для инспекции сырого сетевого трафика в реальном времени.

### Инструкция к пошаговому упражнению (Захват ARP-трафика):
1. Запустите Wireshark.
2. Выберите ваш активный сетевой интерфейс (`Ethernet` или `Wi-Fi`).
3. Нажмите кнопку **«Start Capture»** (иконка синего акульего плавника).
4. Откройте терминал и очистите ARP-кэш операционной системы:
   * **Linux:** `sudo ip neigh flush all` (или `sudo arp -d -a`)
   * **macOS:** `sudo arp -a -d`
   * **Windows (от имени администратора):** `arp -d *`
5. Введите в поле фильтра Wireshark: `arp` и нажмите Enter.
6. В терминале отправьте ICMP-запрос к вашему шлюзу по умолчанию (узнать IP шлюза можно через `ip route` в Linux, `netstat -rn` в macOS или `ipconfig` в Windows):
   * **Linux / macOS:** `ping -c 2 192.168.1.1`
   * **Windows:** `ping -n 2 192.168.1.1`  
   *(подставьте ваш IP шлюза)*.
7. **Результат в Wireshark:** Вы увидите две записи:
   * `ARP Request`: `Who has 192.168.1.1? Tell 192.168.1.100` (Destination MAC: `Broadcast ff:ff:ff:ff:ff:ff`).
   * `ARP Reply`: `192.168.1.1 is at 00:11:22:33:44:55` (Destination MAC: ваш личный MAC-адрес).

### Полезные фильтры отображения в Wireshark:
* `arp` — показывает только ARP-запросы и ответы.
* `eth.addr == 00:1a:2b:3c:4d:5e` — кадры с участием конкретного MAC-адреса.
* `ip.src == 192.168.1.10` — пакеты с конкретного IP-отправителя.
* `tcp.port == 80` — весь TCP-трафик, проходящий через порт 80 (как входящий, так и исходящий).

## Подглава 23.6: Разбор структуры Ethernet и ARP на языке Си

Ниже представлен готовый компилируемый Си-код, демонстрирующий, как бинарные сетевые заголовки описываются с помощью структур C и разворачиваются из сырого буфера байт.

> ⚠️ **Важное инженерное замечание о выравнивании и Strict Aliasing:**  
> 1. **Зачем нужен `#pragma pack(push, 1)`:** По умолчанию компилятор выравнивает поля структур по границам их типов. Например, в синтетической структуре вида `struct { uint8_t type; uint32_t value; }` поле `type` вызвало бы вставку 3 заполнительных байтов (padding) перед 4-байтовым полем `value`, увеличив размер структуры с 5 до 8 байт и сломав бинарные смещения! Кроме того, `#pragma pack(push, 1)` гарантирует точное совпадение при наложении структур на произвольные невыровненные буферы памяти.
> 2. **Strict Aliasing:** Прямое приведение `(EthernetHeader *)raw_frame` допустимо в учебном коде, но формально нарушает правило *Strict Aliasing* стандарта C. В промышленном Си-коде безопасное копирование сетевых структур выполняется через `memcpy()`.
3. **Сетевой порядок байт (Network Byte Order):** Порядок байт в сети всегда **Big-Endian**. На процессорах x86/ARM (Little-Endian) 16-битные поля преобразуются функцией `ntohs()` из `<arpa/inet.h>` (стандарт POSIX; на Windows используется `<winsock2.h>`).

```c
#include <stdio.h>
#include <stdint.h>
#include <arpa/inet.h> // ntohs

#pragma pack(push, 1)

// 1. Структура заголовка Ethernet II (14 байт)
typedef struct {
    uint8_t  dest_mac[6]; // MAC-адрес получателя
    uint8_t  src_mac[6];  // MAC-адрес отправителя
    uint16_t ethertype;   // Тип вложенного протокола (0x0800 = IPv4, 0x0806 = ARP)
} EthernetHeader;

// 2. Структура заголовка ARP-пакета (28 байт)
typedef struct {
    uint16_t hw_type;     // Тип аппаратного обеспечения (1 = Ethernet)
    uint16_t proto_type;  // Тип протокола (0x0800 = IPv4)
    uint8_t  hw_len;      // Длина MAC-адреса (6 байт)
    uint8_t  proto_len;   // Длина IP-адреса (4 байта)
    uint16_t opcode;      // Операция (1 = Request, 2 = Reply)
    uint8_t  sender_mac[6];
    uint8_t  sender_ip[4];
    uint8_t  target_mac[6];
    uint8_t  target_ip[4];
} ArpHeader;

#pragma pack(pop)

// Вспомогательные функции вывода
void print_mac(const uint8_t mac[6]) {
    printf("%02X:%02X:%02X:%02X:%02X:%02X", 
           mac[0], mac[1], mac[2], mac[3], mac[4], mac[5]);
}

void print_ip(const uint8_t ip[4]) {
    printf("%d.%d.%d.%d", ip[0], ip[1], ip[2], ip[3]);
}

int main(void) {
    // Учебный синтетический дамп ARP-кадра (14 б Ethernet + 28 б ARP = 42 б, без L2 Padding и FCS)
    uint8_t raw_frame[42] = {
        // Ethernet Header (14 байт)
        0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF,  // Dest MAC: Broadcast
        0x00, 0x1A, 0x2B, 0x3C, 0x4D, 0x5E,  // Src MAC
        0x08, 0x06,                          // EtherType: 0x0806 (ARP)

        // ARP Header (28 байт)
        0x00, 0x01,                          // Hardware Type: Ethernet (1)
        0x08, 0x00,                          // Protocol Type: IPv4 (0x0800)
        0x06,                                // Hardware Size: 6
        0x04,                                // Protocol Size: 4
        0x00, 0x01,                          // Opcode: 1 (ARP Request)
        0x00, 0x1A, 0x2B, 0x3C, 0x4D, 0x5E,  // Sender MAC
        192, 168, 1, 100,                    // Sender IP: 192.168.1.100
        0x00, 0x00, 0x00, 0x00, 0x00, 0x00,  // Target MAC (00:00:00:00:00:00)
        192, 168, 1, 1                       // Target IP: 192.168.1.1
    };

    size_t frame_len = sizeof(raw_frame);

    printf("=== АНАЛИЗ СЫРОГО ETHERNET-КАДРА ===\n\n");

    // Проверка минимально допустимой длины буфера
    if (frame_len < sizeof(EthernetHeader)) {
        fprintf(stderr, "Ошибка: длина кадра меньше размера Ethernet-заголовка!\n");
        return 1;
    }

    // Парсинг Ethernet-заголовка
    const EthernetHeader *eth = (const EthernetHeader *)raw_frame;
    uint16_t ethertype = ntohs(eth->ethertype);

    printf("[L2 Ethernet Header]\n");
    printf("  Получатель MAC: "); print_mac(eth->dest_mac); printf("\n");
    printf("  Отправитель MAC: "); print_mac(eth->src_mac); printf("\n");
    printf("  EtherType: 0x%04X ", ethertype);

    if (ethertype == 0x0806) {
        printf("(ARP Protocol)\n\n");

        if (frame_len < sizeof(EthernetHeader) + sizeof(ArpHeader)) {
            fprintf(stderr, "Ошибка: кадр слишком короткий для ARP-пакета!\n");
            return 1;
        }

        // Парсинг вложенного ARP-пакета (L2.5: переносится прямо внутри Ethernet-кадра)
        const ArpHeader *arp = (const ArpHeader *)(raw_frame + sizeof(EthernetHeader));
        uint16_t opcode = ntohs(arp->opcode);

        printf("[L2.5 ARP Payload]\n");
        printf("  Тип операции: %d (%s)\n", opcode, (opcode == 1) ? "ARP Request" : "ARP Reply");
        printf("  Кто спрашивает (MAC): "); print_mac(arp->sender_mac); printf("\n");
        printf("  Кто спрашивает (IP) : "); print_ip(arp->sender_ip); printf("\n");
        printf("  Кого ищут      (IP) : "); print_ip(arp->target_ip); printf("\n");
    } else {
        printf("(Другой протокол)\n");
    }

    return 0;
}
```

## Подглава 23.7: Чек-лист системного программиста при работе с сетевыми структурами

1. **Используйте `#pragma pack(push, 1)` для бинарных сетевых структур:**  
   Предотвращает вставку заполнительных байтов (padding) компилятором при смещении полей разных размеров или наложении структур на невыровненный сетевой буфер.
2. **Используйте `ntohs()` и `ntohl()`:**  
   Сетевой порядок байт — всегда Big-Endian. Для чтения 16- и 32-битных полей на x86/ARM преобразуйте их функциями из `<arpa/inet.h>` (POSIX) или `<winsock2.h>` (Windows).
3. **Различайте домены коллизий и широковещательные домены:**  
   * Hub (L1) = 1 домен коллизий, 1 широковещательный домен.
   * Switch (L2) = N доменов коллизий (по числу активных портов), 1 широковещательный домен на VLAN.
   * Router (L3) = N доменов коллизий, N широковещательных доменов.
4. **Учитывайте минимальный размер кадра и FCS:**  
   В реальной сети полезная нагрузка кадра дополняется нулями (padding) до 46 байт. Контрольная сумма FCS (4 байта) проверяется и удаляется сетевой картой на железном уровне.
