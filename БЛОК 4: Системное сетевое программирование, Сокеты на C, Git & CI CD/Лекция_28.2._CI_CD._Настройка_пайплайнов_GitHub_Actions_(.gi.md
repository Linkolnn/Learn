# Лекция 28.2: CI/CD. Настройка пайплайнов GitHub Actions (`.github/workflows/ci.yml`) для C-проектов

В предыдущей лекции (Проект 1 / Лекция 28.1) мы написали асинхронный многопользовательский TCP-чат на языке Си и собрали его с помощью `Makefile`. Мы убедились, что локальная сборка проходит успешно. Однако в командной разработке и продакшене полагаться только на локальную проверку разработчика («у меня всё работает!») смертельно опасно.

Сегодня мы разберём **Continuous Integration & Continuous Delivery (CI/CD)** — концепцию автоматического непрерывного тестирования, статического анализа и сборки кода при каждом изменении в репозитории. Мы изучим архитектуру **GitHub Actions**, напишем промышленный конфигурационный файл `.github/workflows/ci.yml` для автоматической компиляции C-проекта на сетевых сокетах, настроим статический анализатор `cppcheck`, проверку утечек памяти через `valgrind` и матричную сборку под разными компиляторами (`gcc` и `clang`).

---

## 💡 Глоссарий ключевых терминов лекции

> 📌 **1. Continuous Integration (CI — Непрерывная интеграция)**
> * **Что это:** Практика разработки ПО, заключающаяся в автоматической сборке и тестировании кода при каждом отправлении изменений (push/pull request) в центральный репозиторий.

> 📌 **2. Continuous Delivery / Deployment (CD — Непрерывная доставка / Развёртывание)**
> * **Что это:** Автоматизированный процесс доставки проверенного собранного артифакта в тестовое или продакшен-окружение (VPS, Docker-реестр, релизы GitHub).

> 📌 **3. GitHub Actions**
> * **Что это:** Встроенная в GitHub платформенная система автоматизации CI/CD, позволяющая выполнять произвольные скрипты и пайплайны на виртуальных машинах (Runners) при наступлении событий в репозитории.

> 📌 **4. Workflow (Рабочий процесс)**
> * **Что это:** Автоматизированная процедура, описываемая в YAML-файле в директории `.github/workflows/`, состоящая из одного или нескольких заданий (Jobs).

> 📌 **5. Runner (Исполнитель / Вёркер)**
> * **Что это:** Сервер или виртуальная машина (например, `ubuntu-latest`), на которой GitHub Actions запускает команды и шаги пайплайна.

> 📌 **6. Job & Step (Задание и Шаг)**
> * **Job:** Набор шагов, выполняемых на одном и том же раннере. Задания по умолчанию выполняются параллельно.
> * **Step:** Отдельная команда (`run`) или готовый переиспользуемый экшен (`uses`), выполняемый последовательно внутри задания.

> 📌 **7. Matrix Build (Матричная сборка)**
> * **Что это:** Механизм CI, позволяющий автоматически запускать одно и то же задание в нескольких комбинациях ОС (Linux, macOS) и компиляторов (`gcc`, `clang`).

## Подглава 28.2.1: Зачем нужен CI/CD в разработке на Си?

В компилируемых языках низкого уровня, таких как Си, цена ошибки компиляции или скрытого бага памяти крайне высока. Без автоматического CI-пайплайна возникают классические проблемы:

1. **«Синдром чужой машины»:** Разработчик скомпилировал код локально под macOS или специфичной версией `gcc`, но на целевом сервере Ubuntu код не собирается из-за отсутствующих системных библиотек или флагов.
2. **Пропущенные ошибки компиляции:** Кто-то забыл подключить заголовочный файл или добавил неиспользуемую переменную, проигнорировав предупреждения.
3. **Скрытые утечки памяти и UB:** Без автоматического запуска `valgrind` или Sanitizers (`ASan`/`UBSan`) утечка памяти в сокетах попадает в ветку `develop` и ломает продакшен под нагрузкой.
4. **Сломанные тесты при Merge PR:** Ветку сливают в `main` до проверки, ломая сборку всей остальной команде.

**Решение:** Настроить GitHub Actions так, чтобы при создании каждого Pull Request или Push в ветки `develop` / `main` автоматически запускалась виртуальная машина, устанавливала компилятор, собирала проект через `Makefile`, прогоняла статический анализ и тесты. Если хотя бы одна проверка упала — PR заблокирован к слиянию!

## Подглава 28.2.2: Архитектура GitHub Actions и синтаксис YAML

Конфигурация CI-пайплайнов GitHub Actions располагается строго в директории:
```text
.github/workflows/ci.yml
```

### Основные элементы файла `.github/workflows/*.yml`:

```yaml
name: C/C++ CI Pipeline # Название рабочего процесса

on: # Триггеры / события запуска
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main, develop ]

jobs: # Набор параллельных заданий
  build-and-test: # Идентификатор задания
    runs-on: ubuntu-latest # Виртуальная машина (Runner)

    steps: # Последовательные шаги задания
      - name: Checkout repository
        uses: actions/checkout@v4 # Готовый готовый экшен для скачивания кода

      - name: Run compilation
        run: make all # Команда в терминале
```

### Ключевые секции YAML:
* **`on` (Events):** Задает условия триггера (`push`, `pull_request`, `release`, `schedule` по cron).
* **`jobs.<job_id>.runs-on`:** Выбор платформы (`ubuntu-latest`, `ubuntu-22.04`, `macos-latest`, `windows-latest`).
* **`uses`:** Подключение готовых экшенов из GitHub Marketplace (например, `actions/checkout@v4`, `actions/upload-artifact@v4`).
* **`run`:** Выполнение произвольных команд оболочки Bash.

## Подглава 28.2.3: Полный конфигурационный файл `.github/workflows/ci.yml` для C-проекта

Ниже представлен промышленный конфигурационный файл `.github/workflows/ci.yml`, разработанный для нашего асинхронного TCP-чата (Проект 1).

Он включает в себя:
1. Проверку форматирования кода (`clang-format`).
2. Статический анализ кода (`cppcheck`).
3. Матричную компиляцию несколькими компиляторами (`gcc`, `clang`) с максимальными флагами предупреждений (`-Wall -Wextra -Werror -std=c11`).
4. Проверку утечек памяти через `valgrind`.
5. Архивацию собранных бинарников (`upload-artifact`).

```yaml
name: C TCP-Chat CI Pipeline

on:
  push:
    branches: [ "main", "develop", "feature/*", "release/*", "hotfix/*" ]
  pull_request:
    branches: [ "main", "develop" ]

permissions:
  contents: read

jobs:
  # ---------------------------------------------------------------------------
  # JOB 1: Статический анализ и проверка форматирования кода
  # ---------------------------------------------------------------------------
  lint-and-static-analysis:
    name: Code Linting & Static Analysis
    runs-on: ubuntu-latest

    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Install Analysis Tools
        run: |
          sudo apt-get update
          sudo apt-get install -y cppcheck clang-format

      - name: Check Code Formatting (clang-format)
        run: |
          echo "=== Проверка стиля форматирования кода ==="
          clang-format --dry-run --Werror src/*.c include/*.h || {
            echo "Ошибка: Код не соответствует стилю clang-format!"
            exit 1;
          }

      - name: Run Cppcheck Static Analyzer
        run: |
          echo "=== Запуск статического анализатора Cppcheck ==="
          cppcheck --enable=all --suppress=missingIncludeSystem \
                   --error-exitcode=1 -I include/ src/

  # ---------------------------------------------------------------------------
  # JOB 2: Матричная сборка и проверка утечек памяти (Valgrind)
  # ---------------------------------------------------------------------------
  build-and-test:
    name: Build & Test (${{ matrix.compiler }})
    needs: lint-and-static-analysis # Запускается только после успешного линтинга
    runs-on: ubuntu-latest

    strategy:
      fail-fast: false
      matrix:
        compiler: [gcc, clang] # Проверяем сборку обоими компиляторами!

    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Install Build Dependencies & Valgrind
        run: |
          sudo apt-get update
          sudo apt-get install -y build-essential valgrind ${{ matrix.compiler }}

      - name: Display Compiler Version
        run: |
          ${{ matrix.compiler }} --version
          make --version

      - name: Compile Project via Makefile
        env:
          CC: ${{ matrix.compiler }}
        run: |
          echo "=== Компиляция C-проекта с помощью ${{ matrix.compiler }} ==="
          make clean
          make CC=${{ matrix.compiler }} CFLAGS="-Wall -Wextra -Werror -std=c11 -O2 -Iinclude"

      - name: Verify Binary Executables
        run: |
          test -f bin/server || { echo "Ошибка: Исполняемый файл bin/server не найден!"; exit 1; }
          test -f bin/client || { echo "Ошибка: Исполняемый файл bin/client не найден!"; exit 1; }
          echo "Все исполняемые файлы успешно собраны."

      - name: Test Server Execution & Memory Leaks (Valgrind)
        run: |
          echo "=== Проверка запуска сервера под Valgrind ==="
          # Запускаем сервер на 2 секунды в фоновом режиме под Valgrind и проверяем утечки
          valgrind --leak-check=full \
                   --show-leak-kinds=all \
                   --errors-for-leak-kinds=all \
                   --error-exitcode=42 \
                   timeout 2s ./bin/server || status=$?
          
          # Код 124 возвращается утилитой timeout при плановой остановке через 2s
          if [ ${status:-0} -eq 124 ]; then
            echo "Сервер успешно отработал 2 секунды под Valgrind без утечек памяти!"
          elif [ ${status:-0} -eq 42 ]; then
            echo "CRITICAL: Valgrind обнаружил утечки памяти в C-сервере!"
            exit 1
          else
            echo "Сервер завершился с кодом status=${status:-0}"
          fi

      - name: Upload Build Artifacts (Only for GCC)
        if: matrix.compiler == 'gcc'
        uses: actions/upload-artifact@v4
        with:
          name: tcp-chat-binaries
          path: |
            bin/server
            bin/client
          retention-days: 7
```

## Подглава 28.2.4: Разбор ключевых механик CI-пайплайна

### 1. Матричная сборка (`strategy.matrix`)
```yaml
strategy:
  matrix:
    compiler: [gcc, clang]
```
GitHub Actions автоматически раздваивает задание: создаются две независимые виртуальные машины. Одна компилирует код компилятором `gcc`, вторая — `clang`. Это позволяет на самых ранних этапах поймать варнинги, специфичные только для одного из компиляторов.

### 2. Зависимость между заданиями (`needs`)
```yaml
build-and-test:
  needs: lint-and-static-analysis
```
Задание `build-and-test` не начнёт расходовать ресурсы процессора, пока задание `lint-and-static-analysis` не подтвердит, что код отформатирован и статический анализатор `cppcheck` не нашёл ошибок.

### 3. Автоматический запуск под `valgrind` и `timeout`
В сетевом программировании сервер работает в бесконечном цикле `while(1)`. Чтобы проверить его в CI, мы используем сочетание утилиты `timeout 2s` и флага `--error-exitcode=42` у `valgrind`:
* Если `valgrind` находит хотя бы один незакрытый сокет или утечку в `malloc()`, он возвращает специальный код ошибки `42`, фаля CI-степ.
* Если за 2 секунды работы утечек не найдено, утилита `timeout` завершает сервер по таймеру с кодом `124`, что считается успешным завершением степа.

### 4. Сохранение бинарных артифактов (`actions/upload-artifact@v4`)
Успешно скомпилированные бинарники `bin/server` и `bin/client` архивируются и прикрепляются к странице запуска CI в GitHub. Любой разработчик или QA-инженер может скачать готовые скомпилированные файлы прямо из интерфейса GitHub, не собирая их локально!

## Подглава 28.2.5: Защита веток в GitHub (Branch Protection Rules)

Наличие `.github/workflows/ci.yml` в репозитории делает возможным включение **Branch Protection Rules** в настройках GitHub-репозитория (`Settings` -> `Branches` -> `Branch protection rules`):

1. **Require a pull request before merging:** Запрещает делать `git push` напрямую в `main` и `develop`. Все изменения вносятся только через Pull Request.
2. **Require status checks to pass before merging:** Включает обязательное требование: PR невозможно слить (кнопка *Merge* заблокирована), пока пайплайн `C TCP-Chat CI Pipeline` не завершится с зелёной галочкой (`Success`)!
3. **Require signed commits / Code Reviews:** Требует одобрения от лида команды перед слиянием.

```text
[ Developer Push в feature/logging ]
               │
               ▼
[ Создание Pull Request в develop ]
               │
               ▼
[ Автоматический запуск GitHub Actions CI ]
 ├── Step 1: clang-format & cppcheck ──────> PASSED ✅
 ├── Step 2: gcc build & valgrind ─────────> PASSED ✅
 └── Step 3: clang build & valgrind ───────> PASSED ✅
               │
               ▼
[ Кнопка "Merge Pull Request" РАЗБЛОКИРОВАНА ] ──> [ Безопасный Merge в develop ]
```

## Подглава 28.2.6: Чек-лист инженера при настройке CI/CD для Си

1. **Всегда включайте флаг `-Werror` в CI-сборках:**  
   Компилятор должен трактовать любое предупреждение (warning) как фатальную ошибку компиляции.
2. **Используйте `clang-format --dry-run --Werror`:**  
   Это гарантирует единый стиль отступов и скобок во всем C-коде проекта.
3. **Проверяйте сокеты и память под `valgrind` в CI:**  
   Утечки памяти (`malloc`/`free`) и утечки дескрипторов (`socket`/`close`) должны блокировать мерж.
4. **Применяйте `-MMD -MP` в `Makefile`:**  
   Чтобы изменения в `.h` заголовочных файлах гарантированно вызывали пересборку связанных `.c` модулей в CI.
5. **Закрывайте секреты и переменные:**  
   Если CI деплоит бинарники на VPS через SSH, используйте `GitHub Secrets` (`${{ secrets.SSH_PRIVATE_KEY }}`), никогда не храните пароли в YAML!

## Подсказки к практическим задачам

* **Подсказка к Задаче 1:**  
  Разработчик забыл добавить самый первый обязательный шаг — скачивание кода из репозитория на виртуальную машину через экшен `actions/checkout@v4`! Без этого шага текущий рабочий каталог на раннере пуст.

* **Подсказка к Задаче 2:**  
  Используйте флаги компилятора `-fsanitize=address,undefined`:
  ```yaml
  - name: Build & Run with ASan/UBSan
    run: |
      gcc -Wall -Wextra -std=c11 -fsanitize=address,undefined -g src/*.c -o bin/sanitizer_test
      ./bin/sanitizer_test
  ```

* **Подсказка к Задаче 3:**  
  Используйте триггер `tags` в секции `on` и проверку `startsWith(github.ref, 'refs/tags/v')`:
  ```yaml
  on:
    push:
      tags:
        - 'v*'

  jobs:
    publish:
      if: startsWith(github.ref, 'refs/tags/v')
      runs-on: ubuntu-latest
      steps:
        - name: Echo Tag Release
          run: echo "Публикация релиза для тега ${{ github.ref_name }}"
  ```
