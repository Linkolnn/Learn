## 💡 Глоссарий ключевых терминов лекции

> 📌 **1. Система контроля версий (VCS — Version Control System)**
> * **Что это:** Программное обеспечение для фиксации, отслеживания и управления изменениями в исходном коде проекта с возможностью возврата к любой исторической точке.

> 📌 **2. Распределённая VCS (Distributed VCS)**
> * **Что это:** Архитектура контроля версий (Git, Mercurial), в которой каждый разработчик имеет локально полную копию всей истории репозитория, а не только рабочую копию.

> 📌 **3. Направленный ациклический граф (DAG — Directed Acyclic Graph)**
> * **Что это:** Математическая структура данных, лежащая в основе Git. Коммиты являются узлами графа, указывающими на своих предков (родительские коммиты). Граф не содержит циклов.

> 📌 **4. Объекты Git (Blob, Tree, Commit, Tag)**
> * **Blob (Binary Large Object):** объект хранения сырого содержимого файла без метаданных и имени.
> * **Tree:** объект представления директории, связывающий имена файлов/папок с их `blob`-хешами и правами доступа.
> * **Commit:** объект фиксации состояния, содержащий указатель на корневой `tree`, родительские коммиты, автора, коммитера, таймштамп и сообщение.
> * **Tag:** аннотированный тег — отдельный объект с именем, сообщением и ссылкой на другой объект (обычно коммит). Облегчённый (lightweight) тег — не объект, а просто ссылка `refs/tags/<имя>` на коммит.

> 📌 **5. Индекс / Зона подготавливаемых файлов (Index / Staging Area)**
> * **Что это:** Промежуточная бинарная структура данных (файл `.git/index`), содержащая срез файлов, подготовленных к включению в следующий коммит (`git add`).

> 📌 **6. Rebase (Перебазирование) vs Merge (Слияние)**
> * **Merge:** операция объединения историй двух веток с созданием специального коммита слияния (Merge Commit), имеющего двух родителей.
> * **Rebase:** операция последовательного повторного применения коммитов текущей ветки поверх указанной базовой ветки с созданием новых коммитов с новыми хешами (линейная история).

> 📌 **7. Утилита `make` и файл `Makefile`**
> * **Что это:** Утилита автоматизации сборки, определяющая на основе времени модификации файлов (`mtime`), какие части программы требуют перекомпиляции.

> 📌 **8. Правило Makefile (Rule)**
> * **Что это:** Инструкция вида `цель: пререквизиты`, за которой следует рецепт (команды оболочки). **Рецепт обязан начинаться со знака табуляции (`\t`)!**

> 📌 **9. Автоматические переменные Makefile (`$@`, `$<`, `$^`)**
> * **`$@`:** имя текущей цели (Target).
> * **`$<`:** имя первого пререквизита (Prerequisite).
> * **`$^`:** имена всех пререквизитов через пробел.

> 📌 **10. Фиктивные цели (`.PHONY`, Phony targets)**
> * **Что это:** Специальная директива Makefile, указывающая `make`, что данная цель является именем команды (например, `clean`, `all`, `test`), а не физическим файлом на диске.

## Подглава 27.1: Внутреннее устройство Git (DAG, объекты blob, tree, commit, tag)

Многие разработчики воспринимают Git как запутанный набор команд (`git add`, `git commit`, `git push`), но в основе **Git лежит простая идея: это хранилище «ключ — значение», адресуемое по содержимому (ключ — хеш от содержимого)!**

### 1. Объектная база данных `.git/objects/`
Все данные проекта хранятся в каталоге `.git/objects/`. Каждый объект идентифицируется 160-битным SHA-1 хешем (40 шестнадцатеричных символов), рассчитываемым от заголовочной строки типа/размера и содержимого. Первые 2 символа хеша становятся именем подпапки в `.git/objects/`, а остальные 38 — именем файла (содержимое сжато через `zlib`; позднее Git может упаковывать объекты в «packfile»). В новых версиях Git доступен и экспериментальный режим с SHA-256.

Git оперирует 4 базовыми типами объектов:

```text
[ Commit Object ] (Хеш: e8f1a2...)
  ├── Tree: a4b1c3... (Корневая директория)
  ├── Parent: 3f2d1b... (Родительский коммит)
  ├── Author: Dev <dev@example.com>
  └── Message: "Fix socket timeout bug"
        │
        ▼
[ Tree Object ] (a4b1c3...)
  ├── 100644 blob f2d1e0...  main.c
  ├── 100644 blob b8c9a1...  Makefile
  └── 040000 tree 9e8f7a...  src/
                                │
                                ▼
                         [ Tree Object ] (src/) (9e8f7a...)
                           └── 100644 blob c3d2e1...  server.c
```

1. **`blob` (байтовый массив):** Сохраняет только содержимое файла. Двум файлам с одинаковым содержимым в разных папках соответствует один и тот же `blob`! Права доступа, имя файла и путь в `blob` **не хранятся**.
2. **`tree` (дерево/директория):** Таблица, связывающая имена файлов, права (`100644` для обычных файлов, `100755` для исполняемых, `040000` для папок; есть и другие, например `120000` для символических ссылок) и SHA-1 хеши соответствующих `blob` или вложенных `tree`.
3. **`commit` (фиксация):** Текстовый заголовок, содержащий:
   * Ссылку на корневое `tree` проекта.
   * Ссылки на родительские коммиты (`parent`) — 0 у первого коммита, 1 у обычного коммита, 2+ у коммита слияния (Merge Commit).
   * Имя и email автора (`author`) и коммитера (`committer`) с временными метками (Unix-время) и часовым поясом.
   * Текст сообщения коммита.
4. **`tag` (аннотированный тег):** Объект, связывающий имя тега (например, `v1.0.0`) с хешем другого объекта (обычно коммита); содержит имя создателя тега (`tagger`), сообщение и, при желании, GPG-подпись. Облегчённый тег объектом не является — это просто файл-ссылка в `.git/refs/tags/`.

## Подглава 27.2: Жизненный цикл файлов и базовый workflow Git

В Git файлы проекта проходят через три основные области (рабочая копия, индекс, репозиторий) и четыре состояния.

```text
+------------------------------------------------------------------------------------------+
|                                    ЛОКАЛЬНЫЙ КОМПЬЮТЕР                                   |
|                                                                                          |
|  [ Working Directory ] ──git add──> [ Staging Area ] ──git commit──> [ Local .git ]      |
|     (Рабочая копия)                    (Индекс)                       (Репозиторий)      |
|                                                                          │        ▲       |
+--------------------------------------------------------------------------┼--------┼-------+
                                                                      git push   git fetch /
                                                                           │     git pull
                                                                           ▼        │
                                                         [ Remote Repository ] (GitHub / GitLab)
```

### Состояния файлов:
1. **Untracked (Неотслеживаемый):** файл присутствует в `Working Directory`, но отсутствует в `Staging Area` и последнем коммите.
2. **Modified (Изменённый):** файл отслеживается, был изменён в рабочей копии, но изменения еще не внесены в индекс.
3. **Staged (Подготовленный):** изменения файла проиндексированы командой `git add` и готовы войти в следующий коммит.
4. **Unmodified (Неизменённый):** содержимое файла в рабочей копии совпадает с индексом и последним коммитом `HEAD`.

### Базовые команды командной строки:
* `git init` — инициализация нового репозитория (создание скрытой папки `.git`).
* `git status` — вывод состояния рабочей копии и индекса.
* `git add <file|.>` — индексация файлов (создание `blob`-объектов в `.git/objects/` и обновление `.git/index`).
* `git commit -m "сообщение"` — фиксация индекса в коммит.
* `git log --graph --oneline --all` — наглядный просмотр ветвящегося графа коммитов.
* `git diff` — разница между рабочей копией и индексом (`Staging Area`).
* `git diff --staged` — разница между индексом и коммитом `HEAD`.
* `git restore <file>` — сброс изменений рабочей копии к состоянию индекса (**необратимо**: несохранённые изменения файла будут потеряны).
* `git restore --staged <file>` — убрать файл из индекса, не трогая изменения в рабочей копии.


### Настройка, ветки и удалённые репозитории (основные команды):
* `git config --global user.name "Имя"` и `git config --global user.email "mail@example.com"` — задать автора коммитов (один раз на компьютере).
* `git clone <url>` — скопировать удалённый репозиторий вместе со всей историей.
* `git branch` — список веток; `git switch -c <имя>` — создать ветку и переключиться на неё; `git switch <имя>` — переключиться на существующую.
* `git merge <ветка>` — влить указанную ветку в **текущую**.
* `git rebase <ветка>` — перенести коммиты **текущей** ветки поверх указанной.
* `git remote -v` — список удалённых репозиториев (обычно с именем `origin`).
* `git fetch` — скачать новые коммиты, не меняя рабочие файлы; `git pull` — `fetch` + слияние (или перебазирование при `git pull --rebase`); `git push` — отправить локальные коммиты в удалённый репозиторий.

## Подглава 27.3: Ветвление и слияние (Merge vs Rebase, слияние конфликтов)

### 1. Что такое ветка в Git?
Ветка в Git — это не копия папки и не копия файлов! **Ветка — это всего лишь лёгкий 41-байтовый файл-указатель (40 символов хеша и перевод строки) в каталоге `.git/refs/heads/<branch_name>`, содержащий SHA-1 хеш коммита** (после `git gc` ссылки могут храниться в общем файле `.git/packed-refs`).

Служебный файл `.git/HEAD` указывает на текущую активную ветку (например, `ref: refs/heads/main`), а ветка — на свой последний коммит. Поэтому `HEAD` указывает на коммит косвенно: `HEAD → main → C3`.

```text
[ Commit C1 ] <── [ Commit C2 ] <── [ Commit C3 ]
                                          ^
                                          │
                                       (main)
                                          ^
                                          │
                                       (HEAD)
```

---

### 2. Способы объединения веток: Merge vs Rebase

Допустим, от ветки `main` мы создали фичу-ветку `feature/socket-timeout` и сделали в ней коммиты `F1` и `F2`, пока в `main` появился коммит `M1`.

```text
          (F1) <── (F2)  <── (feature/socket-timeout)
         /
(C1) <── (C2) <── (M1)   <── (main)
```

#### Способ A: `git merge feature/socket-timeout` (Three-Way Merge)
Находясь в ветке `main` (`git switch main`), выполняем слияние. Git берёт общего предка (`C2`), вершину `main` (`M1`) и вершину `feature` (`F2`), выполняет трёхстороннее слияние и создаёт **Merge Commit (`M2`)** с двумя родителями (`M1` и `F2`). Существующие коммиты при этом не изменяются.

```text
          (F1) <── (F2)  <── (feature/socket-timeout)
         /          \
(C1) <── (C2) <── (M1) <── (M2: Merge Commit) <── (main)
```
* **Плюсы:** Точно сохраняет истинную историческую хронологию событий и не переписывает уже существующие коммиты, поэтому безопасен для общих веток.
* **Минусы:** Граф становится похож на «спагетти» из завязанных веток.
* **Частный случай (fast-forward):** если в `main` после создания `feature` новых коммитов не появилось, Git не создаёт Merge Commit, а просто сдвигает указатель `main` вперёд на `F2`.

#### Способ B: `git rebase main` (Перебазирование)
Находясь в ветке `feature/socket-timeout` (`git switch feature/socket-timeout`), выполняем `git rebase main`. Git берёт коммиты `F1` и `F2`, вычисляет их diff и заново поочерёдно «переприменяет» их поверх вершины `M1`. При этом создаются **новые коммиты `F1'` и `F2'` с новыми SHA-1 хешами**; старые `F1` и `F2` остаются в базе, но на них больше не указывает ни одна ветка.

```text
(C1) <── (C2) <── (M1) <── (F1') <── (F2') <── (feature/socket-timeout)
                    ^
                    │
                  (main)
```
После этого `main` по-прежнему указывает на `M1`. Чтобы включить фичу в `main`, нужно переключиться на неё и выполнить `git merge feature/socket-timeout`: это будет fast-forward без Merge-коммита, и `main` сдвинется на `F2'`.

* **Плюсы:** Чистая, линейная история без лишних Merge-коммитов.
* **Золотое правило Rebase:** **Никогда не перебазируйте коммиты, которые уже отправлены (`push`) в общий репозиторий и на которых могут основываться другие разработчики (например, общую ветку `main`)!** Rebase меняет хеши коммитов, поэтому история у остальных членов команды разойдётся с вашей, а для отправки пришлось бы делать `git push --force`.

### 3. Разрешение конфликтов слияния (Conflict Resolution)
Если при слиянии один и тот же участок файла был изменён в обеих ветках по-разному, Git останавливает слияние и вставляет в файл **маркеры конфликта**:

```c
<<<<<<< HEAD
int timeout_ms = 5000;
=======
int timeout_ms = 3000;
>>>>>>> feature/socket-timeout
```

Часть между `<<<<<<< HEAD` и `=======` — версия из текущей ветки (например, `main`), часть между `=======` и `>>>>>>>` — версия из вливаемой ветки (`feature/socket-timeout`). *При `rebase` стороны меняются местами: под `HEAD` оказывается ветка, поверх которой идёт перебазирование, а ниже — ваш коммит, который сейчас переприменяется.*

#### Алгоритм разрешения конфликта:
1. Командой `git status` увидеть список файлов с конфликтом (раздел *Unmerged paths*).
2. Открыть файл и вручную выбрать нужный вариант кода (удалив служебные маркеры `<<<<<<<`, `=======`, `>>>>>>>`).
3. Сохранить файл.
4. Выполнить `git add <file>` (пометить конфликт разрешённым).
5. Завершить процедуру: `git commit` (при merge) или `git rebase --continue` (при rebase).

Если запутались, процедуру можно отменить: `git merge --abort` или `git rebase --abort`.

## Подглава 27.4: Автоматизация сборки Си-проектов с помощью Makefile

По мере роста C-проекта ручная компиляция через `gcc main.c server.c client.c utils.c -o app` становится крайне медленной и сбойной. Если изменён только один файл `server.c`, перекомпилировать все остальные файлы — нерациональная трата времени.

Утилита **GNU Make** решает эту проблему за счет **инкрементальной сборки**: она сравнивает метку времени последнего изменения (`mtime`) файла-источника (`.c`) и скомпилированного объекта (`.o`). Если файл `.c` новее файла `.o`, выполняется пересборка.

### 1. Синтаксис правила Makefile
Каждое правило в файле с именем `Makefile` или `makefile` имеет следующую структуру:

```makefile
target: prerequisites ...
	recipe
	...
```

> ⚠️ **КРИТИЧЕСКОЕ ПРАВИЛО MAKEFILE:**  
> Строка с рецептом (`recipe`) **ОБЯЗАТЕЛЬНО должна начинаться с символа ТАБУЛЯЦИИ (`\t`)**! Если вставить 4 или 8 пробелов вместо табуляции, `make` завершится фатальной ошибкой вида `Makefile:2: *** missing separator.  Stop.`.

### 2. Автоматические переменные Make
В рецептах используются встроенные переменные-макросы:
* **`$@`:** Имя текущей цели (Target).
* **`$<`:** Имя первого пререквизита (First Prerequisite).
* **`$^`:** Имена всех пререквизитов через пробел без дубликатов.
* **`$?`:** Имена всех пререквизитов, которые новее цели.

Пример:
```makefile
server.o: server.c server.h
	gcc -Wall -c $< -o $@
# Выполнится как: gcc -Wall -c server.c -o server.o
```

## Подглава 27.5: Готовый чистый Makefile для C-проекта с автозависимостями (`-MMD -MP`)

Главный подвох базовых `Makefile`: если мы изменили заголовочный файл `server.h`, а правило `server.o: server.c` зависит только от `server.c`, `make` **НЕ заметит** изменений в `.h` и не пересоберёт объектный файл!

Флаги компилятора GCC **`-MMD -MP`** автоматически генерируют `.d` файлы зависимостей при компиляции:
* `-MMD` создаёт для каждого `.o` файл `.d` со списком подключённых пользовательских заголовков (системные `<...>` в него не попадают);
* `-MP` добавляет в `.d` пустые «фиктивные» цели для каждого заголовка, чтобы `make` не падал с ошибкой, если заголовок удалили или переименовали.

Ниже представлен практичный `Makefile` для C-проекта со структурой `src/*.c` и `include/*.h` (файлы в подкаталогах `src/` `wildcard` не найдёт — их нужно добавлять отдельно).

```makefile
# ==============================================================================
# ПРАКТИЧНЫЙ MAKEFILE С АВТОМАТИЧЕСКИМ ОТСЛЕЖИВАНИЕМ ЗАГОЛОВОЧНЫХ ЗАВИСИМОСТЕЙ
# ==============================================================================

# 1. Настройки компилятора и флагов
CC      := gcc
# -Werror превращает предупреждения в ошибки (удобно для CI; на учебных проектах можно убрать)
CFLAGS  := -Wall -Wextra -Werror -std=c11 -O2 -Iinclude
# -pthread нужен только если в проекте используются потоки (тогда его добавляют и в CFLAGS)
LDFLAGS := -pthread

# 2. Директории
SRC_DIR   := src
BUILD_DIR := build
BIN_DIR   := bin

# 3. Название итогового бинарного файла
TARGET := $(BIN_DIR)/server_app

# 4. Поиск всех C-файлов исходного кода в папке src/
SRCS := $(wildcard $(SRC_DIR)/*.c)

# 5. Преобразование списка src/file.c -> build/file.o
OBJS := $(patsubst $(SRC_DIR)/%.c, $(BUILD_DIR)/%.o, $(SRCS))

# 6. Список файлов авто-зависимостей (.d)
DEPS := $(OBJS:.o=.d)

# 7. Фони-цели (цели, не являющиеся реальными файлами)
.PHONY: all clean run dirs

# Главная цель по умолчанию (собирает директории и бинарный файл)
all: dirs $(TARGET)

# Создание служебных папок сборки
dirs:
	@mkdir -p $(BUILD_DIR) $(BIN_DIR)

# Линковка финального исполняемого файла из объектных файлов
$(TARGET): $(OBJS)
	@echo "[LINK] $@"
	$(CC) $(OBJS) $(LDFLAGS) -o $@

# Правило компиляции каждого .c файла в .o файл
# Флаги -MMD -MP создают файлы .d с зависимостями от включенных .h файлов!
$(BUILD_DIR)/%.o: $(SRC_DIR)/%.c | dirs
	@echo "[CC] $<"
	$(CC) $(CFLAGS) -MMD -MP -c $< -o $@

# Запуск собранного приложения
run: all
	./$(TARGET)

# Очистка всех сгенерированных бинарников и объектов
clean:
	@echo "[CLEAN] Очистка папок $(BUILD_DIR) и $(BIN_DIR)..."
	@rm -rf $(BUILD_DIR) $(BIN_DIR)

# Включение автосгенерированных файлов зависимостей (.d)
# Минус перед include игнорирует ошибки при первом запуске, когда .d еще не существуют!
-include $(DEPS)
```

## Подглава 27.6: Чек-лист системного программиста (Git & Makefile)

1. **Всегда используйте `.gitignore`:**  
   В репозиторий Git **не следует** коммитить объектные файлы (`*.o`), исполняемые бинарники, внешние библиотеки, сгенерированные файлы зависимостей (`*.d`), личные настройки редакторов (`.vscode/`, `.idea/`) и логи. Для Makefile из этой лекции достаточно `.gitignore` из двух строк: `build/` и `bin/`. Учтите, что `.gitignore` не действует на файлы, которые уже попали в репозиторий.
2. **В рецептах Makefile используйте строго Табуляцию (`\t`):**  
   Замена табуляции на пробелы сделает `Makefile` невалидным.
3. **Объявляйте служебные цели в `.PHONY`:**  
   Цели `all`, `clean`, `test`, `run`, `dirs` обязаны быть внесены в `.PHONY: ...`. Иначе, если кто-то создаст в папке файл с именем `clean`, команда `make clean` перестанет работать!
4. **Используйте флаги `-MMD -MP` и `-include $(DEPS)`:**  
   Это стандартный и надёжный способ гарантировать пересборку `.o` файлов при изменении заголовочных `.h` файлов.
5. **Не используйте Rebase в публичных ветках:**  
   `git rebase` хорошо подходит для локальных фича-веток перед отправкой в PR, но нельзя перебазировать коммиты, уже опубликованные в общем репозитории (например, общую ветку `main`).

## Практические задачи к Лекции 27

### Задача 1: Разбор графа коммитов Git
В репозитории сделаны коммиты. Разработчик находился на ветке `main` (коммит `C3`) и выполнил команду `git merge feature` (где ветка `feature` указывает на коммит `F2`). Ветки разошлись: `F2` не является потомком `C3`, и общим предком является, например, `C2`.

2. На какой коммит (прямо или через ветку) будет указывать `HEAD` после успешного завершения слияния?

## Подсказки к практическим задачам

* **Подсказка к Задаче 1:**  
  1. Коммит слияния (Merge Commit), создаваемый командой `git merge`, является узлом графа с двумя родительскими коммитами: первым родителем становится коммит текущей ветки (`C3`), а вторым — коммит вливаемой ветки (`F2`).
  2. `HEAD` по-прежнему указывает на активную ветку (`main`), а `main` после слияния продвигается на свежесозданный коммит слияния `M1`. Значит, `HEAD` указывает на `M1` косвенно (`HEAD → main → M1`).
* **Подсказка к Задаче 2:**  
  1. **Missing Separator (строки 5 и 8):** рецепты целей `clean` и `app` отформатированы 4 пробелами вместо знака ТАБУЛЯЦИИ (`\t`). `make` остановится с ошибкой `missing separator`.
  2. **Отсутствие `.PHONY`:** цель `clean` не объявлена в `.PHONY`. Если в папке появится файл с именем `clean`, команда `make clean` выдаст `'clean' is up to date.` и ничего не удалит.
  3. **Неверный порядок целей:** первой в файле стоит `clean`, а первая цель — это цель по умолчанию. Команда `make` без аргументов не соберёт программу, а выполнит очистку. Цель сборки (`all` или `app`) должна идти первой.

  Дополнительные недостатки (не ошибки синтаксиса): нет инкрементальной сборки (компиляция двух `.c` файлов одной командой без промежуточных `.o` пересобирает весь проект даже при изменении одного символа) и в `clean` жёстко записано `app` вместо переменной `$(TARGET)`.
* **Подсказка к Задаче 3:**  
  Используйте переменные `SRCS = src/main.c src/calculator.c`, подстановку `OBJS = $(SRCS:src/%.c=build/%.o)`, создание папок через `mkdir -p build bin`, флаги `CFLAGS = -Wall -Wextra -std=c11 -Iinclude` и цели `.PHONY: all clean`.
