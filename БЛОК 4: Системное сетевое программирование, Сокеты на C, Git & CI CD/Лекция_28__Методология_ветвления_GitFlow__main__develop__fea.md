# Лекция 28: Методология ветвления GitFlow (`main`, `develop`, `feature/`, `release/`, `hotfix/`)

В предыдущей лекции мы изучили внутреннее устройство Git (DAG коммитов, объекты `blob`, `tree`, `commit`), базовые операции с репозиторием и автоматизацию сборки C-проектов с помощью `Makefile`. 

Сегодня мы разберём **Методологию ветвления GitFlow** — один из самых известных и структурированных стандартов организации командной работы над кодом. Мы изучим назначение постоянных и временных веток, правила их создания и слияния, семантическое версионирование (**SemVer**), отработаем пошаговый консольный практикум, сравним GitFlow с **Trunk-Based Development** и **GitHub Flow**, а также научимся передавать версию Git в C-код через `Makefile` и флаги препроцессора.

## 💡 Глоссарий ключевых терминов лекции

> 📌 **1. Стратегия ветвления (Branching Strategy)**
> * **Что это:** Набор правил и соглашений в команде разработчиков, определяющих, когда создавать ветки, как их называть, как тестировать код и по каким правилам сливать изменения в основную ветку.

> 📌 **2. GitFlow**
> * **Что это:** Модель ветвления Git, предложенная Винсентом Дриссеном (Vincent Driessen) в 2010 году, спроектированная вокруг понятия «релизного цикла» и изолированных ролей веток (`main`, `develop`, `feature/`, `release/`, `hotfix/`).

> 📌 **3. Семантическое версионирование (SemVer / Semantic Versioning)**
> * **Что это:** Стандарт нумерации версий ПО в формате `MAJOR.MINOR.PATCH` (например, `v1.2.3`), где условия изменения каждой цифры строго регламентированы (ломающие изменения API, новые фичи, багфиксы).

> 📌 **4. Долгоживущие ветки (Long-Lived Branches)**
> * **Что это:** Ветки, которые существуют в репозитории на протяжении всего жизненного цикла проекта: `main` (продакшен-код) и `develop` (интеграция готовых фич).

> 📌 **5. Временные / Вспомогательные ветки (Short-Lived / Supporting Branches)**
> * **Что это:** Короткоживущие ветки, создаваемые под конкретную задачу и удаляемые после слияния: `feature/*` (новые фичи), `release/*` (стабилизация релиза), `hotfix/*` (срочные исправления в продакшене).

> 📌 **6. Флаг `--no-ff` (No Fast-Forward Merge)**
> * **Что это:** Параметр команды `git merge`, принудительно создающий явный коммит слияния (Merge Commit), сохраняя визуальную целостность и историю отдельной фича-ветки в графе Git.

> 📌 **7. Тег Git (Git Tag / Annotated Tag)**
> * **Что это:** Постоянная метка на конкретном коммите (например, `v1.1.0`). Аннотированный тег (`git tag -a`) — отдельный объект, который хранит имя версии, автора тега, дату и сообщение; облегчённый тег — просто ссылка на коммит. Используется для фиксации релизов в ветке `main`.

## Подглава 28.1: Зачем нужны стратегии ветвления? Проблема хаотичной разработки

Если в проекте работает больше одного человека и все делают коммиты напрямую в единственную ветку `main` (или `master`), команда часто сталкивается с серьёзными проблемами:
1. **Сломанный продакшен:** Недописанная или забагованная фича одного разработчика попадает к клиентам.
2. **Конфликты и блокировка:** Разработчики блокируют работу друг друга, не имея возможности протестировать свой код изолированно.
3. **Невозможность срочного исправления (Hotfix):** Если в продакшене найден критический баг, его нельзя исправить быстро, так как ветка замусорена незавершённым кодом будущих фич.

**Стратегия ветвления** решает эти проблемы, предоставляя **изоляцию**: разработка ведётся в параллельных ветках, а слияние происходит только после проверки и прохождения тестов.

## Подглава 28.2: Архитектура веток в методологии GitFlow

Модель **GitFlow** делит все ветки на две группы: **долгоживущие** (существуют всегда) и **вспомогательные** (создаются под задачу и удаляются).

```text
              v1.0.0                        v1.1.0          v1.1.1
main          ──●─────────────────────────────●───────────────●────────────
                │                             ▲     ▼         ▲
hotfix/*        │                             │     ─────●───────
                │                             │                 │
release/*       │                   ─────●───────               │
                ▼                   ▲           ▼               ▼
develop       ──●───────────────●───────────────●───────────────●──────────
                      ▼         ▲
feature/*             ─────●─────

```

На схеме время идёт слева направо; `●` — коммит или слияние, `▲` / `▼` — направление ветвления или слияния, над `main` подписаны теги. Сценарий совпадает с практикумом из подглавы 28.4: фича `feature/logging` → релиз `v1.1.0` → хотфикс `v1.1.1`.

### 1. Долгоживущие ветки (Long-Lived)

* **`main` (ранее `master`):**
  * Содержит **строго стабильный продакшен-код**.
  * Прямые коммиты в `main` **запрещены**!
  * Каждое слияние в `main` (релиз или хотфикс) представляет собой новый опубликованный релиз и **обязательно помечается аннотированным тегом** версии (например, `v1.0.0`, `v1.0.1`).

* **`develop`:**
  * Основная ветка интеграции текущей разработки.
  * Содержит последний законченный код всех готовых фич, предназначенных для следующего релиза.
  * Именно от `develop` создаются ветки `feature/*` и `release/*`.

---

### 2. Вспомогательные ветки (Short-Lived)

#### А. Фича-ветки (`feature/*` или `feature/feature-name`)
* **Назначение:** разработка новой функциональности (например, `feature/tcp-keepalive`, `feature/ssl-handshake`).
* **Ответвляется от:** `develop`.
* **Сливается в:** `develop`.
* **Именование:** `feature/короткое-описание` или `feature/TASK-123`.
* **Правило слияния:** Сливается с флагом `git merge --no-ff`, чтобы в истории сохранился явный блок коммитов данной фичи.

#### Б. Релизные ветки (`release/*` или `release/vX.Y.Z`)
* **Назначение:** подготовка и стабилизация нового планового релиза.
* **Ответвляется от:** `develop` (когда набран планируемый пул фич).
* **Сливается в:** **И в `main`**, **И в `develop`**!
* **Что происходит в релизной ветке:**
  * Замораживается добавление новых фич (Feature Freeze).
  * Выполняется тестирование, исправление мелких багов релиза.
  * Увеличивается (в англоязычной практике — *bump*) номер версии в документации, `Makefile` и заголовочных файлах.
* **Финал релиза:** Ветка сливается в `main` (ставят тег `v1.1.0`), а затем сливается обратно в `develop` (чтобы багфиксы релиза попали в будущую разработку). После этого `release/*` удаляется.

#### В. Хотфикс-ветки (`hotfix/*` или `hotfix/vX.Y.Z`)
* **Назначение:** СРОЧНОЕ исправление критической ошибки на продакшене.
* **Ответвляется от:** `main` (от коммита последнего стабильного релиза!).
* **Сливается в:** **И в `main`**, **И в `develop`**!
* **Результат:** В `main` создаётся новый патч-тег (например, `v1.0.1`), а исправление обязательно переносится в `develop`, чтобы баг не вернулся в следующем релизе.
* **Исключение:** если в момент хотфикса уже существует активная релизная ветка `release/*`, хотфикс сливают в неё вместо `develop`; в `develop` исправление попадёт вместе с релизом.

## Подглава 28.3: Семантическое версионирование (SemVer 2.0.0)

В системном и сетевом программировании строгое версионирование критично для совместимости библиотек и API. Стандарт **SemVer** использует формат:

```text
MAJOR.MINOR.PATCH     (например, v1.4.2)
```

1. **`MAJOR` (Мажорная версия):** увеличивается при внесении **обратно-несовместимых (ломающих) изменений API** (например, изменение сигнатур функций библиотек, переработка протокола сокетов).
2. **`MINOR` (Минорная версия):** увеличивается при добавлении **новой обратно-совместимой функциональности** (например, добавление нового типа запросов в эхо-сервер без поломки старых).
3. **`PATCH` (Патч-версия):** увеличивается при отправке **обратно-совместимых исправлений багов** (например, устранение утечки памяти в функции чтения данных вашей библиотеки или коррекция обработки `SIGPIPE`).

При увеличении `MAJOR` обнуляются `MINOR` и `PATCH`, при увеличении `MINOR` обнуляется `PATCH` (`v1.4.2` → `v1.5.0` → `v2.0.0`). Версии вида `0.y.z` означают начальную разработку: API в них может меняться в любой момент.

## Подглава 28.4: Пошаговый консольный практикум GitFlow

Ниже представлен полный пошаговый сценарий жизненного цикла проекта: от инициализации до создания фичи, проведения релиза и выпуска срочного хотфикса.

### Шаг 1: Инициализация репозитория и веток
*Примечание:* `git init -b` требует Git 2.28 или новее; вместо `git checkout -b <ветка>` можно использовать `git switch -c <ветка>`. Перед первым коммитом должны быть настроены `user.name` и `user.email` (см. лекцию 27).

```bash
# 1. Создание репозитория
mkdir network_server && cd network_server
git init -b main

# 2. Первоначальный коммит в main
echo "# Network Server C Project" > README.md
git add README.md
git commit -m "chore: initial commit"
git tag -a v1.0.0 -m "Release v1.0.0"

# 3. Создание ветки develop от main
git checkout -b develop
```

---

### Шаг 2: Разработка новой фичи (`feature/logging`)
```bash
# 1. Создаем фича-ветку от develop
git checkout develop
git checkout -b feature/logging

# 2. Вносим изменения и делаем коммиты
echo "// Logger module" > logger.c
git add logger.c
git commit -m "feat(logger): add basic logging functionality"

# 3. Завершение фичи: слияние в develop с --no-ff
git checkout develop
git merge --no-ff feature/logging -m "merge: feature/logging into develop"

# 4. Удаление локальной фича-ветки
git branch -d feature/logging
```

> 📌 **Зачем нужен флаг `--no-ff` (No Fast-Forward):**  
> Без `--no-ff` Git просто сдвинет указатель `develop` вперёд (Fast-Forward), и история фичи растворится в общей цепочке. Флаг `--no-ff` гарантирует создание узла слияния, сохраняя историю разработки фичи.

---

### Шаг 3: Проведение планового релиза (`release/v1.1.0`)
```bash
# 1. Создаем релизную ветку от develop
git checkout develop
git checkout -b release/v1.1.0

# 2. Подготовка релиза: фиксация версии, багфиксы
echo '#define SERVER_VERSION "1.1.0"' > version.h
git add version.h
git commit -m "chore(release): bump version to 1.1.0"

# 3. Слияние релиза в main и установка тега
git checkout main
git merge --no-ff release/v1.1.0 -m "merge: release/v1.1.0 into main"
git tag -a v1.1.0 -m "Release v1.1.0"

# 4. Слияние релиза обратно в develop
git checkout develop
git merge --no-ff release/v1.1.0 -m "merge: release/v1.1.0 into develop"

# 5. Удаление релизной ветки
git branch -d release/v1.1.0
```

---

### Шаг 4: Срочный хотфикс в продакшене (`hotfix/v1.1.1`)
```bash
# 1. Отводим хотфикс-ветку от main!
git checkout main
git checkout -b hotfix/v1.1.1

# 2. Исправляем критическую ошибку (например, утечку памяти или crash)
echo '#define SERVER_VERSION "1.1.1" // Fixed memory leak' > version.h
git add version.h
git commit -m "fix(socket): fix critical memory leak on client disconnect"

# 3. Слияние хотфикса в main и установка патч-тега
git checkout main
git merge --no-ff hotfix/v1.1.1 -m "merge: hotfix/v1.1.1 into main"
git tag -a v1.1.1 -m "Hotfix v1.1.1"

# 4. Обязательное слияние хотфикса в develop!
git checkout develop
git merge --no-ff hotfix/v1.1.1 -m "merge: hotfix/v1.1.1 into develop"

# 5. Удаление хотфикс-ветки
git branch -d hotfix/v1.1.1
```

> 📌 **Про одинарные кавычки в `echo`:** при двойных кавычках оболочка «съедает» внутренние кавычки, и в `version.h` попало бы `#define SERVER_VERSION 1.1.1` без кавычек, то есть не строка, а число-подобный токен. Поэтому всю команду берём в одинарные кавычки.

> 📌 **Отправка на сервер:** ветки и теги не публикуются автоматически. Например: `git push origin main develop --follow-tags`.

## Подглава 28.5: Интеграция Git-версии в Си-код через `Makefile`

В системном программировании на Си номер версии проекта и SHA-1 хэш текущего коммита передаются в компилятор автоматизировано при сборке через флаги препроцессора `-D`.

### Практичный `Makefile` с пробросом версии Git:

```makefile
CC      := gcc
CFLAGS  := -Wall -Wextra -std=c11 -O2
TARGET  := server_app

# Извлекаем последний тег Git и сокращенный SHA-1 коммита
GIT_VERSION := $(shell git describe --tags --always --dirty 2>/dev/null || echo "v0.0.0-unknown")

# Пробрасываем переменную в C-код как строковый макрос GIT_VERSION_STR.
# Кавычки ЭКРАНИРУЮТСЯ (\"), иначе оболочка их удалит, и в код попадёт не строка "v1.1.1",
# а токен v1.1.1 (ошибка компиляции).
CFLAGS  += -DGIT_VERSION_STR=\"$(GIT_VERSION)\"

.PHONY: all clean info

all: $(TARGET)

$(TARGET): main.c
	@echo "[CC] Компиляция $(TARGET) с версией $(GIT_VERSION)..."
	$(CC) $(CFLAGS) $< -o $@

info:
	@echo "Текущая версия Git: $(GIT_VERSION)"

clean:
	rm -f $(TARGET)
```

### Использование макроса версии в Си-коде (`main.c`):

```c
#include <stdio.h>

// Если макрос не был передан при компиляции, задаем дефолтное значение
#ifndef GIT_VERSION_STR
#define GIT_VERSION_STR "v0.0.0-dev"
#endif

int main(void) {
    printf("=========================================\n");
    printf(" Сетевой Сервер C-App\n");
    printf(" Версия сборки: %s\n", GIT_VERSION_STR);
    printf("=========================================\n\n");

    printf("Сервер успешно запущен...\n");
    return 0;
}
```

При сборке через `make` (в репозитории из практикума, на коммите с тегом `v1.1.1`) вывод программы отразит текущий тег Git:
```text
=========================================
 Сетевой Сервер C-App
 Версия сборки: v1.1.1
=========================================

Сервер успешно запущен...
```

> ⚠️ **Нюансы:**
> * Если на текущем коммите нет тега, `git describe` вернёт строку вида `v1.1.0-6-gbba75d5` (6 коммитов после тега и короткий хеш). Если изменены отслеживаемые файлы, добавится суффикс `-dirty`.
> * `make` сравнивает только время изменения файлов. Если вы переключили ветку или поставили новый тег, а `main.c` не менялся, `make` ответит `Nothing to be done`, и в бинарнике останется старая версия. Решение: выполнить `make clean && make` (или сделать цель зависимой от файла, который обновляется при смене версии).

## Подглава 28.6: Сравнение стратегий ветвления (GitFlow vs GitHub Flow vs Trunk-Based)

| Критерий | GitFlow | GitHub Flow | Trunk-Based Development |
| :--- | :--- | :--- | :--- |
| **Сложность** | Высокая (5 видов веток) | Низкая (2 вида веток) | Низкая по числу веток, но требует зрелого CI и тестов |
| **Основная ветка** | `develop` + `main` | `main` | `main` (Trunk) |
| **Релизный цикл** | Плановые релизы (недели/месяцы) | Непрерывный деплой (CD, по готовности PR) | Непрерывная интеграция (CI/CD, несколько раз в день) |
| **Применение** | ПО с плановыми релизами и поддержкой нескольких версий (библиотеки, коробочное ПО, драйверы) | Веб-сервисы, SaaS, простые API | Крупные команды с развитым CI/CD и feature flags (флагами функциональности), микросервисы |


> 💡 **Важно:** сам автор GitFlow, Винсент Дриссен, в 2020 году дописал к своей статье, что для ПО с непрерывной поставкой (веб-сервисы) GitFlow лучше не использовать и стоит выбрать более простую модель. GitFlow оправдан, когда нужны плановые релизы и поддержка нескольких версий одновременно. Недостаток GitFlow — долгоживущие ветки, из-за которых растёт число конфликтов слияния.

## Подглава 28.7: Чек-лист разработчика при работе по GitFlow

1. **Никогда не делайте коммиты напрямую в `main` и `develop`:** Все изменения вносятся только через ветки `feature/*`, `release/*` и `hotfix/*`.
2. **Всегда используйте `--no-ff` при слиянии:** Это сохраняет структуру истории в графе Git.
3. **Хотфиксы отводятся строго от `main`:** Не отводите хотфиксы от `develop`, иначе вы притащите в продакшен недописанные фичи!
4. **Не забывайте сливать `hotfix/*` и `release/*` в ОБЕ ветки (`main` и `develop`):** Иначе исправления пропадут из будущего релиза. (Единственное исключение: пока существует релизная ветка, хотфикс сливают в неё, а не в `develop`.)
5. **Тегируйте каждое слияние в `main`:** Используйте аннотированные теги `git tag -a vX.Y.Z -m "..."`.

Напишите правила для `Makefile`, которые:
1. Вызывают `git describe` и сохраняют текущую версию в `GIT_VER`.
2. Проверяют через `git status --porcelain`: если в рабочем каталоге есть незакоммиченные файлы, к строке версии добавляется суффикс `-dirty`.
3. Передают итоговую строку версии компилятору `gcc` через флаг `-DAPP_VERSION="..."` (в Makefile кавычки внутри значения нужно экранировать).

## Подсказки к практическим задачам

* **Подсказка к Задаче 1:**  
  * Сценарий 1: Исправление бага = увеличение `PATCH` → `v2.4.2`.
  * Сценарий 2: Новая функциональность без поломки API = увеличение `MINOR` и сброс `PATCH` → `v2.5.0`.
  * Сценарий 3: Ломающие изменения API = увеличение `MAJOR` и сброс остальных → `v3.0.0`.

* **Подсказка к Задаче 2:**  
  1. **Ошибка 1:** Хотфикс был отведен от ветки `develop` вместо `main`. Из-за этого в продакшен (`main`) попали все недописанные фичи из `develop`.
  2. **Ошибка 2:** Хотфикс не был слит в ветку `develop`. Из-за этого исправленный баг снова появится в следующем плановом релизе!

* **Подсказка к Задаче 3:**  
  Используйте встроенные функции `make`:
  ```makefile
  GIT_VER := $(shell git describe --tags --always 2>/dev/null || echo "v0.0.0")
  GIT_DIRTY := $(shell git status --porcelain 2>/dev/null)
  ifneq ($(GIT_DIRTY),)
      GIT_VER := $(GIT_VER)-dirty
  endif

  CFLAGS += -DAPP_VERSION=\"$(GIT_VER)\"
  ```
  Обратите внимание на экранирование кавычек (`\"`): без него оболочка удалит их, и в код попадёт не строка, а токен. Кроме того, `git status --porcelain` учитывает и неотслеживаемые файлы, а флаг `--dirty` у `git describe` — только изменения отслеживаемых файлов.
