## 💡 Глоссарий ключевых терминов лекции

> 📌 **1. Сетевой сокет (Network Socket)**
> * **Что это:** Абстрактный конечный узел (endpoint) двустороннего межпроцессного или сетевого взаимодействия. В операционных системах семейств UNIX/Linux сокет представляется объектом ядра и доступен процессу через обычный целочисленный **файловый дескриптор (File Descriptor — fd)**.

> 📌 **2. BSD Sockets API (POSIX Sockets)**
> * **Что это:** Стандартизированный интерфейс системных вызовов и структур данных на Си для сетевого программирования, впервые разработанный в дистрибутиве BSD UNIX (4.2BSD) в 1983 году и ставший стандартом де-факто во всех современных ОС (POSIX, Linux, macOS, Windows/Winsock).

> 📌 **3. Служебный сокет (Listening Socket)**
> * **Что это:** Пассивный сокет сервера, переводящийся вызовом `listen()` в состояние ожидания входящих подключений. Он не используется для передачи данных приложений, а лишь принимает запросы 3-Way Handshake и помещает их в очередь подключений ядра.

> 📌 **4. Подключённый сокет (Connected Socket / Client Socket)**
> * **Что это:** Активный сокет, создаваемый системным вызовом `accept()` на сервере (или `socket()` + `connect()` на клиенте). Он жестко привязан к конкретной 4-кортежной комбинации `(Src IP, Src Port, Dst IP, Dst Port)` и используется исключительно для обмена данными (`send()` / `recv()`).

> 📌 **5. Очередь подключений (Accept Queue / Backlog)**
> * **Что это:** Очередь в ядре ОС для хранения полностью установленных TCP-соединений (прошедших 3-Way Handshake), ожидавших вызова `accept()` со стороны пользовательского процесса.

> 📌 **6. Опция `SO_REUSEADDR`**
> * **Что это:** Опция сокета, устанавливаемая через `setsockopt()`, позволяющая повторно привязать сокет (`bind()`) к локальному порту, даже если на нём находятся старые соединения в состоянии `TIME_WAIT`.

## Подглава 26.1: Парадигма UNIX «Всё есть файл» и сокет как файловый дескриптор

В операционных системах UNIX и Linux фундаментальным принципом является абстракция ресурса через интерфейс файла. Файлы на диске, именованные каналы (Pipes), терминалы (TTY), устройства `/dev/null` и **сетевые сокеты** управляются через единый механизм — **таблицу файловых дескрипторов процесса**.

```text
[ Процесс в User Space ]
  │
  ├── File Descriptor Table (Таблица FD процесса)
  │     fd 0 ──> stdin  (Клавиатура)
  │     fd 1 ──> stdout (Экран)
  │     fd 2 ──> stderr (Экран)
  │     fd 3 ──> /var/log/app.log (Обычный файл на диске)
  │     fd 4 ──> Socket (struct socket в ядре Linux)
  │                 │
  │                 ▼
[ Kernel Space: Сетевой стек ядра ]
  ├── TCP/UDP Buffers (Send/Receive Queue)
  └── Сетевая карта (NIC / Driver)
```

### В чём сходство и отличие сокета от обычного файла?
1. **Сходства:**
   * Вызов `socket()` возвращает неотрицательный целочисленный дескриптор `int fd` (например, `fd = 4`).
   * К сокету применимы базовые системные вызовы ввода-вывода POSIX: `read(fd, buf, len)`, `write(fd, buf, len)`, `close(fd)`.
   * Сокет участвует в механизмах мультиплексирования I/O (`select()`, `poll()`, `epoll()`).
2. **Отличия:**
   * Сокет не поддерживает произвольное позиционирование (у потока байт нет «текущей позиции в файле»): системный вызов `lseek()` на сокете вернёт ошибку `ESPIPE` (Illegal seek).
   * Сокет требует специфических системных вызовов управления: конфигурирование адреса (`bind`), перевод в режим прослушивания (`listen`), управление параметрами сетевого стека (`setsockopt`).

## Подглава 26.2: Структуры данных сетевой адресации на Си

Для работы с сетевыми адресами в заголовочных файлах `<sys/socket.h>` и `<netinet/in.h>` определены специальные структуры.

### 1. Обобщённая структура `struct sockaddr`
Системные вызовы API сокетов (`bind`, `connect`, `accept`) являются универсальными и работают с любыми семействами адресов (IPv4, IPv6, UNIX Domain Sockets). Чтобы принимать указатель на любой тип адреса, используется базовое обобщённое определение:

```c
// Обобщенная структура (16 байт)
struct sockaddr {
    sa_family_t sa_family; // Семейство адресов (AF_INET, AF_INET6, AF_UNIX)
    char        sa_data[14]; // Сырые байты адреса и порта
};
```

### 2. Структура адреса IPv4 `struct sockaddr_in`
Для удобной работы с адресами IPv4 используется специализированная структура `struct sockaddr_in`. Перед передачей в системные функции её указатель приводится к типу `(struct sockaddr *)`:

```c
// Эти структуры уже определены в <netinet/in.h>. Здесь они приведены для наглядности,
// в своей программе их переопределять НЕ нужно (будет ошибка компиляции).
#include <netinet/in.h>

struct in_addr {
    in_addr_t s_addr; // 32-битный IPv4-адрес в сетевом порядке байт (Big-Endian)
};

struct sockaddr_in {
    sa_family_t    sin_family; // AF_INET (всегда AF_INET для IPv4)
    in_port_t      sin_port;   // 16-битный номер порта в сетевом порядке байт (htons)
    struct in_addr sin_addr;   // 32-битный IP-адрес (s_addr)
    unsigned char  sin_zero[8];// Заполнитель для совпадения размера с struct sockaddr (16 байт)
};
```

> ⚠️ **Критически важное правило инициализации:**  
> Перед заполнением полей `struct sockaddr_in` **обязательно** обнуляйте всю структуру с помощью `memset(&addr, 0, sizeof(addr))` или инициализации `= {0}`. Поле-заполнитель `sin_zero` и неиспользуемые поля должны быть нулевыми: на некоторых системах «мусор» в них приводит к ошибкам при `bind()` и `connect()`, а в любом случае это защищает от случайно оставшихся неинициализированных данных.

### 3. Структура `struct sockaddr_storage`
Для написания кода, не зависящего от протокола (IPv4/IPv6), применяется структура `struct sockaddr_storage`. Она гарантирует достаточный размер (в Linux — 128 байт) и выравнивание памяти для размещения адреса любого семейства. Типичный приём: передать `accept()` указатель на `sockaddr_storage`, а затем по полю `ss_family` определить, как интерпретировать адрес (`sockaddr_in` или `sockaddr_in6`). В примерах этой лекции для простоты используется только IPv4 и `sockaddr_in`.

## Подглава 26.3: Последовательность системных вызовов TCP-сервера

Создание сетевого сервера в архитектуре BSD Sockets выполняется в определённой последовательности шагов:

```text
[ TCP-Сервер ]                                            [ TCP-Клиент ]
      │                                                         │
1. socket() ──> Создание служебного сокета                     │
      │                                                         │
2. setsockopt(SO_REUSEADDR) ──> Настройка порта                │
      │                                                         │
3. bind() ────> Привязка к IP:Port                             │
      │                                                         │
4. listen() ──> Перевод сокета в режим ожидания                 │
      │                                                    1. socket()
      │                                                         │
      │ <────── 3-Way Handshake (SYN -> SYN-ACK -> ACK) ─────── 2. connect()
      │                                                         │
5. accept() ──> Выемка готового сокета из очереди               │
      │                                                         │
      ├────────────────────── send() / recv() ──────────────────┤
      │                                                         │
6. close() ───> Закрытие подключённого сокета             3. close()
```

### Подробный разбор системных вызовов сервера:

#### 1. `int socket(int domain, int type, int protocol)`
Создаёт сокет и возвращает файловый дескриптор.
* **`domain`:** семейство протоколов (`AF_INET` для IPv4, `AF_INET6` для IPv6, `AF_UNIX` для локальных сокетов).
* **`type`:** тип передачи данных (`SOCK_STREAM` для потокового TCP, `SOCK_DGRAM` для датаграммного UDP).
* **`protocol`:** конкретный протокол (обычно `0`: ядро само выбирает протокол по умолчанию для заданного `type` — TCP для `SOCK_STREAM`, UDP для `SOCK_DGRAM`).
* **Возврат:** `fd >= 0` при успехе, `-1` при ошибке (код ошибки в `errno`).

#### 2. `int bind(int sockfd, const struct sockaddr *addr, socklen_t addrlen)`
Связывает сокет `sockfd` с конкретным локальным IP-адресом и портом.
* **`addr`:** указатель на заполненную структуру `sockaddr_in`, приведённую к `(const struct sockaddr *)`.
* **`addrlen`:** размер структуры адреса `sizeof(struct sockaddr_in)`.
* **Возврат:** `0` при успехе, `-1` при ошибке (например, `EADDRINUSE` — порт уже занят другим процессом).

#### 3. `int listen(int sockfd, int backlog)`
Переводит сокет в пассивный режим ожидания входящих подключений.
* **`backlog`:** максимальная длина очереди полностью установленных TCP-соединений в ядре (например, `128` или константа `SOMAXCONN`).
* **Возврат:** `0` при успехе, `-1` при ошибке.

#### 4. `int accept(int sockfd, struct sockaddr *addr, socklen_t *addrlen)`
Блокируется, пока в очереди нет готовых соединений, затем извлекает первое из очереди `backlog` и создаёт **НОВЫЙ подключённый сокет**.
* **`sockfd`:** служебный прослушивающий сокет.
* **`addr`:** указатель на структуру `sockaddr_in`, в которую ядро запишет IP-адрес и порт подключившегося клиента (если адрес клиента не нужен, можно передать `NULL` и для `addr`, и для `addrlen`).
* **`addrlen`:** указатель на переменную типа `socklen_t`. **Обязательно** должен содержать `sizeof(struct sockaddr_in)` до вызова! Ядро перезапишет его реальным размером записанного адреса.
* **Возврат:** новый файловый дескриптор `client_fd >= 0` для обмена данными с этим клиентом, или `-1` при ошибке.

> 💡 **Различие служебного и подключённого сокетов:**  
> Служебный сокет (`listen_fd`) живет всё время работы сервера и выполняет единственную задачу — принимает новые подключения через `accept()`. Подключённый сокет (`client_fd`) создаётся отдельно для каждого клиента и закрывается вызовом `close(client_fd)` после завершения диалога.

## Подглава 26.4: Последовательность системных вызовов TCP-клиента и обмен данными

### 1. Вызов `connect()` со стороны клиента
Клиент создаёт сокет вызовом `socket()` и инициирует процедуру 3-Way Handshake с сервером:

```c
int connect(int sockfd, const struct sockaddr *addr, socklen_t addrlen);
```
* **`addr`:** IP-адрес и порт целевого сервера.
* **Возврат:** `0` при успешном установлении соединения, `-1` при ошибке (`ECONNREFUSED` — на данном порту никто не слушает, `ETIMEDOUT` — таймаут ответа).

### 2. Приём и отправка данных: `send()` и `recv()`
После успешного соединения обмен данными выполняется функциями `send()` и `recv()` (или универсальными `write()` / `read()`):

```c
ssize_t send(int sockfd, const void *buf, size_t len, int flags);
ssize_t recv(int sockfd, void *buf, size_t len, int flags);
```
* **`flags`:** флаги передачи (например, `0` для стандартного режима, или `MSG_NOSIGNAL` для предотвращения аварийного завершения процесса сигналом `SIGPIPE` при записи в закрытый сокет; этот флаг есть в Linux, а в macOS вместо него используется опция сокета `SO_NOSIGPIPE`).
* **Возвращаемое значение `recv()`:**
  * `> 0`: количество реально прочитанных байт.
  * `= 0`: **удалённая сторона корректно закрыла соединение (получен TCP FIN)**; для сервера это означает, что клиент закончил передачу.
  * `< 0`: произошла ошибка (проверить `errno`).

> ⚠️ **Потоковая природа TCP:**  
> TCP — это непрерывный поток байт (*Byte Stream*). Однократный вызов `send(fd, buf, 1000, 0)` **не гарантирует**, что получатель вычитает все 1000 байт за один вызов `recv()`. Правильный системный код всегда выполняет чтение и запись в цикле!

### 3. Закрытие сокета: `close()` vs `shutdown()`
* `close(sockfd)`: закрывает дескриптор и уменьшает счётчик ссылок на сокет в ядре (ссылок может быть несколько, например после `fork()` или `dup()`). Когда счётчик достигает 0, ядро инициирует закрытие TCP-соединения (отправка `FIN`).
* `shutdown(sockfd, how)`: позволяет закрыть передачу в одном направлении (например, `SHUT_WR` — запретить дальнейшую отправку данных, но продолжить чтение ответа).

## Подглава 26.5: Опции сокетов и обработка системных ошибок

### 1. Установка опции `SO_REUSEADDR`
При перезапуске сервера попытка повторного вызова `bind()` на тот же порт может завершиться ошибкой `EADDRINUSE` из-за того, что предыдущие сокеты находятся в состоянии `TIME_WAIT` (в Linux — 60 секунд).  
Чтобы разрешить повторное использование порта, перед вызовом `bind()` **всегда** устанавливайте опцию `SO_REUSEADDR` (она не позволит занять порт, на котором прямо сейчас слушает другой процесс, — в этом случае `EADDRINUSE` останется):

```c
int opt = 1;
if (setsockopt(listen_fd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt)) < 0) {
    perror("setsockopt SO_REUSEADDR failed");
    close(listen_fd);
    exit(EXIT_FAILURE);
}
```

### 2. Основные коды ошибок `errno` при работе с сокетами:
* **`EADDRINUSE`:** локальный IP-адрес или порт уже используются другим сокетом.
* **`ECONNREFUSED`:** узел существовал, но на указанном порту нет прослушивающего сокета.
* **`EINTR`:** системный вызов был прерван пришедшим сигналом ОС (требуется повторить вызов).
* **`EAGAIN` / `EWOULDBLOCK`:** операция не может быть выполнена немедленно на неблокирующем сокете.
* **`EPIPE`:** попытка записи в сокет, удаленная сторона которого полностью закрыла чтение. По умолчанию ОС генерирует сигнал `SIGPIPE`, который убьёт процесс, если сигнал не проигнорировать: `signal(SIGPIPE, SIG_IGN);`.

## Подглава 26.6: Разбор компилируемого Си-кода TCP Эхо-сервера

Ниже представлен полный, готовый Си-код, демонстрирующий рабочий блокирующий TCP Эхо-сервер. Сервер принимает одно подключение, читает данные, отправляет их обратно («эхо») и корректно закрывает ресурсы. В роли клиента выступает утилита `netcat`.

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <stdint.h>
#include <signal.h>
#include <sys/types.h>
#include <sys/socket.h>
#include <netinet/in.h>
#include <arpa/inet.h>

#define PORT 8080
#define BUFFER_SIZE 1024
#define BACKLOG 5

int main(void) {
    // Игнорируем сигнал SIGPIPE, чтобы запись в закрытый сокет не завершала процесс
    signal(SIGPIPE, SIG_IGN);

    // 1. Создание прослушивающего сокета IPv4 TCP
    int listen_fd = socket(AF_INET, SOCK_STREAM, 0);
    if (listen_fd < 0) {
        perror("Ошибка создания сокета (socket)");
        exit(EXIT_FAILURE);
    }

    // 2. Установка опции SO_REUSEADDR для быстрого перезапуска сервера
    int optval = 1;
    if (setsockopt(listen_fd, SOL_SOCKET, SO_REUSEADDR, &optval, sizeof(optval)) < 0) {
        perror("Ошибка установки SO_REUSEADDR (setsockopt)");
        close(listen_fd);
        exit(EXIT_FAILURE);
    }

    // 3. Инициализация структуры адреса сервера (IPv4, INADDR_ANY, PORT 8080)
    struct sockaddr_in server_addr;
    memset(&server_addr, 0, sizeof(server_addr)); // Обязательное обнуление
    server_addr.sin_family = AF_INET;
    server_addr.sin_addr.s_addr = htonl(INADDR_ANY); // Слушать на всех сетевых интерфейсах
    server_addr.sin_port = htons(PORT);             // Порт в сетевом порядке байт

    // 4. Привязка сокета к IP и порту (bind)
    if (bind(listen_fd, (struct sockaddr *)&server_addr, sizeof(server_addr)) < 0) {
        perror("Ошибка привязки сокета (bind)");
        close(listen_fd);
        exit(EXIT_FAILURE);
    }

    // 5. Перевод сокета в режим прослушивания (listen)
    if (listen(listen_fd, BACKLOG) < 0) {
        perror("Ошибка перевода в режим прослушивания (listen)");
        close(listen_fd);
        exit(EXIT_FAILURE);
    }

    printf("=== TCP ЭХО-СЕРВЕР ЗАПУЩЕН НА ПОРТУ %d ===\n", PORT);
    printf("Ожидание входящих подключений...\n\n");

    // 6. Принятие подключения клиента (accept)
    struct sockaddr_in client_addr;
    socklen_t client_addr_len = sizeof(client_addr); // Обязательная инициализация длины!

    int client_fd = accept(listen_fd, (struct sockaddr *)&client_addr, &client_addr_len);
    if (client_fd < 0) {
        perror("Ошибка принятия подключения (accept)");
        close(listen_fd);
        exit(EXIT_FAILURE);
    }

    // Преобразование IP-адреса клиента в текстовую строку
    char client_ip[INET_ADDRSTRLEN];
    inet_ntop(AF_INET, &client_addr.sin_addr, client_ip, sizeof(client_ip));
    uint16_t client_port = ntohs(client_addr.sin_port);

    printf("Новое подключение от клиента: %s:%d (client_fd = %d)\n",
           client_ip, client_port, client_fd);

    // 7. Цикл Эхо-обмена данными с клиентом
    char buffer[BUFFER_SIZE];
    ssize_t bytes_read;

    while ((bytes_read = recv(client_fd, buffer, sizeof(buffer) - 1, 0)) > 0) {
        buffer[bytes_read] = '\0'; // Гарантируем C-строку
        printf("Получено %zd байт: %s", bytes_read, buffer); // строка уже содержит '\n' от netcat

        // Отправляем вычитанные данные обратно клиенту ("Эхо").
        // Для простоты демо send() вызван один раз; в реальном коде отправку нужно
        // выполнять в цикле, пока не уйдут все байты (см. Задачу 3 и функцию send_all).
        ssize_t bytes_sent = send(client_fd, buffer, (size_t)bytes_read, 0);
        if (bytes_sent < 0) {
            perror("Ошибка отправки данных (send)");
            break;
        }
    }

    if (bytes_read == 0) {
        printf("\nКлиент %s:%d отключился (получен TCP FIN).\n", client_ip, client_port);
    } else if (bytes_read < 0) {
        perror("Ошибка чтения из сокета (recv)");
    }

    // 8. Корректное закрытие ресурсов
    close(client_fd);
    printf("Подключённый сокет client_fd = %d закрыт.\n", client_fd);

    close(listen_fd);
    printf("Служебный сокет listen_fd = %d закрыт. Сервер остановлен.\n", listen_fd);

    return 0;
}
```

## Подглава 26.7: Чек-лист системного программиста при работе с BSD сокетами

1. **Всегда обнуляйте структуры `sockaddr_in`:**  
   Используйте `memset(&addr, 0, sizeof(addr))` перед заполнением полей.
2. **Всегда инициализируйте `socklen_t len = sizeof(addr)` перед `accept()`:**  
   Аргумент длины адреса в `accept()` передаётся по указателю как *Value-Result*. Забытая инициализация приведёт к непредсказуемому поведению: ошибке `EINVAL` либо к тому, что адрес клиента будет записан не полностью.
3. **Устанавливайте `SO_REUSEADDR` до вызова `bind()`:**  
   Это избавит сервер от ошибок `EADDRINUSE` при быстрой перезагрузке (из-за `TIME_WAIT`), но не поможет, если порт занят другим работающим процессом.
4. **Проверяйте возвращаемое значение `recv()` на `0`:**  
   Возврат `0` — это признак того, что удалённая сторона закрыла соединение (вызвала `close()` или `shutdown(SHUT_WR)`) и прислала TCP FIN.
5. **Обрабатывайте сигнал `SIGPIPE`:**  
   Игнорируйте `SIGPIPE` через `signal(SIGPIPE, SIG_IGN)` или используйте флаг `MSG_NOSIGNAL` в `send()` (Linux).
6. **Учитывайте потоковую природу TCP:**  
   Не закладывайтесь на то, что `send()` и `recv()` передадут все данные за один вызов. Напишите обёртки для циклического чтения/записи.

## Подсказки к практическим задачам

* **Подсказка к Задаче 1:**  
  * Код скомпилируется без ошибок (синтаксис корректен).
  * В Linux `listen()` на сокете без `bind()` **не** возвращает ошибку: ядро автоматически привязывает сокет к случайному свободному (эфемерному) порту и переводит его в режим прослушивания.
  * Последующий `bind()` вернёт `-1` с кодом `EINVAL` (сокет уже привязан и прослушивается).
  * Итог: сервер не слушает нужный порт, и клиенты получают `ECONNREFUSED`. Правильный порядок: `socket()` → `bind()` → `listen()` → `accept()`.
* **Подсказка к Задаче 2:**  
  * Если все 5 подключений ещё активны, открыто **6 сокетов**: 1 служебный прослушивающий сокет (`listen_fd`) + 5 подключённых сокетов (`client_fd_1` ... `client_fd_5`).
  * Новые запросы 3-Way Handshake приходят на служебный сокет (`listen_fd`).
  * Отправка данных конкретному клиенту #3 выполняется строго через его подключённый сокет `client_fd_3`.
* **Подсказка к Задаче 3:**  
  Организуйте цикл `while (total_sent < len)`:
  ```c
  ssize_t send_all(int socket_fd, const void *buf, size_t len) {
      size_t total_sent = 0;
      const char *ptr = (const char *)buf;

      while (total_sent < len) {
          ssize_t sent = send(socket_fd, ptr + total_sent, len - total_sent, MSG_NOSIGNAL);
          if (sent < 0) {
              if (errno == EINTR) continue; // Прервано сигналом, повторяем
              return -1; // Реальная ошибка
          }
          if (sent == 0) { errno = EIO; return -1; } // для потокового сокета при len > 0 не ожидается
          total_sent += (size_t)sent;
      }
      return (ssize_t)total_sent; // при успехе равно len
  }
  ```
  Для компиляции нужны `<errno.h>`, `<sys/types.h>` и `<sys/socket.h>`. Флаг `MSG_NOSIGNAL` есть в Linux; в macOS замените его на `0` и используйте `SO_NOSIGPIPE`.
