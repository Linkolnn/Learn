## 💡 Глоссарий ключевых терминов лекции

> 📌 **1. Иерархия файловой системы (FHS — Filesystem Hierarchy Standard)**
> * **Что это:** Стандарт, определяющий назначение каталогов в UNIX-подобных операционных системах (например, `/etc` для конфигураций, `/var` для изменяемых данных, `/proc` для виртуальной информации ядра).

> 📌 **2. SSH (Secure Shell)**
> * **Что это:** Сетевой криптографический протокол прикладного уровня, обеспечивающий безопасное удалённое управление операционной системой и передачу файлов поверх незащищённых сетей (по умолчанию порт 22/TCP).

> 📌 **3. Процесс, PID и PPID**
> * **Что это:** **Процесс** — выполняемый экземпляр программы в изолированном виртуальном адресном пространстве. **PID (Process ID)** — уникальный числовой идентификатор процесса в системе. **PPID (Parent Process ID)** — идентификатор родительского процесса, породившего данный процесс (обычно вызовом `fork()`).

> 📌 **4. Сигналы Linux (Signals)**
> * **Что это:** Асинхронные уведомления, посылаемые ядром ОС или одним процессом другому для оповещения о событии (например, `SIGINT` — прерывание, `SIGTERM` — просьба завершиться, `SIGKILL` — принудительное уничтожение).

> 📌 **5. Процесс-Зомби (Zombie Process / Defunct)**
> * **Что это:** Процесс, который завершил свое выполнение (вызвал `exit()`), но запись о нём остаётся в таблице процессов ядра, пока родительский процесс не вызовет системный вызов `wait()` или `waitpid()` для считывания кода возврата.

> 📌 **6. POSIX DAC (Discretionary Access Control — Дискреционное управление доступом)**
> * **Что это:** Традиционная модель прав доступа в Linux, где права чтения (`r`), записи (`w`) и исполнения (`x`) назначаются отдельно для Владельца (`User`), Группы (`Group`) и Остальных (`Others`).

> 📌 **7. Специальные биты прав (SUID, SGID, Sticky Bit)**
> * **SUID (Set User ID):** позволяет запускать исполняемый файл с правами его владельца.
> * **SGID (Set Group ID):** для файла — запуск с правами группы файла; для каталога — новые файлы наследуют группу каталога.
> * **Sticky Bit:** запрещает пользователям удалять или переименовывать чужие файлы в общем каталоге (например, в `/tmp`).

> 📌 **8. Перенаправление ввода-вывода (I/O Redirection) и Конвейер (Pipe)**
> * **Стандартные потоки:** `stdin` (0), `stdout` (1), `stderr` (2).
> * **Конвейер (`|`):** передаёт стандартный вывод (`stdout`) одной программы на стандартный ввод (`stdin`) другой программы через буфер в памяти ядра, без записи на диск.

> 📌 **9. `grep` (Global Regular Expression Print)**
> * **Что это:** Утилита командной строки для поиска строк, соответствующих заданному регулярному выражению (шаблону поиска), в файлах или входном потоке данных.

> 📌 **10. `awk`**
> * **Что это:** Полноценный язык программирования для обработки текста, предназначенный для анализа логов и табличных данных по колонкам (полям).

> 📌 **11. `sudo`, пакетный менеджер `apt`, служба и `systemd`**
> * **`sudo`** — выполнить одну команду с правами администратора (root). **`apt`** — менеджер пакетов Debian/Ubuntu: устанавливает программы из репозиториев вместе с зависимостями. **Служба (демон)** — программа, работающая в фоне (веб-сервер, SSH-сервер). **`systemd`** — системный менеджер, который запускает службы и управляет ими командой `systemctl`. Подробнее — в Подглаве 30.7.

## Подглава 30.1: Иерархия файловой системы Linux (FHS — Filesystem Hierarchy Standard)

В Linux отсутствует понятие дисков `C:` или `D:`, принятое в Windows. Вся файловая система представляет собой единое древовидное пространство, начинающееся с корневого каталога **`/` (Root)**. Различные физические диски, разделы и виртуальные файловые системы **монтируются** (подключаются) в конкретные точки этого единого дерева.

```text
/ (Корневой каталог)
├── bin -> usr/bin          (Важнейшие бинарные утилиты пользователей)
├── sbin -> usr/sbin        (Системные утилиты администратора)
├── boot                    (Файлы загрузчика GRUB и ядро vmlinuz)
├── dev                     (Файлы устройств: /dev/sda, /dev/null, /dev/urandom)
├── etc                     (Конфигурационные файлы системы и сервисов)
├── home                    (Домашние каталоги обычных пользователей: /home/user)
├── root                    (Домашний каталог суперпользователя root)
├── lib -> usr/lib          (Разделяемые системные библиотеки .so)
├── media / mnt             (Точки монтирования съемных дисков и внешних ФС)
├── opt                     (Дополнительное стороннее ПО: /opt/myapp)
├── proc                    (Виртуальная ФС информации о процессах и ядре)
├── run                     (Данные запущенных служб: PID-файлы, сокеты; очищается при загрузке)
├── sys                     (Виртуальная ФС аппаратных устройств и драйверов)
├── tmp                     (Временные файлы; во многих дистрибутивах очищается при перезагрузке)
├── usr                     (Основная часть установленных программ, библиотек и документации)
│   ├── bin                 (Основные исполняемые файлы)
│   ├── include             (Заголовочные файлы C/C++: /usr/include/stdio.h)
│   └── local               (ПО, установленное администратором вручную)
└── var                     (Изменяемые данные: логи, базы данных, очереди)
    ├── log                 (Системные логи: /var/log/syslog, /var/log/nginx/access.log)
    └── www                 (Файлы веб-сайтов — распространённое соглашение веб-серверов)
```

> ℹ️ **Примечание:** Стрелки `->` означают **символические ссылки**. В современных дистрибутивах (Ubuntu, Debian, Fedora и др.) `/bin`, `/sbin` и `/lib` — это ссылки на каталоги внутри `/usr`. В старых системах это были отдельные каталоги.

### Ключевые каталоги и их системная роль:

1. **`/etc` (конфигурация):**
   Содержит глобальные текстовые конфигурационные файлы. Изменения здесь влияют на работу всей системы (`/etc/passwd` — список учётных записей, `/etc/fstab` — таблица монтирования дисков, `/etc/nginx/nginx.conf`). Название исторически происходит от слова *et cetera* («и прочее»), а расшифровку «Editable Text Configuration» придумали позже как мнемонику.
2. **`/var` (Variable — «изменяемое»):**
   Каталог для данных, объем которых постоянно меняется в процессе работы ОС: лог-файлы (`/var/log`), почтовые очереди, базы данных PostgreSQL/MySQL (например, `/var/lib/postgresql`).
3. **Виртуальные файловые системы ядра (`/proc` и `/sys`):**
   Эти каталоги **не хранятся на диске**. Их содержимое формируется ядром Linux «на лету» в оперативной памяти (RAM) в момент обращения:
   * `/proc/cpuinfo` — характеристики процессора.
   * `/proc/meminfo` — статистика ОЗУ.
   * `/proc/[PID]/` — полная информация о работающем процессе (его память, открытые файловые дескрипторы, переменные окружения). *Файловый дескриптор — это числовой номер, под которым процесс обращается к открытому файлу, сокету или каналу.*
4. **Каталог устройств `/dev` (Devices):**
   Специальные файлы, через которые программы взаимодействуют с аппаратурой и виртуальными устройствами ядра:
   * `/dev/null` — «чёрная дыра». Любые данные, записанные сюда, бесследно уничтожаются.
   * `/dev/zero` — источник бесконечного потока нулевых байтов (байт со значением `0`, в Си — `'\0'`).
   * `/dev/urandom` — генератор криптографически стойких псевдослучайных байтов ядра.

## Подглава 30.2: Удаленное управление и безопасность: Протокол SSH (Secure Shell)

Протокол **SSH (порт 22/TCP по умолчанию)** предоставляет защищённый канал шифрованного взаимодействия между клиентом и сервером. В отличие от устаревшего и небезопасного Telnet, передававшего пароли в открытом виде, SSH шифрует весь трафик сессии.

```text
[ Клиент (Разработчик) ]                               [ SSH-Сервер (VPS) ]
  Приватный ключ id_ed25519                             Публичный ключ authorized_keys
        │                                                         │
        │ ─── 1. TCP-соединение (порт 22) ───────────────────────> │
        │ <── 2. Сервер предъявляет свой ключ хоста; клиент ────── │
        │        сверяет его со списком known_hosts                │
        │ <── 3. Обмен ключами (Diffie-Hellman) → общий ─────────> │
        │        сеансовый ключ; дальше всё шифруется              │
        │ ─── 4. Клиент доказывает владение приватным ключом ────> │
        │        (подписывает данные; сам ключ не передаётся)      │
```

> Для шифрования сессии современные версии OpenSSH используют, например, ChaCha20-Poly1305 или AES-GCM.

### 1. Генерация и настройка ключей авторизации (Public Key Authentication)

Аутентификация по ключам безопаснее паролей, так как устойчива к **брутфорсу** (перебору паролей):
* **Публичный ключ (`id_ed25519.pub`):** копируется на удалённый сервер и размещается в файле `~/.ssh/authorized_keys`. Его можно безопасно показывать кому угодно.
* **Приватный ключ (`id_ed25519`):** хранится строго на компьютере разработчика в секрете и никогда не передаётся по сети! При создании ключа рекомендуется задать **парольную фразу (passphrase)** — она защитит ключ, если файл попадёт в чужие руки.

#### Команды создания и передачи ключа:
```bash
# 1. Генерация современной пары ключей Ed25519
ssh-keygen -t ed25519 -C "developer@company.com"

# 2. Автоматическая передача публичного ключа на сервер
#    (команда сама создаёт ~/.ssh и authorized_keys с правильными правами)
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@192.168.1.100

# 3. Если ключ добавляете вручную — выставите права на СЕРВЕРЕ:
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

> ⚠️ **Правило прав доступа SSH:**
> * **На сервере** при стандартной настройке (`StrictModes yes`) OpenSSH отказывает в авторизации по ключу, если домашний каталог, `~/.ssh` или `authorized_keys` **доступны на запись группе или остальным пользователям**. Рекомендуемые безопасные значения: `700` для `~/.ssh` и `600` для `authorized_keys`.
> * **На клиенте** `ssh` отказывается использовать приватный ключ, если он доступен для чтения другим пользователям (нужно `600`).

### 2. Конфигурация клиента (`~/.ssh/config`)

Для удобства подключения создаётся клиентский файл конфигурации:
```text
Host prod-server
    HostName 203.0.113.10
    User admin
    Port 2222
    IdentityFile ~/.ssh/id_ed25519
```
После этого подключение выполняется простой командой: `ssh prod-server`.
(Значение `Port` должно совпадать с портом, на котором слушает SSH-сервер. Если сервер работает на стандартном порту 22, строку `Port` можно убрать.)

### 3. Усиление безопасности сервера (`/etc/ssh/sshd_config`)

На продакшен-серверах рекомендуются следующие настройки безопасности:
```text
# Запрет входа суперпользователю root напрямую
PermitRootLogin no

# Отключение авторизации по паролям (только по SSH-ключам!)
PasswordAuthentication no

# Включение авторизации по публичным ключам
PubkeyAuthentication yes

# Смена стандартного порта (снижает шум от автоматических сканеров,
# но НЕ является настоящей защитой — это лишь «безопасность через неясность»)
Port 2222
```

> ⚠️ **Как не заблокировать себя на сервере:**
> 1. Прежде чем отключать пароли, убедитесь, что вход по ключу **уже работает** (проверьте во втором окне терминала).
> 2. Проверьте конфигурацию на ошибки: `sudo sshd -t`.
> 3. Если меняете порт, откройте новый порт в файрволе **до** перезапуска службы.
> 4. Не закрывайте текущую сессию, пока не убедитесь, что новая сессия подключается успешно.

Применение изменений: `sudo systemctl restart sshd`.
На Debian/Ubuntu служба обычно называется **`ssh`** (`sudo systemctl restart ssh`); на RHEL/Fedora/CentOS — `sshd`.

> ⚠️ **Ловушка новых Ubuntu (22.10+, включая 24.04).** SSH там запускается через *socket activation*: порт слушает не `sshd`, а systemd-юнит `ssh.socket`, поэтому после смены `Port` в `sshd_config` простого `restart ssh` может быть недостаточно. Выполните `sudo systemctl daemon-reload && sudo systemctl restart ssh.socket`, а затем **проверьте**, на каком порту SSH действительно слушает: `ss -tlnp | grep ssh` (команда описана в Подглаве 30.7). Только после этого закрывайте старую сессию.

## Подглава 30.3: Модель процессов Linux и сигналы (Process Management)

Каждая выполняемая программа в Linux является **процессом**. Все процессы образуют иерархическое дерево, где корнем выступает процесс инициализации **`init` / `systemd` (PID = 1)**.

### 1. Жизненный цикл процесса и состояния (Process States)

```text
[ Parent ] ── fork() ──> [ Child ]   (дочерний процесс — копия родителя)
                            │
                            │ exec()  (необязательно: загружает в процесс другую программу)
                            ▼
                      [ Running (R) ] <───────> [ Sleeping (S/D) ]
                            │                    (ждёт события или ввода-вывода,
                            │ exit()              затем снова готов к работе)
                            ▼
                      [ Zombie (Z) ]  — процесс завершён, но запись о нём ещё в таблице
                            │
                            │ родитель вызывает wait()/waitpid()
                            ▼
                  [ Запись удалена из таблицы процессов ]
```

> `wait()` вызывает **родитель**, а не дочерний процесс: так родитель узнаёт код возврата потомка и позволяет ядру убрать запись о нём.

#### Основные состояния процессов в `ps` / `top`:
* **`R` (Running / Runnable):** процесс выполняется на CPU или находится в очереди готовности к выполнению.
* **`S` (Interruptible Sleep):** процесс заблокирован в ожидании события или ввода-вывода (I/O, сетевой сокет, таймер). Может прерываться сигналами.
* **`D` (Uninterruptible Sleep):** процесс заблокирован в ожидании дискового I/O или операции ядра. **Сигналы (в том числе `kill -9`) не могут его прервать** — они подействуют только после выхода из этого состояния. Если процесс «завис» в `D` надолго, это обычно признак проблем с диском, сетевой ФС или драйвером.
* **`Z` (Zombie):** процесс завершился (вызвал `exit()`), освободил память и другие ресурсы, но его запись (PID и код возврата) остаётся в таблице процессов ядра, пока родитель не вызовет `wait()`.
* **`T` (Stopped):** процесс остановлен сигналом (например, `Ctrl+Z` → `SIGTSTP` или `SIGSTOP`).

---

### 2. Команды инспекции и управления процессами

* **`ps aux`:** вывод списка всех процессов системы.
  * `a` — процессы всех пользователей.
  * `u` — отображение владельца, использования CPU и RAM.
  * `x` — включая процессы без управляющего терминала (**демоны** — фоновые службы).
* **`ps -ef --forest`:** отображение иерархического дерева процессов (родитель-потомок).
* **`top` / `htop`:** интерактивный мониторинг ресурсов системы в реальном времени (нагрузка CPU, Load Average, использование RAM, Swap).
  * **Load Average** — среднее число процессов, которые выполняются или ждут своей очереди (на CPU, а в Linux ещё и на диск), за последние 1, 5 и 15 минут. Если значение устойчиво выше числа ядер процессора, система перегружена.

### 3. Сигналы Linux и утилита `kill`

Сигналы — это асинхронные уведомления процесса о событиях. Процесс может **перехватить** сигнал (назначить свой обработчик через `sigaction`), проигнорировать его или оставить поведение по умолчанию.

| Сигнал | Номер* | Поведение по умолчанию | Возможность перехвата (`sigaction`) | Назначение |
| :--- | :---: | :--- | :--- | :--- |
| **`SIGHUP`** | 1 | Завершение процесса | **Перехватывается** | Обрыв терминала / Перезагрузка конфигов демонов |
| **`SIGINT`** | 2 | Завершение процесса | **Перехватывается** | Прерывание с клавиатуры (`Ctrl+C`) |
| **`SIGQUIT`** | 3 | Завершение + дамп памяти | **Перехватывается** | Выход с дампом памяти (`Ctrl+\`) |
| **`SIGKILL`** | 9 | Немедленное уничтожение | **НЕ ПЕРЕХВАТЫВАЕТСЯ!** | Процесс уничтожается ядром, не успев выполнить собственную очистку (закрыть файлы, сохранить данные) |
| **`SIGUSR1` / `SIGUSR2`** | 10 / 12 | Завершение процесса | **Перехватываются** | Пользовательские сигналы приложения |
| **`SIGTERM`** | 15 | Завершение процесса | **Перехватывается** | Стандартный запрос на корректную остановку (программа может сохранить данные и выйти) |
| **`SIGCHLD`** | 17 | Игнорируется | **Перехватывается** | Уведомление родителю о завершении дочернего процесса |
| **`SIGSTOP`** | 19 | Остановка процесса | **НЕ ПЕРЕХВАТЫВАЕТСЯ!** | Принудительная приостановка (возобновляется сигналом `SIGCONT`) |
| **`SIGTSTP`** | 20 | Остановка процесса | **Перехватывается** | Остановка с клавиатуры (`Ctrl+Z`) |

\* Номера указаны для архитектуры x86-64. На других архитектурах (например, ARM, MIPS) некоторые номера отличаются, поэтому в командах и коде лучше использовать имена сигналов.

#### Примеры использования `kill`, `pkill` и `killall`:
```bash
# Отправка сигнала SIGTERM (15) по PID — просьба завершиться корректно
kill 1234

# Принудительное уничтожение процесса сигналом SIGKILL (9)
# Применяйте, только если SIGTERM не помог: процесс не успеет сохранить данные
kill -9 1234

# Перезагрузка конфигурации Nginx без остановки сервера (SIGHUP)
# (проще и надёжнее: sudo nginx -s reload; Nginx — веб-сервер, его разберём в Лекции 33)
sudo kill -HUP $(cat /run/nginx.pid)

# Завершение процессов, у которых в ПОЛНОЙ командной строке есть "node server.js"
pkill -f "node server.js"

# Завершение всех процессов с точным именем программы
killall nginx
```

## Подглава 30.4: Права доступа Linux (POSIX DAC) и Спец-биты

Каждый файл и каталог в Linux принадлежит конкретному **Пользователю (User/Owner)** и **Группе (Group)**.

### 1. Классическая матрица прав доступа

Права делятся на три категории субъектов: **`u` (User)**, **`g` (Group)**, **`o` (Others)**.

```text
 Тип файла      User (u)       Group (g)     Others (o)
     -          r   w   x      r   -   x     r   -   -
     │          │   │   │      │   │   │     │   │   │
     │          4 + 2 + 1      4 + 0 + 1     4 + 0 + 0
     │            = 7            = 5           = 4
     ▼
 обычный файл            Режим прав: 754  (rwxr-xr--)
```

* **`r` (Read = 4):** чтение содержимого файла / просмотр списка файлов в каталоге.
* **`w` (Write = 2):** изменение файла / создание, удаление и переименование файлов внутри каталога (для этого у каталога также нужно право `x`).
* **`x` (Execute = 1):** запуск файла как программы / возможность зайти в каталог (`cd`) и обращаться к файлам внутри него.

#### Команды смены прав и владельцев:
```bash
# Восьмеричная установка прав (rwxr-xr-x)
chmod 755 script.sh

# Символьная установка прав: добавить исполнение для владельца, убрать запись у группы
chmod u+x,g-w script.sh

# Смена владельца и группы файла
sudo chown admin:www-data /var/www/html/index.html

# Рекурсивная смена владельца всей директории
sudo chown -R admin:admin /opt/myapp
```

---

### 2. Маска прав по умолчанию (`umask`)

Когда процесс создаёт новый файл или каталог, ядро берёт базовые права и **убирает из них те биты, которые включены в маске `umask`**:
* Базовые права для **файлов:** `666` (`rw-rw-rw-`) — исполнение по умолчанию не даётся.
* Базовые права для **каталогов:** `777` (`rwxrwxrwx`).

Формально это операция `базовые_права AND (NOT umask)`. В большинстве типичных случаев (когда в маске нет бит, которых нет в базовых правах) результат совпадает с обычным вычитанием, поэтому для простых расчётов можно пользоваться вычитанием, но помните, что это упрощение.

При стандартном `umask 022`:
* Права нового файла: `666 - 022 = 644` (`rw-r--r--`).
* Права нового каталога: `777 - 022 = 755` (`rwxr-xr-x`).

> ⚠️ **Где вычитание даёт неверный ответ:** для файла при `umask 033` вычитание даёт `666 - 033 = 633`, но по-настоящему получится `644`, потому что бит `x` в базовых правах файла отсутствует и «вычитать» его нечего. Поэтому надёжнее считать побитово: убрать из базовых прав те биты, которые стоят в маске.

---

### 3. Специальные биты прав (SUID, SGID, Sticky Bit)

| Бит | Восьмеричный код | Символьная запись | Действие на файл | Действие на каталог |
| :--- | :---: | :---: | :--- | :--- |
| **SUID** | `4000` | `u+s` (например, `rwsr-xr-x`) | Исполнение от имени **владельца файла** | Нет эффекта |
| **SGID** | `2000` | `g+s` (например, `rwxr-sr-x`) | Исполнение от имени **группы файла** | Новые файлы наследуют группу каталога |
| **Sticky Bit** | `1000` | `+t` (например, `rwxrwxrwt`) | Нет эффекта | Удалять и переименовывать файлы в каталоге может только **владелец файла, владелец каталога или root** |

> Если у файла нет бита `x`, специальный бит отображается заглавной буквой (`S` или `T`) — это обычно признак ошибки в настройке.

#### Примеры использования:
* Утилита `/usr/bin/passwd` имеет бит **SUID** (`chmod 4755`), что позволяет обычному пользователю менять свой пароль: программа выполняется с правами root и может записать изменения в `/etc/shadow`, куда обычному пользователю писать нельзя.
* Каталог `/tmp` имеет **Sticky Bit** (`chmod 1777` / `drwxrwxrwt`), что позволяет всем пользователям создавать файлы в `/tmp`, но запрещает удалять и переименовывать чужие файлы.

## Подглава 30.5: Конвейеры (Pipes) и текстовые консольные утилиты (`grep`, `awk`, `sed`)

### 1. Перенаправление ввода-вывода (I/O Redirection)

Каждый процесс Linux запускается с тремя открытыми стандартными файловыми дескрипторами (он наследует их от родителя):
* **`0` — Standard Input (`stdin`):** стандартный ввод (по умолчанию — клавиатура).
* **`1` — Standard Output (`stdout`):** стандартный вывод (по умолчанию — терминал).
* **`2` — Standard Error (`stderr`):** вывод ошибок (по умолчанию — терминал).

```bash
# 1. Перенаправление stdout в файл (перезапись)
ls -la > files.txt

# 2. Перенаправление stdout в файл (дозапись в конец)
echo "new log entry" >> app.log

# 3. Перенаправление stderr в отдельный файл
gcc main.c 2> build_errors.log

# 4. Перенаправление stderr и stdout в один файл
#    (порядок важен: сначала > output.log, затем 2>&1)
./server_app > output.log 2>&1

# 5. Подавление вывода ошибок (отправка в /dev/null)
find / -name "*.conf" 2>/dev/null
```

---

### 2. Поисковая утилита `grep` (с регулярными выражениями)

`grep` фильтрует входной поток или файлы по текстовому шаблону.

```bash
# Поиск строки "ERROR" в файле app.log
grep "ERROR" app.log

# Рекурсивный поиск с номерами строк, без бинарных файлов
# (-r — рекурсивно, -n — номера строк, -I — пропускать бинарные файлы)
grep -rnI "MAX_CONNECTIONS" src/

# То же, но без учёта регистра (добавляем -i, строчная буква!)
grep -rniI "max_connections" src/

# Инвертированная фильтрация (вывести все строки, НЕ содержащие "DEBUG")
grep -v "DEBUG" app.log

# Расширенные регулярные выражения (Extended Regex, флаг -E): поиск строк, похожих на IP-адрес
# (шаблон проверяет только форму «число.число.число.число», значения вроде 999.1.1.1 тоже подойдут)
grep -E "([0-9]{1,3}\.){3}[0-9]{1,3}" /var/log/nginx/access.log
```

---

### 3. Потоковый процессор `awk`

`awk` разбивает каждую строку текстового потока на колонки (по умолчанию по пробелам и символам табуляции):
* **`$0`** — вся строка целиком.
* **`$1, $2, $3...`** — первая, вторая, третья колонки.
* **`NF`** — количество колонок в текущей строке.
* **`NR`** — номер текущей строки.

В стандартном (combined) формате лога Nginx строка выглядит так:
`203.0.113.5 - - [10/Oct/2026:13:55:36 +0000] "GET /index.html HTTP/1.1" 200 612 "-" "Mozilla/5.0"`
Здесь `$1` — IP-адрес клиента, `$9` — HTTP-код ответа, `$10` — размер ответа в байтах. (Nginx — веб-сервер, о нём Лекция 33; HTTP-код `200` означает «запрос выполнен успешно», остальные коды мы разберём в Лекциях 33 и 117.)

```bash
# 1. Вывести только IP-адрес ($1) и HTTP-код ответа ($9) из лога Nginx
awk '{print $1, $9}' /var/log/nginx/access.log

# 2. Обычные (не системные) пользователи из /etc/passwd:
#    разделитель — двоеточие (-F':'), UID (поле $3) от 1000;
#    верхняя граница 65534 отсекает служебного пользователя nobody
awk -F':' '$3 >= 1000 && $3 < 65534 {print $1, $3}' /etc/passwd

# 3. Суммарный объём переданных данных ($10) по всем запросам, в мебибайтах (МиБ)
awk '{sum += $10} END {print "Total MiB:", sum/(1024*1024)}' /var/log/nginx/access.log
```

### 4. Потоковый редактор `sed`

`sed` выполняет автоматическое редактирование и замену текста в потоке.

```bash
# Замена первого вхождения "http://" на "https://" в каждой строке
# (результат выводится на экран, файл не меняется)
sed 's/http:\/\//https:\/\//' config.txt

# Глобальная замена всех вхождений (флаг g) непосредственно внутри файла (-i)
# Совет: -i.bak перед изменением сохранит копию исходного файла как .env.bak
sed -i 's/PORT=8080/PORT=9090/g' .env
```

## Подглава 30.6: Практический C11-код: обработка сигналов и защита от зомби-процессов

Ниже представлен пример на C, демонстрирующий безопасную обработку сигналов `SIGINT` и `SIGTERM` через вызов `sigaction()`, а также предотвращение образования процессов-зомби через сигнал `SIGCHLD` и вызов `waitpid()`.

> ℹ️ Функции `sigaction`, `fork`, `waitpid` и др. относятся к стандарту POSIX, а не к «чистому» языку Си. При компиляции с флагом `-std=c11` компилятор по умолчанию их «не видит», поэтому первой строкой кода объявлен макрос `_POSIX_C_SOURCE`. Без него программа не соберётся.

```c
#define _POSIX_C_SOURCE 200809L  // открывает POSIX-функции при компиляции с -std=c11

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <signal.h>
#include <sys/types.h>
#include <sys/wait.h>

// Глобальный флаг работы приложения.
// volatile — компилятор не кэширует значение; sig_atomic_t — чтение/запись атомарны
static volatile sig_atomic_t g_running = 1;

// Обработчик сигналов SIGINT и SIGTERM (мягкая остановка)
static void handle_shutdown_signal(int sig) {
    (void)sig; // Подавление предупреждения о неиспользуемом параметре
    g_running = 0;
}

// Обработчик сигнала SIGCHLD (автоматическое удаление процессов-зомби)
static void handle_sigchld(int sig) {
    (void)sig;
    int saved_errno = errno; // waitpid может изменить errno — сохраняем, чтобы не сломать основной код
    // Подбираем все уже завершившиеся дочерние процессы в неблокирующем режиме
    while (waitpid(-1, NULL, WNOHANG) > 0) {
        // Зомби удалены из таблицы процессов ядра
    }
    errno = saved_errno;
}

int main(void) {
    printf("=== Демонстрация обработки сигналов (PID: %d) ===\n", getpid());
    printf("Для завершения нажмите Ctrl+C (SIGINT) или отправьте 'kill %d'\n\n", getpid());

    // 1. Настройка обработчика завершения (SIGINT и SIGTERM)
    struct sigaction sa_shutdown;
    memset(&sa_shutdown, 0, sizeof(sa_shutdown));
    sa_shutdown.sa_handler = handle_shutdown_signal;
    sigemptyset(&sa_shutdown.sa_mask);

    if (sigaction(SIGINT, &sa_shutdown, NULL) < 0) {
        perror("Ошибка установки sigaction(SIGINT)");
        return 1;
    }
    if (sigaction(SIGTERM, &sa_shutdown, NULL) < 0) {
        perror("Ошибка установки sigaction(SIGTERM)");
        return 1;
    }

    // 2. Настройка обработчика SIGCHLD для автоматической очистки зомби
    struct sigaction sa_chld;
    memset(&sa_chld, 0, sizeof(sa_chld));
    sa_chld.sa_handler = handle_sigchld;
    sa_chld.sa_flags = SA_RESTART | SA_NOCLDSTOP;
    sigemptyset(&sa_chld.sa_mask);

    if (sigaction(SIGCHLD, &sa_chld, NULL) < 0) {
        perror("Ошибка установки sigaction(SIGCHLD)");
        return 1;
    }

    // 3. Порождаем дочерний процесс для демонстрации
    fflush(stdout); // сбрасываем буфер вывода, чтобы потомок не продублировал уже напечатанный текст
    pid_t child_pid = fork();
    if (child_pid < 0) {
        perror("Ошибка fork()");
        return 1;
    }

    if (child_pid == 0) {
        // === Код дочернего процесса ===
        printf("  [Child Process] Запущен дочерний процесс (PID: %d, PPID: %d)\n", getpid(), getppid());
        sleep(2);
        printf("  [Child Process] Завершение работы дочернего процесса.\n");
        exit(42); // Завершаемся с кодом 42
    }

    // === Код родительского процесса ===
    printf("  [Parent Process] Создан дочерний процесс PID: %d\n", child_pid);

    int seconds = 0;
    while (g_running && seconds < 5) {
        // sleep() прерывается любым сигналом (в т.ч. SIGCHLD) и возвращает
        // число недоспанных секунд — досыпаем, чтобы счётчик шёл точно
        unsigned int left = 1;
        while (left > 0 && g_running) {
            left = sleep(left);
        }
        if (!g_running) {
            break;
        }
        seconds++;
        printf("Программа работает... (%d сек)\n", seconds);
    }

    if (!g_running) {
        printf("\n[Parent Process] Получен сигнал завершения. Остановка...\n");
    } else {
        printf("Достигнут лимит времени демонстрации.\n");
    }
    return 0;
}
```

### Команда компиляции и сборки:
```bash
gcc -Wall -Wextra -std=c11 signal_demo.c -o signal_demo && ./signal_demo
```

## Подглава 30.7: Минимум администрирования сервера: `sudo`, `apt`, `systemctl`, `ufw` и диагностика

```bash
# sudo выполняет ОДНУ команду от имени root; пользователь должен входить в группу sudo.
```

```bash
sudo systemctl restart nginx        # остановить и запустить заново (соединения рвутся)
```

```bash
sudo ufw status verbose       # посмотреть правила
```

> ⚠️ Если включить `ufw` без разрешающего правила для SSH-порта, вы потеряете доступ к серверу. Также учтите: порты, опубликованные Docker через `ports:`, обходят правила `ufw` (подробнее — в Лекциях 32–33).

## Подглава 30.8: Чек-лист системного программиста & Практические задачи

1. **Защищайте приватные ключи SSH:** Файл `~/.ssh/id_ed25519` должен иметь права `600`, а каталог `~/.ssh` — права `700`.
2. **Не оставляйте зомби в сетевых серверах:** Если ваш сервер порождает процессы через `fork()`, нужно вызывать `wait()` / `waitpid()` (например, в обработчике `SIGCHLD`, как в примере выше). Иначе завершённые потомки останутся зомби-записями, а при их большом количестве таблица процессов переполнится и система не сможет создавать новые процессы.
3. **Используйте `sigaction()` вместо `signal()`:** Поведение `signal()` отличается в разных системах (например, сбрасывается ли обработчик после первого сигнала), а `sigaction()` даёт предсказуемое, переносимое поведение и контроль над масками сигналов.
4. **Учитывайте права на каталоги:** Чтобы пользователь мог добраться до файла, у него должно быть право на исполнение (`x`) для всех каталогов на пути к этому файлу!

### Практические задачи к Лекции 30

#### Задача 1: Расчёт прав доступа по `umask`
В операционной системе установлен параметр `umask 027`.
Рассчитайте результирующие символьные права доступа (например, `rwxr-xr-x`) для:

#### Задача 2: Однострочник на Bash (`grep` + `awk` + `sort`)

## Подсказки к практическим задачам

* **Подсказка к Задаче 1:**
  Из базовых прав убираем биты, включённые в маске (`027` = `---` для владельца, `-w-` для группы, `rwx` для остальных).
  * Файл: базовые права `666` (`rw-rw-rw-`). У группы убираем запись (`2`), у остальных — всё (`7`): получается `640` (`rw-r-----`).
  * Каталог: базовые права `777` (`rwxrwxrwx`). Аналогично: `750` (`rwxr-x---`).
  * Проверка вычитанием: для каталога `777 - 027 = 750` совпадает с ответом, а для файла **не совпадает**: в последней цифре пришлось бы вычитать `7` из `6`, и формальное вычитание даст неверное `637`. Правильный ответ `640` получается только побитово (см. Подглаву 30.4).

* **Подсказка к Задаче 2:**
  Используйте комбинацию `grep`, `awk`, `sort` и `uniq -c`. В логе Nginx код ответа идёт сразу после закрывающей кавычки запроса: `"GET / HTTP/1.1" 200 612`, поэтому шаблон для `grep` — `'" 200 '`:
  ```bash
  grep '" 200 ' /var/log/nginx/access.log | awk '{print $1}' | sort | uniq -c | sort -nr | head -n 3
  ```
  Разбор: `grep` оставляет строки с кодом 200 → `awk` берёт IP → `sort` группирует одинаковые IP рядом (это нужно для `uniq`) → `uniq -c` считает повторы → `sort -nr` сортирует по убыванию числа → `head -n 3` берёт первые три.

  Более точный вариант (проверяет именно 9-ю колонку, а не любое совпадение в строке), `grep` в нём не нужен:
  ```bash
  awk '$9 == 200 {print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -nr | head -n 3
  ```

* **Подсказка к Задаче 3:**
  ```c
  #include <stdio.h>
  #include <unistd.h>
  #include <string.h>
  #include <sys/types.h>
  #include <sys/wait.h>

  int main(void) {
      int pipefd[2];
      if (pipe(pipefd) < 0) {
          perror("pipe");
          return 1;
      }

      pid_t pid = fork();
      if (pid < 0) {
          perror("fork");
          return 1;
      }

      if (pid == 0) {
          // Дочерний процесс: только пишет
          close(pipefd[0]); // Закрываем неиспользуемый конец чтения
          const char *msg = "Hello from Child!";
          write(pipefd[1], msg, strlen(msg) + 1); // +1 — чтобы передать и завершающий '\0'
          close(pipefd[1]);
          return 0;
      } else {
          // Родительский процесс: только читает
          close(pipefd[1]); // Закрываем неиспользуемый конец записи
          char buf[100];
          ssize_t n = read(pipefd[0], buf, sizeof(buf) - 1);
          if (n > 0) {
              buf[n] = '\0'; // гарантируем завершение строки
              printf("Parent received: %s\n", buf);
          }
          close(pipefd[0]);
          wait(NULL); // дожидаемся потомка, чтобы он не остался зомби
      }
      return 0;
  }
  ```
