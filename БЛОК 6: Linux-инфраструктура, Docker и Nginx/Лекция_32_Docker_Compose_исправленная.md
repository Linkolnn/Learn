# Лекция 32: Docker Compose. Оркестрация мультиконтейнерных приложений, монтирование томов (volumes), локальные сети (networks) и переменные окружения (.env)

В предыдущей лекции мы разобрали фундаментальные механизмы контейнеризации в ядре Linux (`namespaces` и `cgroups`), научились собирать минималистичные многоэтапные образы с помощью `Dockerfile` и управлять отдельными контейнерами через Docker CLI. Однако в реальной коммерческой разработке приложения редко существуют в виде одиночного контейнера. Современный веб-сервис — это экосистема, состоящая из веб-сервера (Nginx), приложения (бэкенд на Си/Go/Node.js), базы данных (PostgreSQL), оперативного кэша (Redis) и фоновых обработчиков задач (Workers).

Управлять такой системой вручную через отдельные команды `docker run` с десятками аргументов (порты, тома, переменные окружения) становится невозможным. В этой лекции мы изучим инструмент **Docker Compose**, разберём спецификацию файла `docker-compose.yml`, научимся настраивать изолированные сети (`networks`), постоянные хранилища данных (`volumes`), управлять конфигурацией через `.env`-файлы, настроим проверки состояния (`healthcheck`) и соберём готовый многоконтейнерный стек.

> ℹ️ **Важно понимать границы инструмента:** Docker Compose управляет контейнерами на **одном хосте** (одной машине). Для управления кластером из многих серверов (автоматическое масштабирование, перенос нагрузки между узлами) используются другие оркестраторы — Kubernetes и Docker Swarm. Поэтому в этой лекции под «оркестрацией» мы понимаем описание и запуск связанной группы контейнеров на одной машине.

> 🗺️ **Место лекции в курсе.** Стек из этой лекции в Лекции 33 пополнится подробной настройкой Nginx (балансировка, Rate Limiting, TLS), а в Этапе 7 сквозного проекта тот же подход используется для деплоя на VPS. PostgreSQL и Redis здесь пока «чёрные ящики» (готовые образы из Docker Hub): сами СУБД изучаются в Лекциях 202–205 и 231.

## 💡 Глоссарий ключевых терминов лекции

> 📌 **1. Оркестрация контейнеров (Container Orchestration)**
> * **Что это:** Автоматизированное управление жизненным циклом, сетевым взаимодействием и конфигурацией множества связанных контейнеров. Полноценные оркестраторы (Kubernetes) дополнительно умеют распределять контейнеры по кластеру серверов; Docker Compose работает в пределах одной машины.

> 📌 **2. Docker Compose**
> * **Что это:** Инструмент для определения и запуска многоконтейнерных приложений Docker с помощью единого декларативного файла конфигурации `docker-compose.yml`.

> 📌 **3. Декларативный подход (Declarative Approach)**
> * **Что это:** Подход к конфигурации инфраструктуры, при котором инженер описывает **желаемое конечное состояние системы** (какие сервисы, сети и тома должны существовать), а инструмент сам определяет последовательность действий для достижения этого состояния. (Противоположность — императивный подход: пошаговый список команд, как в `docker run`.)

> 📌 **4. Сервис Docker Compose (Service)**
> * **Что это:** Описание единицы приложения в `docker-compose.yml`, определяющее образ, параметры запуска, порты и переменные окружения. Один сервис может запускаться в виде одного или нескольких контейнеров (реплик).

> 📌 **5. Встроенный DNS Docker (Embedded Docker DNS)**
> * **Что это:** Внутренняя служба доменных имён Docker (DNS — система, превращающая имя в IP-адрес), позволяющая контейнерам в одной пользовательской сети находить друг друга по **имени сервиса** (например, `ping db` или `connect("cache", 6379)`), а не по динамическим IP-адресам, которые меняются при каждом пересоздании контейнера.

> 📌 **6. Именованные тома (Named Volumes)**
> * **Что это:** Постоянные хранилища данных, управляемые Docker, жизненный цикл которых не завязан на конкретный контейнер. Данные сохраняются при перезапуске, пересборке или удалении контейнеров (они удаляются только явно: `docker volume rm` или `docker compose down -v`).

> 📌 **7. Монтирование директорий хоста (Bind Mounts)**
> * **Что это:** Прямое монтирование конкретного файла или папки с файловой системы хоста внутрь контейнера. Используется для разработки (Hot Reload — применение изменений кода без пересборки образа) и передачи конфигурационных файлов.

> 📌 **8. Проверка состояния (Healthcheck)**
> * **Что это:** Настраиваемая команда внутри контейнера, с помощью которой Docker регулярно проверяет работоспособность приложения (например, `pg_isready` для PostgreSQL или `curl` для HTTP-сервера; утилита должна присутствовать внутри образа). Результат: статус `starting`, `healthy` или `unhealthy`.

> 📌 **9. Reverse Proxy (обратный прокси)**
> * **Что это:** Сервер (например, Nginx), который принимает запросы от внешних клиентов и пересылает их приложению внутри закрытой сети. Приложение при этом не открывается наружу напрямую.

## Подглава 32.1: Зачем нужен Docker Compose? Проблема ручного управления контейнерами

Представим типичное бэкенд-приложение, состоящее из трёх компонентов: C-сервера приложения, базы данных PostgreSQL и кэша Redis.

### Запуск мультиконтейнерного стека вручную (без Compose):
Чтобы запустить такую систему вручную через Docker CLI, инженеру придётся выполнить цепочку длинных команд:

```bash
# 1. Создать пользовательскую виртуальную сеть
docker network create my_app_net

# 2. Создать именованный том для базы данных
docker volume create pg_data

# 3. Запустить контейнер базы данных PostgreSQL
docker run -d \
  --name db_postgres \
  --network my_app_net \
  -v pg_data:/var/lib/postgresql/data \
  -e POSTGRES_DB=app_db \
  -e POSTGRES_USER=db_user \
  -e POSTGRES_PASSWORD=secret_pass \
  postgres:16-alpine

# 4. Запустить контейнер кэша Redis
docker run -d \
  --name cache_redis \
  --network my_app_net \
  redis:alpine

# 5. Собрать и запустить контейнер нашего C-сервера
docker build -t my_c_app:latest .
docker run -d \
  --name c_server \
  --network my_app_net \
  -p 8080:8080 \
  -e DB_HOST=db_postgres \
  -e REDIS_HOST=cache_redis \
  my_c_app:latest
```

### Недостатки ручного запуска:
1. **Высокий риск человеческого фактора:** Ошибка в одном имени сети, переменной окружения или пути монтирования ломает всю связку.
2. **Отсутствие документированности:** Архитектура приложения «растворяется» в истории терминала или разрозненных Shell-скриптах.
3. **Сложность остановки и очистки:** Чтобы остановить проект, нужно вручную останавливать и удалять каждый контейнер, сеть и том.
4. **Проблема порядка запуска:** Если приложение стартует раньше, чем PostgreSQL успеет запуститься и начать принимать соединения, сервер не сможет подключиться к БД и аварийно завершится.

**Docker Compose** решает эти проблемы, объединяя описание всей инфраструктуры в едином декларативном файле `docker-compose.yml` и позволяя управлять ею одной командой: `docker compose up -d`. Проблема порядка запуска решается связкой `depends_on` + `healthcheck` (см. подглаву 32.6).

## Подглава 32.2: Структура файла `docker-compose.yml` (Спецификация Compose)

Файл `docker-compose.yml` пишется на языке **YAML**. Главное правило YAML: структура задаётся **отступами из пробелов** (табуляция не допускается), вложенность — это сдвиг вправо на 2 пробела.

В современных версиях Docker используется единая спецификация **Compose Specification**: поле `version` в начале файла больше не нужно (оно считается устаревшим, Docker игнорирует его и выводит предупреждение). Помимо имени `docker-compose.yml`, Compose также распознаёт имя `compose.yaml` — оно является рекомендуемым в новых проектах.

### Основные верхнеуровневые блоки `docker-compose.yml`:

```yaml
services:
  # Блок описания контейнеров (сервисов) приложения

networks:
  # Блок объявления пользовательских сетевых изолированных сред

volumes:
  # Блок объявления именованных томов для постоянного хранения данных
```

### Анатомия описания сервиса (блок `services`):

| Директива | Назначение и пример использования |
| :--- | :--- |
| **`build`** | Указывает путь к контексту сборки `Dockerfile` (`build: .` или `build: { context: ., dockerfile: Dockerfile }`). |
| **`image`** | Указывает готовый образ из Docker Hub / Registry (например, `image: postgres:16-alpine`). |
| **`container_name`** | Задаёт явное имя контейнера в ОС. Если не указано, Compose генерирует имя вида `проект-сервис-1` (например, `myapp-db-1`). |
| **`ports`** | Проброс портов «Хост:Контейнер» (`ports: ["8080:8080"]`). Значения рекомендуется писать в кавычках. |
| **`environment`** | Список переменных окружения внутри контейнера. |
| **`env_file`** | Передача в контейнер переменных из указанного файла (например, `env_file: .env.app`). |
| **`volumes`** | Монтирование томов или директорий хоста (`volumes: ["pg_data:/var/lib/postgresql/data"]`). |
| **`networks`** | Подключение сервиса к виртуальным сетям. |
| **`depends_on`** | Порядок запуска: от каких сервисов зависит данный (подробнее в 32.6). |
| **`healthcheck`** | Команда проверки работоспособности сервиса (подробнее в 32.6). |
| **`restart`** | Политика перезапуска контейнера: `no` (по умолчанию), `always`, `unless-stopped`, `on-failure`. |

## Подглава 32.3: Сетевое взаимодействие между контейнерами (Networks & Docker DNS)

Когда вы запускаете стек через Docker Compose, инструмент **автоматически создаёт отдельную изолированную bridge-сеть** для вашего проекта (по умолчанию с именем `названиепапки_default`).

```text
  [ Хост-система / Внешний мир ]
                │
                │ (ports: "8080:8080" — проброс порта хоста в контейнер)
                ▼
┌──────────────────────────────────────────────────────────────────────┐
│ Виртуальная bridge-сеть Docker Compose (например, 172.28.0.0/16)     │
│                                                                      │
│   ┌──────────────────┐   Имя DNS: "db"   ┌───────────────────────┐   │
│   │   Сервис "web"   │──────────────────>│   Сервис "db"         │   │
│   │  (C-приложение)  │                   │   (PostgreSQL:5432)   │   │
│   └──────────────────┘                   └───────────────────────┘   │
│            │                                                         │
│            │ Имя DNS: "cache"                                        │
│            ▼                                                         │
│   ┌──────────────────┐                                               │
│   │  Сервис "cache"  │                                               │
│   │  (Redis:6379)    │                                               │
│   └──────────────────┘                                               │
└──────────────────────────────────────────────────────────────────────┘
```

### Ключевые правила сетевого взаимодействия Compose:

1. **Встроенный DNS и Service Discovery:**
   Контейнеры внутри одной сети Compose обращаются друг к другу по **имени сервиса** из `docker-compose.yml`.
   * *Пример:* В Си-коде сервера функция подключения к БД инициализируется строкой `"host=db port=5432 dbname=app_db"`. Docker DNS автоматически преобразует имя `db` во внутренний IP-адрес контейнера PostgreSQL (например, `172.28.0.3`).
   * ⚠️ **Частая ошибка новичков:** писать в настройках подключения `localhost` или `127.0.0.1`. Внутри контейнера это адрес **самого этого контейнера**, а не соседнего.

2. **Изоляция и безопасность портов:**
   Если сервису (например, базе данных PostgreSQL или Redis) не нужно получать трафик из внешнего мира, директиву **`ports` для него указывать НЕ нужно**!
   * Контейнеры, находящиеся **в одной сети**, видят все слушающие порты друг друга напрямую — пробрасывать их для этого не требуется.
   * Директива `ports` открывает порт на хосте. По умолчанию он становится доступен на **всех сетевых интерфейсах**, т. е. из внешней сети, что потенциально создаёт угрозу безопасности. Наружу следует пробрасывать только входные точки (Nginx / API Gateway). Если порт нужен только для локальной отладки, привяжите его к loopback: `"127.0.0.1:5432:5432"`.

3. **Разделение сетей (Network Segmentation):**
   Вы можете явно объявить несколько сетей для изоляции компонентов:

```yaml
networks:
  frontend_net:
    driver: bridge
  backend_net:
    driver: bridge

services:
  nginx:
    image: nginx:alpine
    networks:
      - frontend_net

  c_app:
    build: .
    networks:
      - frontend_net
      - backend_net

  postgres:
    image: postgres:16-alpine
    networks:
      - backend_net # Nginx (из frontend_net) не может обратиться к базе данных!
```

## Подглава 32.4: Сохранение данных в Docker Compose (Volumes vs Bind Mounts)

Контейнеры по своей природе эфемерны: при **удалении** контейнера (но не при простом перезапуске) весь его верхний записываемый слой (Writable-слой файловой системы OverlayFS) уничтожается вместе с данными. Для сохранения состояния используются тома (**Volumes**) и директории хоста (**Bind Mounts**).

```yaml
services:
  db:
    image: postgres:16-alpine
    volumes:
      # 1. Именованный том (Named Volume) - для данных базы данных
      - pg_data:/var/lib/postgresql/data

  web:
    build: .
    volumes:
      # 2. Bind Mount - монтирование файла с хоста для передачи конфигурации
      - ./config/server.conf:/app/config/server.conf:ro # :ro = Read-Only (Только чтение)

volumes:
  pg_data: # Объявление именованного тома на верхнем уровне
    driver: local
```

Как отличить том от bind mount по синтаксису: если слева от двоеточия стоит **путь** (начинается с `./`, `/` или `~`) — это bind mount; если просто **имя** (`pg_data`) — это именованный том, и его нужно объявить в блоке `volumes` верхнего уровня.

### Сравнение Volume и Bind Mount:

| Характеристика | Именованный том (Named Volume) | Монтирование хоста (Bind Mount) |
| :--- | :--- | :--- |
| **Где хранится** | В служебной директории Docker (на Linux — `/var/lib/docker/volumes/`) | В любой произвольной папке хост-системы (например, `./src`) |
| **Управление** | Управляется командами `docker volume` | Управляется файловой системой хоста |
| **Основной кейс** | Базы данных (PostgreSQL, MySQL), постоянное состояние | Исходный код при разработке, файлы конфигураций (`nginx.conf`) |
| **Производительность** | На Linux обе схемы работают на нативной скорости. В Docker Desktop (macOS/Windows) том обычно быстрее, т. к. хранится внутри виртуальной машины Docker | На Linux — нативная скорость; на macOS/Windows часто медленнее из-за передачи файлов между хостом и виртуальной машиной |

## Подглава 32.5: Конфигурация и переменные окружения (`.env` файлы)

Зашивать пароли и ключи шифрования прямо в `docker-compose.yml` — серьёзная ошибка безопасности: этот файл обычно хранится в Git, и секреты попадут в историю репозитория. Для управления конфигурацией используется файл **`.env`**.

### 1. Файл переменных окружения `.env` (в том же каталоге, что и `docker-compose.yml`):

```ini
# Сетевые порты
APP_PORT=8080

# Параметры базы данных PostgreSQL
POSTGRES_DB=production_db
POSTGRES_USER=app_admin
POSTGRES_PASSWORD=super_secret_secure_password_123
```

> ⚠️ **Правило безопасности:** Файл `.env` с реальными секретами **ОБЯЗАТЕЛЬНО добавляется в `.gitignore`**! В репозиторий коммитится только шаблон `.env.example` с фейковыми значениями.

> ℹ️ **Не путайте `.env` и `env_file`:**
> * Файл `.env` Compose читает **автоматически** и использует для подстановки значений в сам `docker-compose.yml` (запись `${ПЕРЕМЕННАЯ}`). Внутрь контейнеров эти переменные сами по себе **не попадают** — их нужно явно передать через `environment`.
> * Директива `env_file: имя_файла` напротив **передаёт все переменные из файла внутрь контейнера**.
>
> Проверить, как Compose подставил значения, можно командой `docker compose config`.
>
> Для продакшена с повышенными требованиями к безопасности вместо `.env` используют Docker secrets или внешние хранилища секретов (Vault и др.).

### 2. Использование переменных в `docker-compose.yml`:

```yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: ${POSTGRES_DB}
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - pg_data:/var/lib/postgresql/data

  web:
    build: .
    ports:
      - "${APP_PORT}:8080"
    environment:
      - DB_NAME=${POSTGRES_DB}
      - DB_USER=${POSTGRES_USER}
      - DB_PASSWORD=${POSTGRES_PASSWORD}
      - DB_HOST=db

volumes:
  pg_data:
```

## Подглава 32.6: Управление порядком запуска и проверки состояния (Healthchecks & `depends_on`)

Без `depends_on` Docker Compose запускает контейнеры параллельно. Но даже простая директива `depends_on: [db]` лишь гарантирует, что контейнер `db` будет **запущен первым**. Она НЕ ждёт, пока СУБД внутри него завершит инициализацию и станет готова принимать сетевые соединения!

Чтобы бэкенд не аварийно завершался при старте из-за попытки подключиться к ещё не поднявшейся БД, используются **Healthchecks**.

```yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: app_db
      POSTGRES_USER: app_user
      POSTGRES_PASSWORD: secret_password
    healthcheck:
      # Проверка готовности СУБД с помощью утилиты pg_isready
      test: ["CMD-SHELL", "pg_isready -U app_user -d app_db"]
      interval: 5s      # Интервал между проверками
      timeout: 5s       # Тайм-аут одной проверки
      retries: 5        # Сколько неудачных проверок подряд нужно для статуса unhealthy
      start_period: 10s # Время на первичную инициализацию: неудачные проверки в этот период не засчитываются

  web:
    build: .
    ports:
      - "8080:8080"
    depends_on:
      db:
        # Запускать сервис web ТОЛЬКО ПОСЛЕ того, как db станет healthy!
        condition: service_healthy
```

> 💡 Хорошая практика: помимо `healthcheck`, само приложение тоже должно уметь повторять попытку подключения к БД при ошибке — база может перезапуститься и во время работы.

## Подглава 32.7: Утилита Docker Compose CLI (Основные команды)

В современных версиях используется **Compose V2** — плагин `docker compose` (через пробел, без дефиса). Он входит в состав Docker Desktop, а на Linux с Docker Engine устанавливается отдельным пакетом `docker-compose-plugin`. Старая утилита `docker-compose` (с дефисом, V1) больше не поддерживается.

```bash
# 1. Сборка образов и запуск всех сервисов в фоновом режиме (Detached)
docker compose up -d --build

# 2. Просмотр статуса запущенных сервисов и портов
docker compose ps

# 3. Просмотр логов всех сервисов в режиме реального времени (Follow)
docker compose logs -f

# 4. Просмотр логов конкретного сервиса (например, только базы данных)
docker compose logs -f db

# 5. Выполнение команды внутри запущенного сервиса (например, запуск psql в БД)
docker compose exec db psql -U app_user -d app_db

# 6. Остановка всех сервисов (контейнеры, сети и данные в volumes сохраняются)
docker compose stop

# 7. Остановка и удаление контейнеров и сетей (именованные тома СОХРАНЯЮТСЯ)
docker compose down

# 8. То же, но с удалением именованных томов (!Удаляет данные БД безвозвратно!)
docker compose down -v

# 9. Проверка итогового конфига (после подстановки переменных из .env)
docker compose config
```

## Подглава 32.8: Готовый стек: C-Server + Nginx + PostgreSQL + Redis

Ниже представлен рабочий декларативный стек для C-сервера, который скрыт за Reverse-Proxy сервером Nginx, с PostgreSQL в качестве СУБД и Redis для оперативного кэширования. Для запуска понадобятся три файла: `.env`, `docker-compose.yml` и `nginx/nginx.conf`, а также `Dockerfile` вашего C-приложения (слушающего порт 8080).

Структура проекта:

```text
project/
├── .env
├── docker-compose.yml
├── Dockerfile
└── nginx/
    └── nginx.conf
```

### 1. Файл `.env`:
```ini
# Порт, на котором Nginx принимает трафик на хосте
HTTP_PORT=80

# База данных PostgreSQL
POSTGRES_DB=network_db
POSTGRES_USER=c_developer
POSTGRES_PASSWORD=hardcore_secure_pass_2026
```

### 2. Файл `nginx/nginx.conf`:
```nginx
events {}

http {
  server {
    listen 80;

    location / {
      # "web" - имя сервиса из docker-compose.yml, его разрешает Docker DNS
      proxy_pass http://web:8080;
      proxy_set_header Host $host;
      proxy_set_header X-Real-IP $remote_addr;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      proxy_set_header X-Forwarded-Proto $scheme;
    }
  }
}
```

### 3. Файл `docker-compose.yml`:
```yaml
services:
  # 1. Reverse Proxy веб-сервер Nginx (Входная точка трафика)
  proxy:
    image: nginx:1.30-alpine   # актуальная stable-ветка на момент написания; проверяйте версию на nginx.org и Docker Hub
    container_name: nginx_proxy
    ports:
      - "${HTTP_PORT}:80"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on:
      web:
        condition: service_started
    networks:
      - frontend_net
    restart: unless-stopped

  # 2. Наш C-сервер приложения
  web:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: c_backend_app
    environment:
      - APP_PORT=8080
      - DB_HOST=db
      - DB_PORT=5432
      - DB_NAME=${POSTGRES_DB}
      - DB_USER=${POSTGRES_USER}
      - DB_PASSWORD=${POSTGRES_PASSWORD}
      - REDIS_HOST=cache
      - REDIS_PORT=6379
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    networks:
      - frontend_net
      - backend_net
    restart: unless-stopped

  # 3. База данных PostgreSQL
  db:
    image: postgres:16-alpine
    container_name: postgres_db
    environment:
      POSTGRES_DB: ${POSTGRES_DB}
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - pg_data_volume:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s
      timeout: 5s
      retries: 5
      start_period: 10s
    networks:
      - backend_net
    restart: unless-stopped

  # 4. Оперативный кэш Redis
  cache:
    image: redis:7-alpine
    container_name: redis_cache
    volumes:
      - redis_data_volume:/data
    networks:
      - backend_net
    restart: unless-stopped

# Изолированные сети
networks:
  frontend_net:
    driver: bridge
  backend_net:
    driver: bridge

# Постоянные именованные тома
volumes:
  pg_data_volume:
    driver: local
  redis_data_volume:
    driver: local
```

Как это работает: внешний клиент обращается к Nginx (единственный сервис с `ports`), Nginx через `frontend_net` пересылает запрос сервису `web`, а `web` через `backend_net` обращается к `db` и `cache`. До БД и Redis из внешнего мира и из Nginx добраться нельзя.

> ℹ️ **Допущение.** Пример предполагает, что C-приложение говорит по **HTTP** (Nginx проксирует его через `proxy_pass http://...`). TCP-чат из Лекции 28.1 использует «сырой» TCP, и для него нужен модуль `stream`; пример такой настройки — в Подглаве 33.3.

## Подглава 32.9: Чек-лист DevOps / Системного инженера при работе с Docker Compose

1. **Никогда не зашивайте секреты в `docker-compose.yml`:** Используйте `.env` файлы и добавляйте их в `.gitignore`.
2. **Не пробрасывайте порты (`ports`) базы данных наружу без необходимости:** Для работы приложения достаточно внутреннего Service Discovery.
3. **Настраивайте `healthcheck` для СУБД:** Используйте `depends_on: { condition: service_healthy }` для предотвращения ошибок старта бэкенда.
4. **Монтируйте файлы конфигураций в режиме Read-Only (`:ro`):** Это защитит файлы на хосте от случайного изменения изнутри контейнера.
5. **Для долгоживущих (production) сервисов используйте `restart: unless-stopped`:** Контейнеры автоматически поднимутся после сбоя или перезагрузки сервера (при условии, что сам Docker запускается при старте ОС). Для разовых и отладочных задач политика не нужна.
6. **Не используйте `docker compose down -v` без необходимости:** Эта команда безвозвратно удаляет данные в именованных томах.

## Подсказки к практическим задачам

* **Подсказка к Задаче 1:**
  1. Нет, `nginx_proxy` находится только в `frontend_net`, а `postgres_db` — только в `backend_net`. Общей сети у них нет, поэтому они изолированы.

* **Подсказка к Задаче 2:**
  1. **Ошибка 1 (неверный адрес):** В `DB_URL` указан `127.0.0.1`. Внутри контейнера `app` адрес `127.0.0.1` означает сам контейнер `app`, а не базу данных! Нужно указать имя сервиса `db`.
  2. **Ошибка 2 (несоответствие пользователя и базы):** В `DB_URL` используются пользователь `user` и база `db`, но для сервиса `db` заданы только `POSTGRES_PASSWORD`. Нужно добавить `POSTGRES_USER=user` и `POSTGRES_DB=db`.
  3. **Дополнительные проблемы (не критичны для подключения):**
     * Нет `healthcheck` и `depends_on` — `app` может стартовать раньше, чем БД будет готова.

     * Логин и пароль записаны прямо в файле — их нужно вынести в `.env`.
