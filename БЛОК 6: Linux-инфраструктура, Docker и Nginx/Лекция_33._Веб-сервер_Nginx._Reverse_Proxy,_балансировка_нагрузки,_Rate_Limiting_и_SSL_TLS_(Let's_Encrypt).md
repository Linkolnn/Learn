В предыдущих лекциях Блока 6 мы изучили основы Linux (процессы, права доступа, SSH), упаковали приложение в изоляцию **Docker** и научились запускать несколько контейнеров вместе через **Docker Compose** (тома, сети, переменные окружения).

В примерах этой лекции «бэкенд» — это любое серверное приложение (например, написанное на Си), которое слушает порт и отвечает по протоколу HTTP.

Сегодня мы завершаем Блок 6 и изучаем один из самых важных компонентов современной веб-инфраструктуры — веб-сервер и обратный прокси-сервер **Nginx**. ## 💡 Глоссарий ключевых терминов лекции

> 📌 **1. Nginx**
> * **Что это:** Высокопроизводительный HTTP-сервер, обратный прокси-сервер (Reverse Proxy) и почтовый прокси-сервер с открытым исходным кодом. Автор — Игорь Сысоев: разработка началась в 2002 году, первый публичный релиз состоялся в 2004 году. Название читается как «энджин-экс».

> 📌 **2. Обратный прокси-сервер (Reverse Proxy)**
> * **Что это:** Сервер, стоящий между глобальным Интернетом и внутренними бэкенд-сервисами. Принимает внешние клиентские запросы, маршрутизирует их на внутренние сервисы, а ответы бэкендов возвращает обратно клиентам, скрывая реальную топологию сети.
> * **Не путать с обычным (forward) прокси:** обычный прокси работает *от имени клиента* (например, корпоративный прокси для выхода в Интернет), а обратный — *от имени сервера*.

> 📌 **3. Событийно-ориентированная архитектура (Event-Driven Architecture)**
> * **Что это:** Архитектура Nginx, при которой один рабочий процесс (Worker) использует неблокирующий ввод-вывод и механизм ядра ОС (`epoll` в Linux, `kqueue` в BSD/macOS), чтобы обслуживать тысячи одновременных соединений в одном потоке с минимальным расходом ОЗУ.
> * **Проблема C10K** — задача обслуживания 10 000 одновременных соединений на одном сервере (от англ. *Connection 10 Thousand*). Классические модели «один процесс/поток на соединение» с ней справлялись плохо.

> 📌 **4. Балансировка нагрузки (Load Balancing)**
> * **Что это:** Распределение входящего сетевого трафика между пулом нескольких идентичных бэкенд-серверов (**Upstream**) для выравнивания нагрузки и обеспечения отказоустойчивости.

> 📌 **5. Ограничение скорости запросов (Rate Limiting)**
> * **Что это:** Механизм ограничения количества HTTP-запросов в единицу времени (чаще всего — от одного клиентского IP-адреса). Защищает бэкенд от перегрузок, скрапинга (массового сбора данных) и **Brute-Force** (перебора паролей), а также смягчает простые flood-атаки с небольшого числа адресов. Работает по алгоритму «протекающего ведра» (Leaky Bucket).
> * **Важно:** Rate Limiting **не заменяет** полноценную защиту от распределённой DDoS-атаки (когда запросы идут с тысяч разных IP). Для этого используют CDN, WAF и защиту на уровне провайдера.

> 📌 **6. SSL/TLS и Let's Encrypt**
> * **Что это:** Криптографические протоколы шифрования сетевого трафика (**TLS** — современный преемник устаревшего **SSL**; сегодня реально используются только TLS 1.2 и 1.3, хотя по привычке говорят «SSL-сертификат»). **Let's Encrypt** — бесплатный автоматизированный центр сертификации (CA), выдающий валидные TLS-сертификаты по протоколу **ACME**. Клиент для получения сертификатов — утилита **Certbot**.

> 📌 **7. Upstream**
> * **Что это:** Группа бэкенд-серверов, на которые Nginx передаёт (проксирует) запросы. «Upstream» — «вверх по течению»: от Nginx в сторону приложения.

> 📌 **8. TLS-терминация**
> * **Что это:** Схема, при которой Nginx сам принимает зашифрованное HTTPS-соединение от клиента, расшифровывает его и передаёт запрос бэкенду уже по обычному HTTP внутри доверенной сети. Бэкенду не нужно заниматься шифрованием.

## Подглава 33.1: Архитектура Nginx: событийный цикл vs «процесс/поток на соединение»

Традиционные веб-серверы прошлых поколений (например, классический Apache HTTP Server в режиме `mpm_prefork`) выделяли отдельный процесс или поток ОС под каждое новое клиентское HTTP-соединение.

```text
[Традиционная модель (Apache MPM Prefork)]:
Подключение 1 ──> [ Процесс 1 (Память: ~10 МБ, ориентировочно) ] ──> Ожидание I/O / Диска...
Подключение 2 ──> [ Процесс 2 (Память: ~10 МБ, ориентировочно) ] ──> Ожидание I/O / Диска...
Подключение N ──> [ Процесс N ] ──> Память исчерпана! (OOM / C10K Problem)
```

> **OOM (Out Of Memory)** — ситуация, когда у системы заканчивается оперативная память и ядро начинает принудительно завершать процессы.

При росте числа одновременных пользователей до 10 000 (проблема **C10K**) эта модель упиралась в лимиты памяти и в накладные расходы на переключение между процессами (**Context Switching** — процессор тратит время на «переключение внимания» вместо полезной работы).

> **Замечание:** современный Apache умеет работать и в событийном режиме (`mpm_event`), поэтому сравнение выше — это сравнение двух *подходов*, а не «Nginx хороший, Apache плохой».

### Аналогия для понимания

Представьте ресторан. В традиционной модели на каждого гостя выделяется отдельный официант, который стоит у столика и ждёт, пока гость выберет блюдо. В модели Nginx несколько официантов (Worker) постоянно обходят все столики и обслуживают только тех, кто *уже готов* сделать заказ. Никто не простаивает в ожидании.

### Событийная архитектура Nginx (Master / Worker):

Nginx использует **Master-Worker** модель с асинхронным неблокирующим циклом событий (Event Loop на базе системного вызова `epoll` в Linux). Вызов `epoll` позволяет процессу сказать ядру: «разбуди меня, когда хотя бы один из этих тысяч сокетов будет готов к чтению или записи» — и до этого момента процесс не тратит ресурсы на пустое ожидание.

```text
                  ┌─────────────────────────────┐
                  │   Master Process (root)     │ <── Считывание конфигов,
                  └──────────────┬──────────────┘     перезапуск воркеров
                                 │
         ┌───────────────────────┼───────────────────────┐
         ▼                       ▼                       ▼
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│ Worker 1 (epoll)│     │ Worker 2 (epoll)│     │ Worker N (epoll)│
└────────┬────────┘     └────────┬────────┘     └────────┬────────┘
         │                       │                       │
         └──> [Каждый Worker обслуживает тысячи соединений в ОДНОМ потоке на неблокирующих сокетах]
```

1. **Master Process (Процесс-мастер):**
   * Запускается с правами `root` (это нужно, чтобы занять привилегированные порты 80/443 и прочитать закрытые ключи сертификатов).
   * Считывает и валидирует файлы конфигурации.
   * Управляет жизненным циклом рабочих процессов (Worker) и применяет конфигурацию без простоя (`nginx -s reload`): запускаются новые воркеры с новым конфигом, а старые дорабатывают текущие соединения и завершаются.
2. **Worker Processes (Рабочие процессы):**
   * Запускаются от имени непривилегированного пользователя, который задаётся директивой `user` (например, `www-data` в Debian/Ubuntu или `nginx` в официальных пакетах).
   * Директива `worker_processes auto;` задаёт **количество** воркеров, равное числу ядер CPU. Жёсткая привязка каждого воркера к конкретному ядру по умолчанию **не** выполняется (для неё есть отдельная директива `worker_cpu_affinity`); планировщик ОС сам распределяет воркеры по ядрам.
   * Используют системный вызов `epoll` для обслуживания тысяч клиентов в одном процессе без создания потоков под каждое соединение.

## Подглава 33.2: Структура и древо контекстов конфигурации `nginx.conf`

Конфигурация Nginx строится из **директив** (простые настройки, завершающиеся точкой с запятой `;`) и **контекстов/блоков** (группы директив, обрамлённые фигурными скобками `{}`).

### Пример главного файла `nginx.conf`:

```nginx
# 1. Main (Global) контекст: настройки процессов и логов
user nginx;
worker_processes auto;
error_log /var/log/nginx/error.log warn;
pid /var/run/nginx.pid;

# 2. Events контекст: настройки сетевых событий и epoll
events {
    worker_connections 1024; # Макс. одновременных соединений на 1 воркер
    use epoll;               # Механизм ввода-вывода Linux (в Linux выбирается автоматически)
}

# 3. HTTP контекст: глобальные настройки HTTP/HTTPS
http {
    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    access_log /var/log/nginx/access.log;

    sendfile on;       # Передача файлов средствами ядра, минуя копирование в память процесса (zero-copy)
    tcp_nopush on;     # При sendfile: отправка заголовков и начала файла вместе, заполненными пакетами
    keepalive_timeout 65;

    # Подключение внешних конфигурационных файлов.
    # Именно в них обычно лежат блоки server и upstream для конкретных сайтов.
    include /etc/nginx/conf.d/*.conf;
}
```

> **Важно про `worker_connections`.** Общее число одновременных соединений ≈ `worker_processes × worker_connections`. Например, 4 воркера × 1024 = 4096. Чтобы выдерживать 10 000+ соединений, значение нужно увеличивать (и, как правило, поднимать лимит открытых файлов директивой `worker_rlimit_nofile`). Кроме того, при работе в роли reverse proxy каждый клиент занимает **два** соединения: одно с клиентом, второе с бэкендом.

### Иерархия контекстов (вложенность):

```text
main (глобальный уровень, вне фигурных скобок)
├── events
└── http
    ├── upstream   (пул бэкендов)
    └── server     (виртуальный хост)
        └── location   (маршрут по URI)
```

* **`main` (глобальный):** опции процессов, PID, `error_log`.
* **`events`:** низкоуровневые параметры сети и событий.
* **`http`:** общие параметры веб-сервера, сжатие (gzip), таймауты, логи, зоны Rate Limiting.
* **`upstream`:** определение пулов бэкенд-серверов для проксирования и балансировки (находится внутри `http`).
* **`server`:** виртуальный хост (виртуальный сайт), привязанный к порту и имени домена (`listen`, `server_name`).
* **`location`:** маршрутизация внутри виртуального хоста по URI запроса.

Вложенные контексты **наследуют** настройки родительских. Но есть тонкость: для директив-«списков» (например, `proxy_set_header`, `add_header`) наследование работает по принципу «всё или ничего» — если вы задали хотя бы одну такую директиву на более глубоком уровне, то **все** значения с верхнего уровня перестают действовать. Это частая причина «пропавших» заголовков.

## Подглава 33.3: Обратный прокси (Reverse Proxy) и проброс заголовков

Одно из главных назначений Nginx — принимать HTTP-запросы из глобальной сети на портах `80/443`, выполнять тяжёлую работу по терминации (расшифровке) TLS, сжатию и раздаче статики, а затем проксировать динамические запросы на внутренний C/Go/Node бэкенд через директиву **`proxy_pass`**.

> **Оговорка.** Директива `proxy_pass` в контексте `http` работает только с протоколом HTTP (и родственными ему, например WebSocket с доп. настройками). Если ваше приложение (например, учебный чат на Си) общается по «сырому» TCP-протоколу, а не по HTTP, то для него нужен другой модуль — `stream`, который проксирует TCP/UDP без анализа содержимого.

### Проблема потери клиентских данных при проксировании:
Когда Nginx делает запрос к внутреннему бэкенду (`http://127.0.0.1:8080`), для бэкенда IP-адресом клиента становится IP-адрес самого Nginx (`127.0.0.1`).

### Рекомендуемые заголовки проксирования (`proxy_set_header`):

```nginx
server {
    listen 80;
    server_name example.com www.example.com;

    # Раздача статического контента напрямую Nginx (быстро и без нагрузки на C-бэкенд)
    location /static/ {
        alias /var/www/example/static/;
        expires 30d;                                  # добавит заголовок Cache-Control: max-age=...
        add_header Cache-Control "public, no-transform";  # добавит ещё одно значение Cache-Control
    }

    # Динамические запросы отправляем на C-бэкенд (наше приложение или API)
    location / {
        proxy_pass http://127.0.0.1:8080;

        # Передаём исходный Host запрашиваемого сайта
        # (без этой строки бэкенд увидит Host: 127.0.0.1:8080)
        proxy_set_header Host $host;

        # Передаём реальный IP-адрес клиента бэкенду
        proxy_set_header X-Real-IP $remote_addr;

        # Передаём цепочку всех промежуточных прокси
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        # Передаём исходный протокол (http или https)
        proxy_set_header X-Forwarded-Proto $scheme;

        # Таймауты
        proxy_connect_timeout 5s;   # сколько ждать установки соединения с бэкендом
        proxy_read_timeout 60s;     # сколько ждать очередную порцию ответа от бэкенда (60s — значение по умолчанию)
    }
}
```

> **Безопасность:** бэкенд должен доверять заголовкам `X-Real-IP` / `X-Forwarded-For` **только** от Nginx. Если бэкенд доступен напрямую из Интернета, клиент сможет подделать эти заголовки.

## Подглава 33.4: Балансировка нагрузки между бэкендами (`upstream`)

Если одного C/Go приложения не хватает для обработки высокого трафика, запускают несколько экземпляров приложения (например, на портах `8081`, `8082`, `8083` или в разных контейнерах Docker) и объединяют их в блок **`upstream`**.

```text
                           ┌──> [ App Instance 1: 127.0.0.1:8081 ]
                           │
[ Клиент ] ──> [ Nginx ] ──┼──> [ App Instance 2: 127.0.0.1:8082 ]
                           │
                           └──> [ App Instance 3: 127.0.0.1:8083 ]
```

### Алгоритмы (методы) балансировки Nginx:
1. **Round Robin (по умолчанию):** циклическая последовательная передача запросов по очереди.
2. **Least Connections (`least_conn`):** отправка запроса на бэкенд с наименьшим количеством активных соединений.
3. **IP Hash (`ip_hash`):** закрепление клиента за конкретным бэкендом на основе хэша его IP-адреса (для сохранения сессий — Sticky Sessions). Недостаток: клиенты за одним NAT (например, весь офис) попадут на один и тот же сервер.
4. **Hash (`hash $ключ`)** и **Random (`random`)** — дополнительные методы: хэш по произвольному ключу (например, по URI) и случайный выбор.

### Веса (`weight=N`)
Вес — это **не отдельный алгоритм**, а параметр сервера внутри `upstream`. Он работает вместе с Round Robin или `least_conn` и задаёт долю трафика пропорционально мощности сервера (сервер с `weight=3` получает в 3 раза больше запросов, чем сервер с весом по умолчанию 1).

### Конфигурация Upstream с пассивным контролем сбоев:

```nginx
upstream backend_cluster {
    # Алгоритм наименьшего количества соединений
    least_conn;

    # Сервер 1 с повышенным весом.
    # max_fails=3 fail_timeout=10s: если за 10 секунд было 3 неудачные попытки обращения,
    # сервер считается недоступным и исключается из ротации на 10 секунд.
    server 127.0.0.1:8081 weight=3 max_fails=3 fail_timeout=10s;

    # Сервер 2
    server 127.0.0.1:8082 max_fails=3 fail_timeout=10s;

    # Резервный сервер (включается, только если 8081 и 8082 недоступны)
    server 127.0.0.1:8083 backup;
}

server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://backend_cluster;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

> **Про «Health Checks».** Параметры `max_fails` и `fail_timeout` — это **пассивная** проверка: Nginx узнаёт о проблеме только тогда, когда реальный клиентский запрос к серверу завершился ошибкой. **Активные** проверки (когда Nginx сам периодически «пингует» бэкенды) доступны только в коммерческой версии NGINX Plus.

## Подглава 33.5: Защита от перегрузок и Brute-Force через Rate Limiting

Nginx позволяет защитить сервер от чрезмерной частоты запросов (**Rate Limiting**), реализуя алгоритм **«протекающего ведра» (Leaky Bucket)**: запросы «наливаются» в ведро, а «вытекают» из него с постоянной скоростью; если ведро переполнено — лишние запросы отбрасываются.

> **Ограничение метода.** Лимит по IP эффективен против одиночных клиентов и скриптов-переборщиков. Против распределённой DDoS-атаки с множества адресов он бессилен — нужны CDN/WAF. Кроме того, если перед Nginx стоит другой прокси или CDN, переменная `$remote_addr` будет содержать адрес *этого прокси*; в таком случае нужно настраивать модуль `realip`, иначе лимит применится ко всем пользователям сразу.

### Настройка ограничения частоты запросов:

1. В контексте **`http`** (например, в файле из `conf.d`, вне блоков `server`) задаются зоны памяти для хранения состояния IP-адресов:
```nginx
# Зона 'api' объёмом 10 МБ (хранит ~160 000 IP-адресов), лимит 10 запросов в секунду с одного IP
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;

# Отдельная, более строгая зона для формы входа: 5 запросов в минуту (в среднем 1 запрос в 12 секунд)
limit_req_zone $binary_remote_addr zone=login:10m rate=5r/m;
```

2. В контексте **`server`/`location`** применяется ограничение:
```nginx
server {
    listen 80;
    server_name example.com;

    # Код ответа при превышении лимита (по умолчанию 503 Service Temporarily Unavailable)
    limit_req_status 429;

    # Общий лимит на API: мягкий, с запасом на всплески
    location /api/ {
        limit_req zone=api burst=20 nodelay;
        proxy_pass http://127.0.0.1:8080;
    }

    # Форма входа: строгий лимит против перебора паролей
    location /api/v1/login {
        limit_req zone=login burst=3 nodelay;
        proxy_pass http://127.0.0.1:8080;
    }
}
```

* **`rate`:** средняя допустимая скорость. Nginx считает её по-настоящему «ровно»: `rate=10r/s` означает «1 запрос каждые 100 мс», а не «10 запросов, которые можно отправить в любую долю секунды».
* **`burst=N`:** размер «запаса» — сколько запросов сверх ровной скорости Nginx готов принять в короткий промежуток. Свободное место в этом запасе освобождается постепенно, с той же скоростью `rate`.
* **Без `nodelay`:** запросы из `burst` ставятся в очередь и **задерживаются**, чтобы выдерживалась ровная скорость.
* **С `nodelay`:** запросы из `burst` обрабатываются **сразу**, без задержки, но занимают места в запасе. Всё, что не поместилось, немедленно отклоняется с кодом **`429 Too Many Requests`** (при `limit_req_status 429`) или **`503`** (по умолчанию).

## Подглава 33.6: Шифрование HTTPS и автоматическое получение SSL/TLS сертификатов Let's Encrypt

В современном веб-пространстве передача паролей и cookie по незашифрованному HTTP (порт `80`) недопустима. Трафик должен шифроваться протоколом **TLS 1.2 / TLS 1.3** на порту `443` (HTTPS).

### 1. Автоматическое получение бесплатного TLS-сертификата с помощью Certbot:

Утилита **Certbot** запрашивает сертификат у центра **Let's Encrypt** по протоколу **ACME**. Для подтверждения того, что вы владеете доменом, используется **HTTP-01 вызов**: Certbot кладёт временный файл в каталог `/.well-known/acme-challenge/`, а Let's Encrypt пытается скачать его по адресу `http://ваш-домен/.well-known/acme-challenge/...`.

**Условия для успешной выдачи:**
* домен должен быть реальным и его DNS A/AAAA-запись должна указывать на ваш сервер;
* порт `80` должен быть доступен из Интернета (для этого и нужен HTTP-сервер).

```bash
# Установка Certbot и плагина Nginx в Ubuntu/Debian
sudo apt update && sudo apt install -y certbot python3-certbot-nginx

# Вариант А. Автоматическое получение сертификата И автоматическая правка конфига Nginx:
sudo certbot --nginx -d example.com -d www.example.com

# Вариант Б. Только получение сертификата, конфиг вы пишете сами (метод webroot).
# Именно этот вариант соответствует конфигурации ниже:
sudo certbot certonly --webroot -w /var/www/html -d example.com -d www.example.com

# Проверка автоматического продления (сухой прогон, ничего не меняет)
sudo certbot renew --dry-run
```

**Срок действия и продление.** Сертификаты Let's Encrypt выдаются на ограниченный срок (сейчас по умолчанию — 90 дней, в будущем срок будет сокращаться). Поэтому продление должно быть автоматическим: пакет `certbot` обычно сам настраивает системный таймер или задание cron, которое периодически запускает `certbot renew`. После обновления сертификата Nginx нужно перечитать конфигурацию (`nginx -s reload`) — Certbot делает это сам при использовании плагина `--nginx`.

### 2. Типовая HTTPS-конфигурация Nginx (метод webroot):

```nginx
# 1. Редирект с незашифрованного HTTP (80) на безопасный HTTPS (443)
server {
    listen 80;
    listen [::]:80;
    server_name example.com www.example.com;

    # Каталог для проверки домена Certbot (ACME Challenge).
    # Должен быть доступен по HTTP, поэтому не редиректится.
    location /.well-known/acme-challenge/ {
        root /var/www/html;
    }

    # Все остальные HTTP-запросы редиректим на HTTPS
    location / {
        return 301 https://$host$request_uri;
    }
}

# 2. Безопасный виртуальный хост HTTPS (443)
server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;    # HTTP/2 включается отдельной директивой (Nginx 1.25.1+).
                 # Старая запись "listen 443 ssl http2;" считается устаревшей.
    server_name example.com www.example.com;

    # Пути к ключам и сертификатам Let's Encrypt
    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    # Параметры TLS (рекомендации Mozilla, профиль "Intermediate")
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305:DHE-RSA-AES128-GCM-SHA256:DHE-RSA-AES256-GCM-SHA384:DHE-RSA-CHACHA20-POLY1305;
    ssl_prefer_server_ciphers off;

    # Кэширование сессий TLS для ускорения повторных подключений
    ssl_session_timeout 1d;
    ssl_session_cache shared:SSL:10m;
    ssl_session_tickets off;

    # Проксирование трафика на локальное C/Go приложение
    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

> **Примечания.**
> * Директива `ssl_ciphers` влияет только на TLS 1.2; наборы шифров TLS 1.3 фиксированы и безопасны по умолчанию.
> * Профиль Mozilla «Modern» разрешает **только** TLS 1.3. Конфигурация, где включён и TLS 1.2, — это профиль «Intermediate».
> * Если вы получали сертификат вариантом А (`certbot --nginx`), Certbot сам допишет нужные строки в ваш конфиг; тогда готовый конфиг выше нужен лишь как образец.

## Подглава 33.7: Интеграция Nginx в Docker Compose стек

Ниже представлен минимальный рабочий манифест **`docker-compose.yml`**, объединяющий Nginx (Reverse Proxy) и наш C-сервер приложений. Предполагается, что рядом лежит `Dockerfile`, собирающий образ приложения, которое слушает порт `8080`.

```yaml
# Поле "version" в современном Docker Compose больше не нужно (считается устаревшим).

services:
  # Наш C-сервер (бэкенд)
  app_backend:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: c_app_backend
    restart: always
    # expose НЕ публикует порт наружу: 8080 доступен ТОЛЬКО другим контейнерам этой сети Compose.
    expose:
      - "8080"

  # Reverse-Proxy Nginx (принимает внешний трафик)
  web_proxy:
    image: nginx:alpine
    container_name: nginx_proxy
    restart: always
    ports:
      - "80:80"
      # - "443:443"   # раскомментируйте, когда настроите HTTPS (см. подглаву 33.6)
    volumes:
      - ./default.conf:/etc/nginx/conf.d/default.conf:ro
      - ./html:/var/www/html:ro
      # - certs_data:/etc/letsencrypt   # понадобится при настройке HTTPS
    depends_on:
      - app_backend

# volumes:
#   certs_data:
```

### Содержимое монтируемого файла `default.conf`:

Этот файл подменяет стандартную конфигурацию виртуального хоста внутри контейнера (`/etc/nginx/conf.d/default.conf`). Это **не** полный `nginx.conf`, а только блок `server` — главный `nginx.conf` в образе остаётся стандартным и сам подключает всё из `conf.d/`.

```nginx
server {
    listen 80;
    server_name localhost;

    location / {
        # Обращаемся к C-бэкенду по имени сервиса в Docker DNS!
        proxy_pass http://app_backend:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

> **Тонкость.** Nginx преобразует имя `app_backend` в IP-адрес **один раз при запуске**. Если контейнер бэкенда не существует в этот момент, Nginx не запустится с ошибкой `host not found in upstream`; если контейнер потом пересоздастся с другим IP, Nginx про это не узнает до перезагрузки конфигурации. Поэтому в манифесте указан `depends_on`, а при пересоздании бэкенда выполняйте `nginx -s reload`.

## Подглава 33.8: Чек-лист системного администратора при работе с Nginx

1. **Всегда проверяйте синтаксис конфигов перед применением:**
   Выполняйте `nginx -t` перед `nginx -s reload` или `systemctl reload nginx`. Если проверка не прошла, перезагружать конфигурацию нельзя.
2. **Пробрасывайте реальный IP клиента — и учите бэкенд его использовать:**
   Без `proxy_set_header X-Real-IP $remote_addr;` (и `X-Forwarded-For`) все логи C/Go бэкенда будут содержать IP-адрес `127.0.0.1` или IP-адрес Docker-контейнера. Само приложение при этом должно читать этот заголовок и доверять ему только от Nginx.
3. **Не путайте `root` и `alias` в `location`:**
   Директива `root` **добавляет** URI запроса к пути на диске, а `alias` **заменяет** совпавшую с `location` часть URI. Если путь на диске не повторяет структуру URL, используйте `alias` (и следите за слешем на конце: `location /static/` ↔ `alias /путь/static/;`).
4. **Закрывайте внутренние порты бэкендов от внешнего мира:**
   Внешний доступ к C-бэкендам должен идти **строго через Nginx** (порты `80/443`). Порты бэкендов (`8080`) и СУБД (`5432`) не должны открываться в глобальный Интернет. **Внимание для Docker:** опубликованные через `ports:` порты Docker открывает в обход правил `ufw`. Поэтому для внутренних сервисов используйте `expose:` или привязку к localhost (`"127.0.0.1:8080:8080"`).
5. **Включайте `sendfile` и `keepalive`:**
   Директива `sendfile on;` сокращает нагрузку на CPU при раздаче статических файлов за счёт системного вызова ядра Linux `sendfile()`. Директива `keepalive_timeout` позволяет клиенту переиспользовать одно TCP-соединение для нескольких запросов вместо открытия нового на каждый запрос.

## Подсказки и решения к практическим задачам

* **Подсказка к Задаче 1:**
  1. Настройка `rate=12r/m` означает в среднем 12 запросов в минуту. Nginx контролирует скорость «ровно», поэтому это равно **1 запросу каждые $60 / 12 = 5$ секунд**. Отправить все 12 запросов подряд в первую секунду минуты (без `burst`) не получится.
  2. Без параметра `burst` (когда `burst=0`) любой повторный запрос от одного IP-адреса, пришедший раньше, чем через **5 секунд** после предыдущего, будет сразу отклонён с ошибкой (по умолчанию `503`, либо `429`, если задан `limit_req_status 429`).

* **Подсказка к Задаче 2:**
  Всего в конфигурации четыре ошибки двух типов.

  **Тип 1. Синтаксические (Nginx не запустится):** пропущены точки с запятой `;` в трёх строках — `server_name mysite.com;`, `proxy_pass http://127.0.0.1:5000;` и `proxy_set_header Host $host;`. Проверка `nginx -t` сообщит о синтаксической ошибке.

  **Тип 2. Логическая (будет `404`):** неверное сочетание `location` и `root`. При `location /static/` и `root /var/www/mysite/static/;` Nginx *добавляет* URI к пути `root` и будет искать файлы по пути `/var/www/mysite/static/static/file.css` (`/static/` дублируется). Исправление — либо `alias /var/www/mysite/static/;`, либо `root /var/www/mysite/;`.

* **Подсказка к Задаче 3:**
  Готовое решение (блоки находятся в контексте `http`, например в файле из `conf.d`):
  ```nginx
  upstream c_backend_pool {
      least_conn;
      server 127.0.0.1:9001 max_fails=3 fail_timeout=10s;
      server 127.0.0.1:9002 max_fails=3 fail_timeout=10s;
  }

  # HTTP Редирект
  server {
      listen 80;
      server_name app.internal;
      return 301 https://$host$request_uri;
  }

  # HTTPS Сервер
  server {
      listen 443 ssl;
      server_name app.internal;

      # Для внутреннего домена .internal Let's Encrypt сертификат не выдаст,
      # поэтому используется собственный (например, самоподписанный) сертификат
      ssl_certificate     /etc/ssl/certs/app.crt;
      ssl_certificate_key /etc/ssl/private/app.key;
      ssl_protocols TLSv1.2 TLSv1.3;

      location / {
          proxy_pass http://c_backend_pool;
          proxy_set_header Host $host;
          proxy_set_header X-Real-IP $remote_addr;
          proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
          proxy_set_header X-Forwarded-Proto $scheme;
      }
  }
  ```
