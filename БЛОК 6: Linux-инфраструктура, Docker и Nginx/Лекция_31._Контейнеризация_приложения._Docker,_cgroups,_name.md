## 💡 Глоссарий ключевых терминов лекции

> 📌 **1. Контейнеризация (Containerization)**
> * **Что это:** Метод виртуализации на уровне операционной системы, позволяющий запускать изолированные процессы (контейнеры) с собственными файловыми системами, деревом процессов и сетевыми стеками, использующие единое общее ядро ОС (Host Kernel).

> 📌 **2. Пространства имён ядра (Linux Namespaces)**
> * **Что это:** Механизм ядра Linux, обеспечивающий изоляцию системных ресурсов (PID, Network, Mount, IPC, UTS, User и др.) для группы процессов, из-за чего контейнер «видит» только предназначенную ему часть системы.

> 📌 **3. Контрольные группы (Control Groups / cgroups)**
> * **Что это:** Механизм ядра Linux, позволяющий ограничивать и учитывать потребление ресурсов (CPU, ОЗУ, ввод-вывод диска, количество процессов) для группы процессов.

> 📌 **4. Многослойная файловая система (OverlayFS)**
> * **Что это:** Файловая система, которая накладывает несколько директорий друг на друга и показывает их как одну. Нижние слои образа остаются доступными только для чтения (`lowerdir`), а все изменения записываются в верхний слой контейнера (`upperdir`) по принципу **Copy-on-Write (COW)**. OverlayFS относится к классу *union-файловых систем* (union mount); именно её использует драйвер Docker `overlay2`.

> 📌 **5. Образ Docker (Docker Image)**
> * **Что это:** Неизменяемый (Immutable) шаблон только для чтения, состоящий из набора слоёв файловой системы и метаданных, используемый для создания и запуска контейнеров.

> 📌 **6. Контейнер Docker (Docker Container)**
> * **Что это:** Запущенный изолированный экземпляр образа Docker, представляющий собой обычный процесс Linux, ограниченный пространствами имён и cgroups, с изменяемым слоем записи OverlayFS.

> 📌 **7. Многоэтапная сборка (Multi-Stage Build)**
> * **Что это:** Техника написания `Dockerfile` с несколькими инструкциями `FROM`, позволяющая скомпилировать приложение в «тяжёлом» промежуточном образе со всеми компиляторами и инструментами, а затем скопировать готовый бинарный файл в лёгкий финальный образ (например, `alpine` или `scratch`).

## Подглава 31.1: Виртуализация vs Контейнеризация. Механизмы ядра Linux

Разработчики часто путают классические виртуальные машины (VM) и контейнеры.

### Сравнение архитектуры:

```text
[ Классическая Виртуальная Машина (VM) ]           [ Контейнер Docker ]

+-------------------------------------+      +-------------------------------------+
|   Приложение A   |   Приложение B   |      |   Приложение A   |   Приложение B   |
+------------------+------------------+      +------------------+------------------+
| Зависимости/Libs | Зависимости/Libs |      | Зависимости/Libs | Зависимости/Libs |
+------------------+------------------+      +------------------+------------------+
| Гостевая OS A    | Гостевая OS B    |      | Контейнер A (NS) | Контейнер B (NS) |
| (Своё ядро OS)   | (Своё ядро OS)   |      +------------------+------------------+
+------------------+------------------+      |       Docker Engine / OCI          |
|            Гипервизор               |      +-------------------------------------+
|      (KVM / ESXi / VirtualBox)      |      |   Единое ядро Linux (Host Kernel)   |
+-------------------------------------+      +-------------------------------------+
|         Аппаратное железо           |      |         Аппаратное железо           |
+-------------------------------------+      +-------------------------------------+
```

* **Виртуальные машины (Гипервизор):** гипервизор выделяет каждой VM виртуальное «железо». Каждая VM запускает собственное полноценное ядро ОС, поэтому занимает сотни мегабайт — гигабайты ОЗУ и обычно загружается десятки секунд.
* **Контейнеры (Виртуализация на уровне ОС):** контейнер — это **обычный процесс в Linux**, изолированный от других процессов с помощью механизмов ядра. Контейнеры делят одно общее ядро хоста, запускаются за доли секунды и потребляют минимум памяти.
* **Цена такой лёгкости:** изоляция слабее, чем у VM, потому что ядро общее — уязвимость в ядре может затронуть все контейнеры. Кроме того, контейнеру Linux нужно ядро Linux: Docker Desktop на Windows и macOS запускает для этого небольшую виртуальную машину с Linux.

## Подглава 31.2: Фундамент контейнеров: Namespaces и cgroups

Контейнер держится на двух «столпах» ядра Linux:

### 1. Пространства имён (Linux Namespaces) — Изоляция видимости

Namespaces определяют, **что процесс может видеть** в системе. В Linux существует 8 типов пространств имён; в контейнерах чаще всего используются эти шесть:

1. **`pid` (Process IDs):** изоляция дерева процессов. Первый процесс контейнера получает `PID 1` и не видит процессов хоста.
2. **`net` (Network):** изоляция сетевых интерфейсов, IP-адресов, таблиц маршрутизации и портов.
3. **`mnt` (Mount):** изоляция точек монтирования файловой системы.
4. **`ipc` (Inter-Process Communication):** изоляция разделяемой памяти, очередей сообщений и семафоров (System V и POSIX).
5. **`uts` (UNIX Timesharing System):** изоляция имени хоста (`hostname`) и доменного имени.
6. **`user` (User IDs):** отображение UID/GID внутри контейнера на другие UID/GID хоста (например, `root` в контейнере может быть обычным пользователем `UID 1000` на хосте).

Оставшиеся два типа — `cgroup` (изолирует вид иерархии cgroups) и `time` (изолирует системные часы).

> ⚠️ По умолчанию Docker **не включает** `user` namespace: `root` внутри контейнера — это настоящий `UID 0` на хосте, только с урезанными возможностями (capabilities). Поэтому запуск от непривилегированного пользователя (см. чек-лист) так важен.

---

### 2. Контрольные группы (cgroups v1/v2) — Ограничение ресурсов

cgroups определяют, **сколько ресурсов процесс может потреблять**. В современных дистрибутивах по умолчанию используется единая иерархия **cgroups v2**.

* **Ограничение RAM** (`docker run --memory=256m`): если контейнер превышает лимит памяти, ядро запускает **OOM Killer (Out-Of-Memory)**, который убивает процесс сигналом `SIGKILL`. Код завершения при этом равен `137` (128 + номер сигнала 9). Такой же код получится и при `docker kill`; чтобы отличить причину, смотрите поле `OOMKilled` в `docker inspect`.
* **Ограничение CPU:** задаётся **квота процессорного времени** (механизм CFS bandwidth control). Например, `--cpus="1.5"` означает «не больше, чем 1,5 ядра по суммарному времени», но *не* закрепляет контейнер за конкретными ядрами. Для закрепления есть отдельный параметр `--cpuset-cpus`.
* **I/O диска:** ограничение скорости чтения/записи (IOPS и МБ/с) для блочных устройств.
* **Количество процессов:** лимит на число процессов в контейнере (`--pids-limit`) защищает от «fork-бомб».

## Подглава 31.3: Устройство OverlayFS и слои образов

Образы Docker строятся по принципу слоёв. Инструкции `RUN`, `COPY` и `ADD` создают новый слой файловой системы, доступный только для чтения (**Read-Only Layer**). Остальные инструкции (`ENV`, `WORKDIR`, `USER`, `EXPOSE`, `CMD`, `ENTRYPOINT`) меняют только метаданные образа и слоёв с файлами не добавляют.

### Архитектура overlay2:

```text
+-----------------------------------------------------------------------+
|  Верхний слой записи контейнера (Container Layer / upperdir)  [RW]     |  <-- Все изменения
+-----------------------------------------------------------------------+
|  Слой 3: Установка компилятора и библиотек           [Read-Only]     |
|  Слой 2: Копирование исходного кода                  [Read-Only]     |  <-- Образ Docker
|  Слой 1: Базовая ОС Alpine Linux                     [Read-Only]     |
+-----------------------------------------------------------------------+
                                  │
                                  ▼ (Объединение через OverlayFS)
+-----------------------------------------------------------------------+
|  Объединённый вид файловой системы контейнера (merged)                |
+-----------------------------------------------------------------------+
```

* **`lowerdir`:** набор нижних неизменяемых слоёв образа (Read-Only).
* **`upperdir`:** верхний слой контейнера с правами чтения и записи (Read-Write).
* **`workdir`:** служебный каталог, который OverlayFS использует для атомарных операций.
* **`merged`:** итоговая виртуальная директория, которую видит процесс внутри контейнера.
* **Принцип Copy-on-Write (COW):** если контейнер пытается изменить файл из нижнего Read-Only слоя, OverlayFS сначала копирует этот файл целиком в верхний слой `upperdir` и только потом модифицирует копию.
* **Удаление файлов:** удалить файл из нижнего слоя нельзя — в верхнем слое создаётся специальная метка («whiteout»), которая *скрывает* файл. Физически он остаётся в нижнем слое (это важно для размера образа, см. Задачу 1).

## Подглава 31.4: Архитектура Docker: Engine, containerd и runc

Docker не является монолитом, а состоит из цепочки компонентов, соответствующих стандартам **OCI (Open Container Initiative)**:

```text
[ Docker CLI ]  ──(REST API через Unix-сокет)──>  [ dockerd (Docker Daemon) ]
                                                          │
                                                          ▼
                                                  [ containerd ]
                                                          │
                                                          ▼
                                          [ containerd-shim ] ── следит за контейнером
                                                          │
                                                          ▼
                                            [ runc (OCI Runtime) ]
                                                          │
                                                          ▼
                                            [ Контейнер (Процесс Linux) ]
```

1. **Docker CLI (`docker`):** клиентская консольная утилита, отправляющая REST-запросы к демону. По умолчанию связь идёт через Unix-сокет `/var/run/docker.sock`.
2. **`dockerd`:** высокоуровневый демон, управляющий образами, сетями, томами и сборкой.
3. **`containerd`:** системная служба управления жизненным циклом контейнеров (скачивание образов, передача управления runtime).
4. **`containerd-shim`:** небольшой процесс-посредник, который остаётся «родителем» контейнера и позволяет перезапускать `dockerd`/`containerd`, не убивая контейнеры.
5. **`runc`:** низкоуровневая утилита OCI Runtime, которая напрямую вызывает системные функции Linux (`clone()`, `unshare()`, `setns()`, настройка cgroups) для создания контейнера, после чего завершает работу.

> ⚠️ Доступ к `/var/run/docker.sock` фактически равен правам root на хосте (через Docker можно смонтировать любой каталог хоста). Не добавляйте в группу `docker` тех, кому нельзя доверять root.

## Подглава 31.5: Разработка Dockerfile: Best Practices и Multi-Stage Builds

`Dockerfile` — это текстовый сценарий сборки образа.

### 1. Антипаттерн: сборка и запуск в одном образе (Размер: ~300 МБ)

```dockerfile
# ПЛОХО: образ замусорен компиляторами, кэшем пакетов и исходниками,
# приложение работает от root
FROM ubuntu:22.04
RUN apt-get update && apt-get install -y gcc make
COPY . /app
WORKDIR /app
RUN gcc -O2 main.c -o my_server
CMD ["./my_server"]
```

---

### 2. Best Practice: Промышленный Multi-Stage Dockerfile (Размер: ~10 МБ)

```dockerfile
# ==============================================================================
# ЭТАП 1: Сборка (Build Stage)
# ==============================================================================
# Версия образа приведена для примера: используйте актуальную поддерживаемую версию
FROM alpine:3.22 AS builder

# Установка компилятора и библиотек
RUN apk add --no-cache gcc musl-dev make

WORKDIR /build

# Копируем исходники проекта (лишнее исключается файлом .dockerignore)
COPY . .

# Компилируем статический бинарник (не зависит от системных библиотек).
# Предполагается, что Makefile учитывает CFLAGS и создаёт файл my_server
RUN make CFLAGS="-O2 -static"

# ==============================================================================
# ЭТАП 2: Финальный минималистичный образ (Production Stage)
# ==============================================================================
FROM alpine:3.22

# Создаём не-root пользователя для безопасности
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

WORKDIR /app

# Копируем ИСКЛЮЧИТЕЛЬНО готовый бинарник из этапа builder.
# Файл остаётся принадлежать root: appuser может его запускать, но не изменять
COPY --from=builder /build/my_server /app/my_server

# Переключаемся на непривилегированного пользователя
USER appuser

# Документируем, какой порт слушает приложение.
# EXPOSE сам порт НЕ публикует — для этого нужен флаг -p при docker run
EXPOSE 8080

# Используем exec-форму (JSON-массив), чтобы сигналы получало само приложение
ENTRYPOINT ["/app/my_server"]
```

> 📌 **Ключевые правила оптимизации Dockerfile:**
> 1. **Используйте Multi-Stage builds:** оставляйте компиляторы (`gcc`, `make`) на этапе сборки.
> 2. **Порядок слоёв имеет значение:** копируйте редко меняющиеся файлы раньше часто меняющихся, чтобы Docker мог переиспользовать закэшированные слои (Docker Layer Cache). Как только меняется один слой, пересобираются **все** слои после него. Типичный пример для проекта с зависимостями (Node.js, который мы изучим в Блоке 12):
>    ```dockerfile
>    COPY package.json package-lock.json ./   # меняется редко
>    RUN npm ci                               # слой с зависимостями берётся из кэша
>    COPY . .                                 # меняется часто
>    ```
>    В нашем маленьком Си-проекте сторонних зависимостей нет, поэтому достаточно `COPY . .`.
> 3. **Не запускайте контейнер от `root`:** создавайте и используйте непривилегированного пользователя (`USER appuser`).
> 4. **Используйте JSON-форму ENTRYPOINT / CMD:** `ENTRYPOINT ["/app/app"]` запускает приложение напрямую, оно становится `PID 1` и само получает сигналы. Shell-форма `ENTRYPOINT ./app` запускает оболочку `/bin/sh -c`, которая, как правило, не передаёт `SIGTERM` приложению.
> 5. **Помните об особенности `PID 1`:** ядро не применяет к `PID 1` действия сигналов по умолчанию. Если у процесса нет собственного обработчика `SIGTERM` (как в лекции 30, через `sigaction`), он этот сигнал проигнорирует. Приложение в контейнере должно обрабатывать `SIGTERM` либо запускаться с флагом `docker run --init` (вставляет лёгкий init-процесс).
> 6. **Различайте `ENTRYPOINT` и `CMD`:** `ENTRYPOINT` задаёт основную программу контейнера, `CMD` — команду или аргументы по умолчанию, которые легко заменить в конце `docker run`. Типичная схема: `ENTRYPOINT ["/app/my_server"]` + `CMD ["--port", "8080"]`. Если указан только `CMD`, замена аргументов в `docker run` заменяет всю команду целиком.

### 3. Файл `.dockerignore`

Он лежит рядом с `Dockerfile` и перечисляет файлы, которые **не** попадут в контекст сборки (то, что передаётся Docker при `COPY . .`). Это ускоряет сборку и не пускает секреты в образ:

```text
.git
.env
*.o
server
client
```

Здесь исключены история Git, файл с секретами, объектные файлы и бинарники, собранные локально (их соберёт сам `Dockerfile`).

## Подглава 31.6: Справочник базовых команд Docker CLI

| Команда | Описание |
| :--- | :--- |
| `docker build -t my_app:v1.0 .` | Сборка образа с тегом `my_app:v1.0` из текущей директории |
| `docker run -d -p 8080:8080 --name app my_app:v1.0` | Запуск контейнера в фоновом режиме (`-d`) с пробросом порта: `-p порт_хоста:порт_контейнера` |
| `docker run -d --memory=256m --cpus=1.5 --name app my_app:v1.0` | Запуск с лимитами ресурсов (cgroups): не более 256 МБ ОЗУ и 1,5 ядра CPU |
| `docker images` | Список локальных образов |
| `docker ps -a` | Список всех контейнеров (активных и остановленных) |
| `docker logs -f app` | Просмотр логов контейнера в реальном времени (как `tail -f`) |
| `docker exec -it app /bin/sh` | Запуск оболочки внутри работающего контейнера (в образах без оболочки, например `scratch`, не сработает) |
| `docker stats` | Мониторинг потребления CPU, RAM и I/O контейнерами в реальном времени |
| `docker stop app` | Остановка: сначала `SIGTERM`, и если процесс не завершился за 10 секунд (по умолчанию) — `SIGKILL` |
| `docker rm app` | Удаление остановленного контейнера |
| `docker system prune -a --volumes` | Удаление остановленных контейнеров, неиспользуемых сетей, **всех неиспользуемых образов**, кэша сборки и неиспользуемых **анонимных** томов |

> ⚠️ **Тома и очистка.** В Docker 23 и новее (API 1.42+) флаг `--volumes` удаляет только неиспользуемые **анонимные** тома (те, что создаются автоматически и не имеют имени). Именованные тома эта команда не трогает: их удаляют отдельно, `docker volume prune --all` (или `docker volume rm имя`). Но будьте осторожны и с этими командами: тома часто хранят данные (например, базы данных), и удалённые тома восстановить нельзя. В старых версиях Docker `--volumes` удалял и именованные тома, поэтому на чужих серверах проверяйте версию (`docker version`).

## Подглава 31.7: Практика на Си: создание собственного контейнера через `clone()` и Linux Namespaces

Ниже представлен пример на C, демонстрирующий, как с помощью системного вызова `clone()` и флагов изоляции `CLONE_NEWPID`, `CLONE_NEWUTS`, `CLONE_NEWNS` создаётся процесс в новых пространствах имён — «скелет» контейнера. Для запуска нужны права root (или `CAP_SYS_ADMIN`).

> ℹ️ Это учебный пример. Настоящий контейнер дополнительно использует `net`/`ipc`/`user` namespaces, ограничения cgroups, смену корневой файловой системы (`pivot_root`) и ограничение привилегий (capabilities, seccomp). Здесь всего этого нет.

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <signal.h>
#include <unistd.h>
#include <sched.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <sys/mount.h>

// Размер стека для дочернего изолированного процесса.
// Выравнивание на 16 байт требуется ABI на многих платформах
#define STACK_SIZE (1024 * 1024)
static char child_stack[STACK_SIZE] __attribute__((aligned(16)));

// Функция, выполняемая внутри изолированного "контейнера"
static int container_main(void *arg) {
    (void)arg;

    printf("=== ВНУТРИ ИЗОЛИРОВАННОГО КОНТЕЙНЕРА ===\n");
    printf("1. PID в новом namespace: %d\n", getpid()); // будет 1

    // Изменяем hostname только внутри нашего UTS namespace.
    // Длину берём через strlen — так она всегда совпадает со строкой
    const char *new_hostname = "my-c-container";
    if (sethostname(new_hostname, strlen(new_hostname)) < 0) {
        perror("Ошибка sethostname");
    } else {
        printf("2. Имя хоста изменено на '%s'\n", new_hostname);
    }

    // Делаем все точки монтирования приватными, чтобы наши изменения
    // в Mount namespace не «протекли» на хост
    if (mount("none", "/", NULL, MS_REC | MS_PRIVATE, NULL) < 0) {
        perror("Ошибка mount (MS_PRIVATE)");
    }

    // Монтируем новую файловую систему proc: без этого утилита ps
    // покажет процессы хоста, а не контейнера
    if (mount("proc", "/proc", "proc", 0, NULL) < 0) {
        perror("Ошибка mount /proc");
    } else {
        printf("3. Процессы, видимые внутри контейнера:\n");
        fflush(stdout); // сбрасываем буфер, чтобы вывод шёл по порядку
        system("ps -e");
    }

    printf("Контейнер завершил выполнение работы.\n\n");
    return 0;
}

int main(void) {
    printf("=== ХОСТОВАЯ СИСТЕМА ===\n");
    printf("1. PID основного процесса на хосте: %d\n", getpid());
    fflush(stdout); // чтобы буфер вывода не продублировался у потомка

    // Запускаем дочерний процесс в новых пространствах имён:
    // CLONE_NEWPID - новое дерево процессов (наш код станет PID 1)
    // CLONE_NEWUTS - собственное имя хоста (hostname)
    // CLONE_NEWNS  - собственная таблица монтирования файловой системы
    // SIGCHLD      - сигнал родителю при завершении потомка (нужен для waitpid)
    int flags = CLONE_NEWPID | CLONE_NEWUTS | CLONE_NEWNS | SIGCHLD;

    // clone принимает указатель на ВЕРШИНУ стека (стек растёт вниз на x86 и ARM)
    pid_t child_pid = clone(container_main, child_stack + STACK_SIZE, flags, NULL);

    if (child_pid < 0) {
        perror("Ошибка вызова clone (требуются права root / CAP_SYS_ADMIN)");
        return 1;
    }

    printf("2. На хосте создан контейнерный процесс с PID: %d\n\n", child_pid);

    // Ожидаем завершения контейнера
    waitpid(child_pid, NULL, 0);

    printf("=== ХОСТОВАЯ СИСТЕМА ===\n");
    printf("3. Контейнер %d завершился. Хост продолжит работу.\n", child_pid);

    return 0;
}
```

### Команда компиляции и запуска:
```bash
gcc -Wall -Wextra -std=c11 container_demo.c -o container_demo && sudo ./container_demo
```
Один и тот же процесс имеет разные PID «снаружи» (на хосте) и «внутри» (в своём namespace) — это и есть изоляция `pid` namespace.

## Подглава 31.8: Чек-лист разработчика при работе с Docker

1. **Запускайте приложения в контейнерах от непривилегированного пользователя (`USER`):** Если злоумышленник взломает приложение, запущенное от `root` внутри контейнера, и найдёт способ выйти из изоляции (например, через уязвимость в ядре), он получит права root на хосте.
2. **Для компилируемых языков используйте Multi-Stage builds:** не отправляйте в продакшен образы с компиляторами `gcc`, `g++` и исходным кодом.
3. **Фиксируйте версии базовых образов:** не используйте тег `latest` (`FROM alpine:latest`). Указывайте конкретные версии (например, `FROM alpine:3.22`) для воспроизводимости сборок. Ещё надёжнее — фиксировать образ по хэшу (`FROM alpine@sha256:...`). Следите за тем, чтобы версия базового образа оставалась поддерживаемой и получала обновления безопасности.
4. **Очищайте кэш пакетов в том же слое `RUN`:** пишите `apt-get update && apt-get install -y --no-install-recommends ... && rm -rf /var/lib/apt/lists/*`, чтобы файлы кэша не остались в слое образа (для Alpine — `apk add --no-cache`).
5. **Используйте `.dockerignore`:** исключайте `.git`, временные файлы и секреты из контекста сборки.

## Подсказки к практическим задачам

* **Подсказка к Задаче 1:**
  1. Каждая инструкция `RUN` создаёт отдельный неизменяемый слой, значит, будет **5 новых слоёв** (поверх слоёв базового образа).
  2. Команда `RUN rm ...` создаёт **ещё один новый слой**, в котором файлы лишь помечаются как удалённые (whiteout-метки). Нижние слои неизменяемы, поэтому файлы продолжают физически храниться в них, входят в образ и скачиваются вместе с ним. Чтобы кэш не попал в образ, установку и очистку нужно делать **в одной инструкции** `RUN` через `&&`. Заодно пять повторных `apt-get update` не нужны: достаточно одного в начале того же `RUN`.

* **Подсказка к Задаче 2:**
  Shell-форма `CMD ./my_server` запускает `/bin/sh -c ./my_server`. Оболочка становится `PID 1`, получает `SIGTERM` от `docker stop`, но, как правило, не передаёт его серверу, и через 10 секунд Docker убивает контейнер сигналом `SIGKILL`.
  Исправление: JSON-форма (exec-форма), например `CMD ["/app/my_server"]` или `ENTRYPOINT ["/app/my_server"]`. Теперь сервер сам становится `PID 1`.
  **Важное дополнение:** для `PID 1` ядро не применяет поведение по умолчанию, поэтому сервер должен сам обрабатывать `SIGTERM` (через `sigaction`, как в лекции 30). Иначе сигнал будет проигнорирован и задержка в 10 секунд останется. Альтернатива — запуск с `docker run --init`. Обратите внимание: сервер TCP-чата из Лекции 28.1 такого обработчика не имеет (там игнорируется только `SIGPIPE`), поэтому в контейнере он тоже остановился бы только по `SIGKILL`. Добавьте в него флаг `g_running` и `sigaction` по образцу Лекции 30.

* **Подсказка к Задаче 3:**
  Используйте двухэтапную сборку (Multi-Stage Build):
  ```dockerfile
  FROM alpine:3.22 AS builder
  RUN apk add --no-cache gcc musl-dev make
  WORKDIR /src
  COPY . .
  RUN make CFLAGS="-O2 -static"

  FROM alpine:3.22
  WORKDIR /app
  COPY --from=builder /src/server /app/server
  USER nobody
  ENTRYPOINT ["/app/server"]
  ```
  Статическая сборка (`-static`) позволяет при желании взять в качестве финального образа пустой `scratch`: тогда образ будет содержать только ваш бинарник. В `scratch` нет ни оболочки, ни `adduser`, поэтому пользователя задают числом, например `USER 65534`.
