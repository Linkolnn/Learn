# Лекция 16: Алгоритмы поиска и двоичный поиск (Binary Search)

В предыдущей лекции мы изучили нотацию **Big O** и научились оценивать скорость работы программ при росте объёма данных `n`. Теперь мы переходим к практическому применению этих знаний.

Одной из самых частых и фундаментальных задач в программировании является **поиск информации**: найти пользователя в базе данных по ID, проверить наличие товара на складе, найти нужную строчку в файле или найти элемент в массиве.

В этой лекции мы разберём два основных подхода к поиску: простой универсальный **линейный поиск `O(n)`** и очень быстрый **двоичный поиск `O(log n)`**. Отдельно разберём типичную ловушку, из-за которой «правильный» по учебнику код ломается на больших массивах: переполнение при вычислении середины (`mid`).

---

## 💡 Глоссарий ключевых терминов лекции

> 📌 **1. Поиск (Search)**
> * **Что это:** Задача найти в наборе данных элемент, равный искомому значению (`target`), и вернуть его позицию (индекс) либо сообщить, что такого элемента нет.

> 📌 **2. Линейный поиск (Linear Search)**
> * **Что это:** Последовательная проверка элементов один за другим, пока не найдём нужный или не дойдём до конца. Работает на любых данных.

> 📌 **3. Двоичный (бинарный) поиск (Binary Search)**
> * **Что это:** Поиск в **отсортированном** массиве, при котором на каждом шаге проверяется средний элемент, а половина оставшихся элементов отбрасывается.

> 📌 **4. Логарифм `log n`**
> * **Что это:** В этой лекции — «сколько раз число `n` можно разделить пополам, пока не останется 1». Например, `log₂ 8 = 3` (8 → 4 → 2 → 1). В нотации Big O основание логарифма не пишут: `O(log n)`.

> 📌 **5. Целочисленное переполнение (Integer Overflow)**
> * **Что это:** Ситуация, когда результат арифметической операции не помещается в тип переменной. Для знаковых типов (`int`) в языке Си поведение при этом **не определено** (Undefined Behavior): на практике чаще всего получается отрицательное число, но стандарт ничего не гарантирует.

## Подглава 16.1: Линейный поиск (Linear Search)

### 1. Суть алгоритма
**Линейный поиск** — это самый простой и интуитивный способ найти элемент.

Представьте, что перед вами лежит стопка из 100 нерассортированных бумажных карточек с фамилиями. Чтобы найти нужную фамилию, у вас нет другого выхода, кроме как брать карточки по одной сверху вниз и проверять каждую.

### 2. Реализация на языке Си

```c
#include <stdio.h>
#include <stddef.h>

// Функция линейного поиска
// Возвращает индекс найденного элемента или -1, если элемент не найден
int linear_search(const int *arr, size_t size, int target) {
    for (size_t i = 0; i < size; i++) {
        if (arr[i] == target) {
            return (int)i; // Элемент найден! Возвращаем его индекс
        }
    }
    return -1; // Прошли весь массив, элемент не найден
}
```

Тип `size_t` — беззнаковый целый тип для размеров и индексов (определён в `<stddef.h>`). Значение `-1` как «не найдено» удобно, потому что корректный индекс всегда `>= 0`.

### 3. Оценка сложности линейного поиска
* **Лучший случай: `O(1)`** — нужный элемент оказался на самом первом месте (`arr[0]`). (Иногда лучший случай записывают нижней границей Ω(1).)
* **Худший случай: `O(n)`** — нужный элемент находится в самом конце массива или вовсе отсутствует. Программе приходится сделать ровно `n` проверок.
* **Средний случай: `O(n)`** — если искомый элемент равновероятно лежит в любом месте, в среднем понадобится около `n/2` проверок; константу `1/2` Big O отбрасывает.
* **Пространственная сложность (память): `O(1)`** — не требуется никакой дополнительной памяти, кроме нескольких переменных.

> ℹ️ «Лучший/худший случай» — это **сценарии** входных данных, а `O`, `Ω` — **способы записи** оценки. Когда в курсе говорят «сложность алгоритма `O(n)`», по умолчанию имеют в виду худший случай.

### 4. Главное преимущество и недостаток
* **Плюс:** Работает на **абсолютно любых** данных (неважно, отсортирован массив или элементы перемешаны хаотично), а код — минимальный.
* **Минус:** Очень медленный на больших объёмах. Если в массиве **1 000 000 000 элементов** (1 миллиард), в худшем случае придётся сделать 1 миллиард сравнений.

## Подглава 16.2: Двоичный поиск (Binary Search)

### 1. Главное условие
> **⚠️ КРИТИЧЕСКИ ВАЖНОЕ ПРАВИЛО:**
> Двоичный поиск работает **ТОЛЬКО на предварительно отсортированных данных** (в этой лекции — по возрастанию)!
> Если массив не отсортирован, результат будет неверным: алгоритм может не найти элемент, который в массиве есть.

Есть и второе условие: нужен **произвольный доступ** к элементам по индексу за `O(1)`, как в массиве. В связном списке (лекция 21) до середины можно добраться только пройдя по узлам, поэтому двоичный поиск там не даёт выигрыша.

### 2. Идея алгоритма: игра «Угадай число»
Представьте, что ваш друг загадал число от 1 до 100, а вы пытаетесь его угадать. За каждый ответ друг говорит только: «Моё число больше» или «Моё число меньше».

* **Плохая стратегия (линейная):** Спрашивать «Это 1? Это 2? Это 3?». В худшем случае потребуется 100 попыток.
* **Умная стратегия (бинарная):** Спросить «Это 50?».
  * Если друг говорит «Моё число больше», вы сразу отбрасываете все числа от 1 до 50! Остался диапазон 51–100.
  * Следующим шагом вы берёте середину оставшегося отрезка: «Это 75?».
  * За каждый ответ область поиска **сокращается примерно в 2 раза**.

Число от 1 до 100 угадывается максимум за **7 попыток** (`2^7 = 128 ≥ 100`), а число от 1 до 1 000 000 — максимум за **20 попыток** (`2^20 = 1 048 576 ≥ 1 000 000`). Это и есть логарифм: `log₂ 100 ≈ 6,6`, `log₂ 1 000 000 ≈ 19,9`.

---

### 3. Пошаговая механика в коде
Для реализации двоичного поиска в отсортированном массиве используются три индекса:
1. `left` — левая граница текущего диапазона поиска (изначально `0`).
2. `right` — правая граница текущего диапазона поиска, **включительно** (изначально `size - 1`).
3. `mid` — индекс элемента посередине между `left` и `right`.

На каждом шаге цикла:
1. Находим середину: `mid = left + (right - left) / 2`.
2. Сравниваем значение `arr[mid]` с искомым `target`:
   * Если `arr[mid] == target` — элемент найден, возвращаем `mid`.
   * Если `arr[mid] < target` — искомое число находится **правее**. Сдвигаем левую границу: `left = mid + 1`.
   * Если `arr[mid] > target` — искомое число находится **левее**. Сдвигаем правую границу: `right = mid - 1`.
3. Повторяем цикл, пока `left <= right`. Если `left` превысил `right`, диапазон пуст, значит элемента в массиве нет.

**Разбор на примере.** Массив `[2, 5, 8, 12, 16, 23, 38, 56, 72, 91]` (индексы 0–9), ищем `target = 23`:

| Шаг | `left` | `right` | `mid` | `arr[mid]` | Решение |
| :-: | :-: | :-: | :-: | :-: | :--- |
| 1 | 0 | 9 | 4 | 16 | `16 < 23` → ищем правее: `left = 5` |
| 2 | 5 | 9 | 7 | 56 | `56 > 23` → ищем левее: `right = 6` |
| 3 | 5 | 6 | 5 | 23 | Найдено! Возвращаем индекс `5` |

Всего 3 сравнения вместо 6, которые потребовал бы линейный поиск.

### 4. Подводный камень: переполнение типов при расчёте `mid`

Во многих учебниках вы можете увидеть такую формулу расчёта середины:
```c
int mid = (left + right) / 2; // ❌ ОПАСНО!
```
**В чём баг?** Если индексы большие, сумма `left + right` может превысить максимум типа `int` (`INT_MAX = 2 147 483 647`) и уйти в **целочисленное переполнение**. Для `int` это неопределённое поведение, на практике чаще всего получается отрицательное число, и программа обращается к памяти за пределами массива. Для этого нужны индексы порядка миллиарда: например, `left` и `right` оба больше ~1,07 млрд (`2^30`), то есть массив больше 1 млрд элементов. Этот баг много лет жил в стандартных библиотеках известных языков (в том числе в Java) и был обнаружен только тогда, когда массивы стали достаточно большими.

**Правильная формула:**
```c
size_t mid = left + (right - left) / 2; // ✅ Безопасно от переполнения
```
Почему это работает: `right - left` — это длина диапазона, она всегда помещается в тип, а `left + (половина длины)` не превосходит `right`, то есть никогда не выходит за допустимые индексы.

> ℹ️ В 64-битной программе с `size_t` (8 байт) переполнить `left + right` практически невозможно, но формулу с вычитанием всё равно нужно писать: она работает и на 32-битных системах, и при смене типов.

### 5. Реализация двоичного поиска на Си

```c
#include <stdio.h>
#include <stddef.h>

// Итеративная реализация двоичного поиска.
// Массив arr ДОЛЖЕН быть отсортирован по возрастанию.
// Возвращает индекс найденного элемента или -1, если элемента нет.
// (Тип int ограничивает возвращаемый индекс значением INT_MAX, для учебных задач этого достаточно.)
int binary_search(const int *arr, size_t size, int target) {
    if (size == 0) return -1; // Пустой массив: без этой проверки size - 1 даст огромное число

    size_t left = 0;
    size_t right = size - 1;

    while (left <= right) {
        // Безопасный расчёт среднего индекса
        size_t mid = left + (right - left) / 2;

        if (arr[mid] == target) {
            return (int)mid; // Элемент найден
        }

        if (arr[mid] < target) {
            left = mid + 1; // Ищем в правой половине
        } else {
            // size_t — беззнаковый тип: 0 - 1 даст не -1, а огромное число (SIZE_MAX).
            // Поэтому, если mid == 0, левее искать уже нечего.
            if (mid == 0) break;
            right = mid - 1; // Ищем в левой половине
        }
    }

    return -1; // Элемент не найден
}

int main(void) {
    int arr[] = {2, 5, 8, 12, 16, 23, 38, 56, 72, 91};
    size_t n = sizeof(arr) / sizeof(arr[0]);

    printf("%d\n", binary_search(arr, n, 23)); // 5
    printf("%d\n", binary_search(arr, n, 7));  // -1
    printf("%d\n", binary_search(arr, n, 1));  // -1 (меньше всех элементов)
    return 0;
}
```

Сборка и запуск: `gcc -Wall -Wextra -o bs main.c && ./bs`.

> 💡 Если использовать **полуоткрытый** диапазон `[left, right)` (правая граница не включается, начальное `right = size`, условие цикла `left < right`, сдвиг `right = mid`), то проверка `mid == 0` не нужна. Этот вариант очень популярен в задачах про границы (`lower_bound`) и пригодится в практических задачах ниже.

### 6. Оценка сложности двоичного поиска
* **Лучший случай: `O(1)`** — искомый элемент оказался ровно посередине.
* **Худший случай: `O(log n)`** — на каждом шаге диапазон уменьшается вдвое: `n → n/2 → n/4 → … → 1`. Число шагов — это то, сколько раз можно разделить `n` пополам, то есть около `log₂ n`.
* **Пространственная сложность: `O(1)`** — в итеративной версии хранятся только `left`, `right` и `mid`.

### 7. Готовая функция в стандартной библиотеке: `bsearch`

В Си уже есть двоичный поиск в `<stdlib.h>`. Он работает с массивом любого типа, поэтому принимает **указатель на функцию сравнения** (тема лекции про указатели на функции):

```c
#include <stdio.h>
#include <stdlib.h>

// Функция сравнения: отрицательное число, 0 или положительное
static int cmp_int(const void *a, const void *b) {
    int x = *(const int *)a;
    int y = *(const int *)b;
    return (x > y) - (x < y); // безопасно: не используем x - y, который может переполниться
}

int main(void) {
    int arr[] = {2, 5, 8, 12, 16, 23, 38, 56, 72, 91};
    size_t n = sizeof(arr) / sizeof(arr[0]);
    int target = 56;

    int *p = bsearch(&target, arr, n, sizeof(arr[0]), cmp_int);
    if (p != NULL) {
        printf("Найдено, индекс %td\n", p - arr); // 7
    } else {
        printf("Не найдено\n");
    }
    return 0;
}
```

`bsearch` возвращает указатель на найденный элемент либо `NULL`. Для обучения мы пишем свой вариант вручную, а в реальных проектах разумно использовать проверенные библиотечные функции.

## Подглава 16.3: Сравнение линейного и двоичного поиска

Давайте сравним максимальное количество шагов (худший случай), требуемое обоим алгоритмам в зависимости от размера массива `n`:

| Размер массива `n` | Линейный поиск `O(n)` | Двоичный поиск `O(log n)` | Выигрыш по числу шагов |
| :--- | :--- | :--- | :--- |
| **10** элементов | 10 шагов | 4 шага | примерно в 2,5 раза |
| **1 000** элементов | 1 000 шагов | 10 шагов | в 100 раз |
| **1 000 000** (1 млн) | 1 000 000 шагов | 20 шагов | в 50 000 раз |
| **1 000 000 000** (1 млрд) | 1 000 000 000 шагов | 30 шагов | примерно в 33 млн раз |

Это сравнение **числа шагов**. Реальное время зависит ещё от процессора и кэша: на совсем маленьких массивах (десятки элементов) простой линейный проход может быть не медленнее двоичного поиска, потому что он последовательно читает память, а двоичный «прыгает» по ней. Выигрыш двоичного поиска становится решающим на больших `n`.

### Когда что использовать?
1. **Данные НЕ отсортированы и запрос всего один:** используйте линейный поиск `O(n)`. Сортировка массива перед одним-единственным поиском займёт больше времени (`O(n log n)`, об алгоритмах сортировки — в лекциях 17 и 19), чем сам линейный проход.
2. **Данные отсортированы заранее или поисковых запросов много:** один раз отсортируйте массив, а затем выполняйте множество поисков двоичным поиском `O(log n)`.
3. **Данные часто меняются:** вставка элемента в отсортированный массив стоит `O(n)` (нужно сдвинуть «хвост»), поэтому для динамических данных обычно используют другие структуры: деревья поиска (лекция 22) и хеш-таблицы (в курсе — в лекции 60 на примере `Map`).

## Практические задачи к Лекции 16

### Задача 1: Поиск первой и последней позиции элемента в отсортированном массиве (LeetCode 34)

В отсортированном массиве могут встречаться дубликаты (повторяющиеся числа). Стандартный `binary_search` возвращает *любой* найденный индекс.

Напишите программу на Си с двумя функциями:
1. `int find_first_position(const int *arr, size_t size, int target)` — возвращает индекс **самого первого (левого)** вхождения числа.
2. `int find_last_position(const int *arr, size_t size, int target)` — возвращает индекс **самого последнего (правого)** вхождения числа.

Если числа в массиве нет, обе функции возвращают `-1`. Обе функции должны иметь временную сложность **`O(log n)`**.

*Пример:*
Массив: `[1, 2, 4, 4, 4, 5, 7, 9]`, искомое число: `4`.
Результат: первое вхождение = индекс `2`, последнее вхождение = индекс `4`.

### Задача 2: Поиск места для вставки (Search Insert Position — LeetCode 35)

Дан отсортированный массив уникальных целых чисел и значение `target`.

Напишите функцию `int search_insert(const int *arr, size_t size, int target)` со сложностью **`O(log n)`**, которая:
* Возвращает индекс элемента, если он найден в массиве.
* Если элемент не найден — возвращает **индекс, на который его следует вставить**, чтобы массив остался отсортированным.

*Пример 1:* Массив `[1, 3, 5, 6]`, target `5` ⇒ Ответ: `2` (элемент найден на индексе 2).
*Пример 2:* Массив `[1, 3, 5, 6]`, target `2` ⇒ Ответ: `1` (число 2 должно встать между 1 и 3).
*Пример 3:* Массив `[1, 3, 5, 6]`, target `7` ⇒ Ответ: `4` (число 7 должно встать в конец).
*Пример 4:* Массив `[1, 3, 5, 6]`, target `0` ⇒ Ответ: `0` (число 0 должно встать в начало).

Не забудьте про пустой массив: для него ответ `0`.

### Задача 3: Экспериментальное сравнение времени работы (линейный vs бинарный)

Напишите программу на Си, которая:
1. Создаёт отсортированный динамический массив на **10 000 000 элементов** (`int`), например `arr[i] = 2 * i` (тогда примерно половина случайных искомых значений в массиве будет отсутствовать).
2. Генерирует **1 000 случайных чисел** и ищет каждое из них с помощью `linear_search`. Замерьте общее время работы в миллисекундах через `<time.h>`.
3. Ищет с помощью `binary_search` **1 000 000** случайных чисел и замеряет время работы.
4. Выведите на экран общее время каждого алгоритма, **среднее время одного поиска** и их соотношение.

Почему именно такие количества запросов? Линейный поиск по 10 млн элементов занимает в среднем несколько миллисекунд, поэтому 100 000 таких поисков шли бы около десяти минут. Двоичный поиск настолько быстрее, что для заметного времени ему нужно на порядки больше запросов. Поэтому сравнивать нужно время **одного** поиска, а не общее.

## Подсказки к задачам

* **Подсказка к Задаче 1:** В стандартном бинарном поиске, когда вы находите `arr[mid] == target`, вы сразу делаете `return mid`. Чтобы найти *первое* вхождение, не останавливайтесь! Сохраните `mid` в переменную-результат `ans = mid` и продолжайте поиск в **левой половине** (`right = mid - 1`). Для последнего вхождения — сохраните результат и продолжайте поиск в **правой половине** (`left = mid + 1`). Не забудьте про защиту от `mid == 0` при `size_t`.
* **Подсказка к Задаче 2:** Проследите за поведением индекса `left` во время работы итеративного бинарного поиска. Когда цикл `while (left <= right)` завершается без находки, где именно оказывается значение переменной `left`? (Потренируйтесь на примерах 2–4 вручную, как мы сделали в таблице в 16.2.) Если вы выбрали полуоткрытый диапазон `[left, right)`, ответ — тоже `left`.
* **Подсказка к Задаче 3:**
  * Для замера времени используйте `<time.h>`:
    ```c
    clock_t start = clock();
    // Выполнение серии поисков
    clock_t end = clock();
    double time_spent = (double)(end - start) * 1000.0 / CLOCKS_PER_SEC;
    ```
    (`clock()` измеряет процессорное время программы, для учебного эксперимента этого достаточно.)
  * Случайные числа берите в диапазоне `0 … 2*N - 1`: `rand() % (2 * N)`. На Linux (gcc) `RAND_MAX` равен 2 147 483 647; на Windows он всего 32 767, и там придётся склеивать два вызова `rand()`.
  * Накапливайте результаты поисков (например, суммируйте найденные индексы) и выводите сумму на экран. Иначе компилятор с оптимизацией (`-O2`) может заметить, что результат поиска нигде не используется, и вообще убрать цикл, а вы получите «время 0 мс».
  * Собирайте с оптимизацией: `gcc -O2 -Wall -Wextra -o bench main.c`.
