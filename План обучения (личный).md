Настройка компилятора C (Си) на Arch Linux

В Arch Linux компилятор `gcc` и все необходимые утилиты для сборки (включая `make`) поставляются в одном мета-пакете.

1. Откройте ваш терминал и обновите систему, попутно установив группу пакетов `base-devel`:
    
    bash
    
    ```
   sudo pacman -Syu base-devel
    ```
    
    Используйте код с осторожностью.
    
2. Проверьте успешность установки, запросив версию компилятора:
    
    bash
    
    ```
    gcc --version
    ```
    
    Используйте код с осторожностью.
    
3. Для проверки создайте файл `test.c`:
    
    c
    
    ```
    #include <stdio.h>
    int main() {
        printf("Arch Linux + C готовы!\n");
        return 0;
    }
    ```
    
    Используйте код с осторожностью.
    
4. Скомпилируйте и запустите его:
    
    bash
    
    ```
    gcc test.c -o test && ./test
    ```
    
    Используйте код с осторожностью.

## Неделя 2: Укрощение циклов (`for`, `while`) и физика массивов

- **Теория сетей:**
    - Устройство IP-адреса (IPv4). Что такое сетевая часть и хостовая часть. Маски подсетей, CIDR-нотация (что значит `/24` или `/16`). Разница между публичными (белыми) и приватными (серыми: `10.x.x.x`, `192.168.x.x`) адресами. Как технология NAT позволяет вашему домашнему роутеру раздавать интернет на все устройства за одним белым IP. Протокол DNS: иерархия серверов (корневые, TLD, авторитетные), кэширование записей.
- **Теория Си:**
    - Чтение главы 3 книги Фило (Массивы, Стеки, Очереди).
    - Циклы `for`, `while`, `do-while`. Итераторы, шаг цикла, условия выхода.
    - Что такое статический массив в Си. Вы должны осознать, что массив в Си — это непрерывный кусок памяти фиксированной длины. Компьютер на низком уровне не знает длину массива, он знает только адрес первого элемента. Формула поиска элемента: `Адрес = Начало + Индекс * Размер_Типа`. Именно поэтому доступ к элементу по индексу равен O(1).
- **Источники для изучения:**
    - _Книга:_ Э. Таненбаум, «Компьютерные сети» — Глава 5 (Раздел 5.6 «Сетевой уровень в интернете» — подразделы IP, CIDR, NAT) и Глава 7 (Раздел 7.1 «DNS»).
    - _Документация:_ Что такое IP-адрес — MDN Web Docs.
    - _Интерактивный учебник:_ Циклы и Массивы в Си на METANIT (Глава 3).
- **Практика:**
    1. **Работа с сетью:** В терминале Arch Linux выполните команды `nslookup google.com` и `traceroute google.com` (если утилиты нет, поставьте: `sudo pacman -S bind-tools iputils`). Разберитесь, сколько маршрутизаторов (хопов) проходит ваш запрос от квартиры до дата-центра.
    2. **Задача на Си «Поиск без читов»:** Создайте статический массив из 20 случайных чисел. Напишите **один цикл `for`**, который находит в этом массиве _второе по величине_ число за один единственный проход. Использовать сортировку или вложенные циклы (цикл в цикле) запрещено. Вам нужно жонглировать переменными `max1` и `max2` на каждой итерации.
    3. **Задача на Си «Разворот куска памяти»:** Напишите программу, которая разворачивает массив задом наперед (первый элемент становится последним, второй — предпоследним). Условие: нельзя создавать второй (временный) массив. Цикл должен выполнить ровно N/2 итераций, меняя элементы местами с начала и конца с помощью одной временной переменной.

## Неделя 3: Указатели (Pointers) и ручное управление памятью (`malloc` / `free`)

- **Теория сетей:**
    - Как роутеры пересылают пакеты. Таблицы маршрутизации. Кратко о протоколах OSPF (внутримасштабный) и BGP (глобальный протокол интернета, связывающий провайдеров между собой).
- **Теория Си:**
    - **Указатели**. Понимание того, что указатель — это просто переменная, которая хранит число (адрес ячейки памяти). Оператор взятия адреса `&` и оператор разыменования `*` (переход по адресу).
    - Анатомия памяти процесса: Стек (Stack) — быстрая автоматическая память для локальных переменных, и Куча (Heap) — большая динамическая память.
    - Функции `malloc()` и `calloc()` для ручного выделения байт в куче. Функция `free()` для очистки. Ошибка "Segmentation Fault" (обращение к невыделенной или чужой памяти) и утечки памяти (Memory Leaks).
- **Источники для изучения:**
    - _Видео:_ Гарвардский курс CS50 — Лекция 5 «Управление памятью, malloc» (смотреть обязательно, там наглядно на доске показывают, как указатели двигаются по ячейкам).
    - _Интерактивный учебник:_ Указатели и управление памятью в Си на METANIT (Главы 4 и 5).
- **Практика:**
    1. **Задача на Си «Ручной swap»:** Напишите функцию `void swap(int *a, int *b)`. Внутри функции через указатели поменяйте значения двух переменных, объявленных в функции `main`. Поймите, почему без указателей в Си невозможно изменить внешнюю переменную внутри функции (передача по значению vs передача по ссылке).
    2. **Задача на Си «Динамическая строка»:** Запросите у пользователя через терминал число N. С помощью `malloc` выделите в куче массив `char` размером N байт. Считайте туда строку от пользователя. Напишите цикл, который заменяет все пробелы в этой строке на нижнее подчеркивание `_`. Выведите результат в консоль. В конце программы вызовите `free()`.

## Неделя 5: Транспортный уровень (TCP/UDP) под микроскопом

- **Теория сетей:**
    - Чтение глав 1 и 6 книги Таненбаума (Раздел 6.4 «Протокол UDP», раздел 6.5 «Протокол TCP»).
    - Задачи транспортного уровня. Понятие сетевого порта и сокета как конечной точки соединения.
    - Глубокий разбор **TCP (Transmission Control Protocol)**: почему он гарантирует доставку? Архитектура трехэтапного рукопожатия (`SYN` ➡️ `SYN-ACK` ➡️ `ACK`). Контроль перегрузок (алгоритмы Slow Start и Congestion Avoidance), механизм скользящего окна (Sliding Window) [1].
    - Разбор **UDP (User Datagram Protocol)**: почему он быстрый, но ненадежный [1]. Где он применяется в реальном вебе (видеопотоки, WebRTC, HTTP/3).
- **Теория безопасности:**
    - Сетевые уязвимости транспортного уровня. Что такое **SYN Flood** атака (разновидность DoS/DDoS), когда хакер заваливает сервер SYN-пакетами, заставляя его бесконечно ждать ответа и расходовать память.
    - Что такое **Port Scanning** (сканирование портов) — как злоумышленники с помощью утилит вроде `nmap` ищут открытые и незащищенные службы в вашей системе.
- **Источники для изучения:**
    - _Видео:_ Плейлист «Компьютерные сети» А. Созыкина — Смотреть видео про транспортный уровень, порты, UDP и TCP.
    - _Статья:_ [Анатомия TCP-соединения — Хабр](https://habr.com/ru/articles/483202/) (наглядный разбор флагов и фаз жизни соединения).
    - _Статья:_ Как работает SYN Flood атака и защита от нее — Cloudflare (профессиональный разбор концепта).
- **Практика:**
    1. **Работа с Wireshark:** Запустите Wireshark в Arch Linux. Начните запись трафика. Откройте любой терминал и выполните подключение по протоколу SSH или сделайте curl-запрос. Найдите в Wireshark самую первую цепочку пакетов между вашим IP и удаленным сервером. Разверните заголовки Transmission Control Protocol и найдите флаги `Syn` и `Ack`. Убедитесь, что соединение устанавливается ровно за 3 шага.
    2. **Исследование сетевых портов в Arch Linux:** С помощью утилиты `ss` (замена устаревшего `netstat`) изучите, какие порты сейчас слушают процессы в вашей системе. Выполните команду `ss -tulpn` и разберите, какие приложения работают по TCP, а какие по UDP.

## Неделя 6: Протоколы HTTP/HTTPS и анатомия браузерного запроса

- **Теория сетей:**
    - Чтение главы 7 книги Таненбаума (Раздел 7.3 «Веб-технологии», подраздел «Протокол HTTP»).
    - Структура текстового протокола HTTP/1.1: Стартовая строка (Метод, URL, Версия), Заголовки (Headers: `Host`, `User-Agent`, `Content-Type`, `Cookie`), Тело запроса (Body). Структура HTTP-ответа и семантика статус-кодов (2xx, 3xx, 4xx, 5xx).
    - Эволюция протокола: ограничения HTTP/1.1 (блокировка начала очереди — Head-of-Line blocking), мультиплексирование в HTTP/2, переход на транспортный протокол QUIC (поверх UDP) в HTTP/3.
    - Как работает HTTPS: основы криптографии, асимметричное шифрование (обмен ключами через RSA/Diffie-Hellman), симметричное шифрование сессии, роль SSL/TLS сертификатов.
- **Теория безопасности:**
	- Что такое атака **MITM (Man-in-the-Middle — Человек посередине)**. Почему передавать пароли (например, из формы авторизации вашего ToDo-листа) по обычному протоколу HTTP смертельно опасно (любой провайдер или владелец публичного Wi-Fi видит ваш пароль в чистом текстовом виде).
	- Глубокий разбор **HTTPS**: как симметричное и асимметричное шифрование (TLS-рукопожатие) полностью защищают тело запроса и заголовки от перехвата и подмены (тампер-атак).
- **Источники для изучения:**
    - _Документация:_ Обзор протокола HTTP — MDN Web Docs (обязательно к прочтению).
    - _Статья:_ Как работает HTTPS — Хабр (простым языком про ключи, сертификаты и рукопожатие).
    - _Статья:_ Что такое атака «человек посередине» (MitM)? — Касперский.
- **Практика:**
    1. **Работа с утилитой curl:** Откройте терминал Arch Linux и отправьте ручной запрос к тестовому API с флагом подробного вывода: `curl -v https://typicode.com`.
    2. Разберите вывод по строчкам: найдите строки, начинающиеся с `>`, — это то, что ваш компьютер отправил в сеть (HTTP Request). Найдите строки, начинающиеся с `<`, — это то, что вернул сервер (HTTP Response). Найдите статус-код и заголовки `Content-Type` и `Content-Length`.
    3. **Эксперимент с перехватом трафика:** Откройте Wireshark. Попробуйте отправить запрос по незашифрованному протоколу HTTP (например, `curl http://httpbin.org`). Найдите этот пакет в Wireshark и убедитесь, что вы можете прочитать весь URL и заголовки. Затем сделайте то же самое с HTTPS (`https://...`) и убедитесь, что в Wireshark вместо данных виден только нечитаемый зашифрованный поток (TLS Application Data).

## Неделя 7: Контейнеризация с нуля (Установка и база Docker)

- **Теория инфраструктуры:**
    - Проблема «На моей машине работает, а на сервере падает». Что такое контейнеризация?
    - Принципиальное отличие Docker от виртуальных машин: виртуальные машины эмулируют аппаратное обеспечение (железо) и запускают полноценную гостевую ОС, а Docker изолирует процессы на уровне единого ядра Linux с помощью механизмов `namespaces` и `cgroups`.
    - Основные сущности: Image (Образ — неизменяемый слепок файловой системы), Container (Контейнер — запущенный изолированный процесс), Dockerfile (инструкция по сборке образа). Слойность образов и кэширование сборки.
    - Управление постоянными данными (Volumes) и сетевое взаимодействие контейнеров (Networks).
- **Теория безопасности (Docker Hardening):**
    - Почему запускать процессы внутри контейнера от имени пользователя `root` — это огромный риск (при уязвимости «побег из контейнера» злоумышленник получает root-права на вашем реальном хосте Arch Linux). Инструкция `USER` в Dockerfile.
    - Уязвимости базовых образов: почему образы вроде `ubuntu:latest` весят много и содержат сотни старых уязвимостей в системных библиотеках, и почему использование ультра-легковесных образов (например, `node:alpine` или `python:alpine`) существенно снижает площадь атаки.
    - Запрет жесткого прописывания (hardcode) паролей баз данных внутри файлов Dockerfile — использование переменных окружения (`.env` файлов, добавленных в `.gitignore`).
- **Источники для изучения:**
    - _Официальный гайд:_ Docker Curriculum (лучшее практическое руководство для старта на английском).
    - _Статья:_ Docker для новичков — Хабр.
    - _Официальный гайд:_ Docker Security Best Practices (главный стандарт настройки контейнеров).

## Неделя 8: Оркестрация с Docker Compose и настройка веб-сервера Nginx

- **Теория инфраструктуры:**
    - Зачем нужен **Docker Compose**? Декларативное описание многоконтейнерных приложений в формате YAML.
    - Что такое веб-сервер **Nginx**? Его событийно-ориентированная, асинхронная архитектура (в отличие от старого Apache, создающего отдельный поток на каждый запрос).
    - Роли Nginx в веб-разработке: 1) Быстрая раздача статических файлов (HTML/CSS/JS фронтенда), 2) **Reverse Proxy (Обратный прокси)** — защита бэкенда, прием трафика на стандартном 80/443 порту и перенаправление во внутреннюю сеть, 3) Балансировка нагрузки.
- **Теория безопасности (Nginx Security):**
	- Зачем прятать бэкенд за Reverse Proxy: бэкенд-приложение (на Node.js или Python) не должно смотреть напрямую в интернет, так как оно не умеет эффективно отражать сетевые атаки и быстро обрабатывать тысячи «медленных» соединений (Slowloris атаки). Nginx принимает удар на себя.
	- Что такое **Information Disclosure** (раскрытие информации) — почему нужно отключать вывод версии Nginx в HTTP-заголовках ответа (`server_tokens off`), чтобы хакеры не знали, под какую конкретно версию искать готовый эксплоит.
	- Настройка HTTP-заголовков безопасности для защиты фронтенда: `X-Frame-Options` (защита от Clickjacking — кражи кликов через невидимые iframe-слои) и `X-Content-Type-Options: nosniff` (запрет браузеру угадывать тип файлов, защищает от выполнения JS-кода, замаскированного под картинку).
- **Источники для изучения:**
    - _Документация:_ [Официальное руководство Docker Compose](https://docs.docker.com/compose/) и [Nginx Beginner's Guide](https://nginx.org/en/docs/beginners_guide.html).
    - _Статья:_ Nginx для начинающих — Хабр.
    - _Гайд:_ [Nginx Security Tuning — Руководство OWASP](https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/01-Information_Gathering/02-Fingerprint_Web_Server).
	 - _Инструмент проверки:_ [Security Headers Scanner](https://securityheaders.com/) (сервис для проверки заголовков безопасности сайтов).
- **Практика:**
    1. **Пишем Docker Compose файл:** Создайте пустую папку. Напишите в ней файл `docker-compose.yml`, который одновременно будет запускать контейнер базы данных PostgreSQL и веб-интерфейс администратора базы данных pgAdmin. Настройте их внутреннюю сеть, чтобы pgAdmin мог подключиться к PostgreSQL по имени контейнера. Запустите одной командой `docker compose up -d`.
    2. **Конфигурация Nginx Reverse Proxy:** Создайте простейший файл конфигурации `nginx.conf`. Настройте блок `server {}` так, чтобы Nginx слушал порт `80`, и при обращении на `http://localhost/` отдавал заглушку, а при обращении на `http://localhost/api/` — прозрачно перенаправлял (проксировал) запрос через директиву `proxy_pass` на порт вашего будущего бэкенд-приложения. Запустите этот Nginx в Docker-контейнере, подкинув ему ваш файл конфигурации через раздел `volumes`.
    3. Напишите файл `docker-compose.yml`, который поднимает связку: контейнер базы данных PostgreSQL и контейнер веб-сервера Nginx.
    4. Напишите безопасный файл конфигурации `nginx.conf`. В блоке `http {}` или `server {}` обязательно пропишите директиву `server_tokens off;`. Inside блока `server {}` настройте проксирование (`proxy_pass`) и руками добавьте заголовки безопасности через команду `add_header`:
        
        nginx
        
        ```
        add_header X-Frame-Options "DENY" always;
        add_header X-Content-Type-Options "nosniff" always;
        ```
        
        Используйте код с осторожностью.
        
    5. Запустите сборку через `docker compose up -d`. Сделайте запрос к вашему локальному Nginx через `curl -I http://localhost` (запрос только заголовков) и убедитесь, что в ответе появились добавленные вами защитные заголовки, а строка `Server:` содержит только слово `nginx` без указания точной версии.

## Неделя 9: Архитектура на Vanilla JS (Модули, Компонентный подход и SPA)

## Неделя 10: Переход на TypeScript (Строгая типизация, Интерфейсы и Контракты)

- **Теория фронтенда:**
    - Что такое **TypeScript (TS)** и почему это не новый язык, а надмножество (Superset) над JavaScript. Понятие статической типизации на этапе разработки в отличие от динамической типизации в JS.
    - Как устроен процесс компиляции TS: компилятор `tsc` проверяет код на ошибки типов на этапе разработки и полностью вырезает их, превращая код в чистый JavaScript, так как браузеры не умеют выполнять TypeScript.
    - Базовые типы: `string`, `number`, `boolean`, `void`, `any` (почему `any` — это табу), массивы (`string[]`), кортежи (Tuples).
    - Сложные типы: Описание структуры объектов через **Interfaces** и **Types**. Union типы (`string | number`). Типизация функций (аргументы и возвращаемое значение).
- **Теория безопасности:**
    - Как TypeScript помогает безопасности данных: явное описание типов исключает логические ошибки, когда функция ожидает ID задачи в виде строки, а фронтенд случайно передает туда объект сессии, что могло бы привести к крашу вкладки браузера (DoS на клиенте) или непредвиденной отправке некорректных данных на бэкенд.
- **Источники для изучения:**
    - _Официальный сайт:_ [TypeScript Handbook — Введение для фронтендеров](https://www.typescriptlang.org/docs/handbook/intro.html).
    - _Интерактивный учебник:_ [Курс по TypeScript на METANIT](https://metanit.com/web/typescript/) (Главы 1, 2 и 3 — основы, типы, интерфейсы).
- **Практика:**
    1. Инициализируйте TypeScript в вашем проекте ToDo-листа. Переименуйте файлы из `.js` в `.ts`. Настройте файл конфигурации `tsconfig.json`.
    2. Создайте файл `types.ts` и опишите строгие контракты данных вашего приложения:
        
        typescript
        
        ```
        export interface ITask {
            id: string;

        }
        ```

    3. Полностью перепишите вашу компонентную систему на TypeScript. Добейтесь того, чтобы компилятор TS не выдавал ни одной ошибки (особенно ошибок неявного типа `implicit any`). Типизируйте аргументы функций добавления и удаления задач, а также события DOM (`Event`, `SubmitEvent`).

## Неделя 11: ООП (Объектно-Ориентированное Программирования) в TypeScript

- **Теория безопасности:**

## Неделя 12: Паттерны проектирования и Принципы SOLID

- **Теория фронтенда:**
    - Глубокий разбор **Принципов SOLID** для построения чистого и легко заменяемого кода:
        1. **S** (Single Responsibility) — Каждая сущность отвечает только за одну задачу (например, компонент формы занимается только сбором инпутов, но не отправкой запросов в сеть).
        2. **O** (Open/Closed) — Код открыт для расширения (наследования), но закрыт для модификации (изменения базового класса).
        3. **L** (Liskov Substitution) — Наследники должны безболезненно заменять родителей без поломки логики.
        4. **I** (Interface Segregation) — Лучше создать много маленьких интерфейсов под узкие задачи, чем один огромный.
        5. **D** (Dependency Inversion) — Зависимость от абстракций (интерфейсов), а не от конкретных реализаций. Паттерн Внедрения зависимостей (Dependency Injection).
- **Теория безопасности:**
    - Принцип Single Responsibility как элемент безопасности: разделение логики отображения (UI) и логики работы с конфиденциальными данными (Storage/API) исключает появление сайд-эффектов, когда визуальный компонент при перерисовке может случайно залогировать секретный ключ пользователя в консоль или отправить его на неверный URL.
- **Источники для изучения:**
    - _Архитектура:_ [Принципы SOLID в картинках и примерах — Хабр](https://habr.com/ru/companies/productivity_inside/articles/505430/).
    - _Паттерны:_ Рефакторинг.Гуру — Паттерны проектирования в JS/TS (лучший мировой визуальный учебник по паттернам).
- **Практика:**
    1. **Тотальный рефакторинг на SOLID:** Переработайте кодовую базу ToDo-листа.
    2. Создайте класс `TodoStorage`, который инкапсулирует работу с данными (хранение массива задач). Следуя принципу **Dependency Inversion (D)**, создайте интерфейс `IStorage`. Сделайте так, чтобы ваши визуальные компоненты зависели от интерфейса `IStorage`, а не от конкретного класса.
    3. Напишите реализацию `LocalStorageService`, которая сохраняет задачи в память браузера. Благодаря принципу D, вы сможете передать эту службу в конструктор компонентов. Это позволит вам в будущем безболезненно заменить её на `HttpApiService` (для работы с реальным сервером), не изменив ни одной строчки кода внутри самих визуальных компонентов.

## Неделя 13: Углубленный Vue 3 (Composition API) + Глобальный стейт Pinia

## Неделя 14: Meta-фреймворк Nuxt (Архитектура 3/4) и SSR-хранилища

- **Теория безопасности:**
    - **Гидратационные атаки (Hydration Mismatch):** Понимание рисков, когда данные на сервере (SSR) не совпадают с данными на клиенте.
    - Написание серверных Middleware для защиты роутов (Route Guards) — жесткая блокировка страниц на уровне сервера до отправки HTML в браузер.

    - _Статья:_ [Что такое Server-Side Rendering (SSR) и зачем он нужен — Хабр](https://habr.com/ru/articles/483202/).
- **Практика:**

## Неделя 18: Трехслойная архитектура (Layered Architecture) и CRUD для ToDo API

- **Теория бэкенда:**
    - **Современная архитектура бэкенд-проектов:** Разбор **Трехслойной архитектуры (Layered Architecture)**, применяемой в индустрии для изоляции кода. Приложение делится на 3 независимых слоя:
        1. **Слой роутеров и контроллеров (Web / Controller Layer):** Отвечает только за прием HTTP-запросов, извлечение параметров (`req.body`, `req.params`) и отправку HTTP-ответов (`res.status().json()`).
        2. **Слой бизнес-логики (Service Layer):** Чистый JavaScript-код, где происходят все расчеты, проверки прав, валидация. Сервисы ничего не знают про HTTP, они получают чистые данные и возвращают результат.
        3. **Слой данных (Data Access / Repository Layer):** Отвечает исключительно за прямое общение с базой данных или файлами.
    - Проектирование ToDo REST API: `GET /api/tasks`, `POST /api/tasks`, `PATCH /api/tasks/:id`, `DELETE /api/tasks/:id`.
- **Теория безопасности:**
    - **Improper Input Validation (Неправильная валидация ввода):** Хакеры могут прислать в теле `POST`-запроса пустую строку, деформированный JSON или огромный текст размером в гигабайт, чтобы вызвать падение (Crash) памяти Node.js (DoS атака). Валидация типов входящих данных на уровне Middleware — критически важный рубеж обороны.
- **Источники для изучения:**
    - _Архитектура:_ [Архитектурные паттерны: Слоистая архитектура (Layered Architecture) — Хабр](https://habr.com/ru/articles/483202/).
    - _Безопасность:_ [OWASP Input Validation Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html) (мировой стандарт валидации данных).
- **Практика:**
    1. **Создание структуры папок:** Спроектируйте архитектуру проекта по слоям:
        
        ```
        src/
         ├── controllers/  # Слой приема HTTP
         ├── services/     # Слой бизнес-логики
         ├── repositories/ # Слой работы с файлами/БД
         └── routes/       # Объединение эндпоинтов
        ```
        
    2. Напишите полноценный CRUD для ToDo-листа, распределив код строго по трем слоям. На этой неделе базы данных еще нет: пускай ваш `TaskRepository` читает и пишет данные в обычный локальный файл `tasks.json` на диске вашего Arch Linux с помощью асинхронного встроенного модуля `fs/promises`.
    3. **Внедрение безопасности:** Установите библиотеку валидации `zod` (`npm install zod`). Опишите строгую схему проверки входящей задачи (поле `title` обязано быть строкой, не должно содержать только пробелы, минимальная длина — 3 символа, максимальная — 255). Убедитесь, что сервер возвращает структурированный статус `400 Bad Request` при отправке некорректных данных.

## Неделя 19: Реляционная база данных PostgreSQL и чистый язык SQL

- **Теория бэкенда:**
    - Что такое Реляционные системы управления базами данных (РСУБД). Почему таблицы — это стандарт структурированного хранения данных. Установка и базовая конфигурация **PostgreSQL**.
    - Глубокое изучение синтаксиса **языка SQL (Structured Query Language)** без использования ORM:
        - `CREATE TABLE` — проектирование таблиц, указание типов данных (`SERIAL`, `VARCHAR`, `BOOLEAN`, `TIMESTAMP`).
        - `PRIMARY KEY` и `FOREIGN KEY` — организация связей между таблицами. Связь «Один-ко-многим» (`One-to-Many`): один пользователь владеет множеством задач.
        - Операторы манипуляции данными: `INSERT INTO`, `SELECT` с фильтрацией `WHERE` и сортировкой `ORDER BY`, `UPDATE`, `DELETE`.
- **Теория безопасности:**
    - **SQL Injection (SQL-инъекции):** Главная и самая опасная уязвимость бэкенд-систем. Происходит, когда разработчик склеивает строки при отправке запроса к базе данных (например, `SELECT * FROM tasks WHERE id =` + `req.params.id`). Злоумышленник может передать в URL строку `' OR '1'='1`, заставив базу проигнорировать условия и выгрузить конфиденциальные данные всех пользователей. Защита: использование **параметризованных запросов (Prepared Statements)**, где данные передаются отдельно от тела SQL-команд.
- **Источники для изучения:**
    - _Интерактивный тренажер:_ [SQL Academy](https://sql-academy.org/ru) (пройдите первые 15 практических заданий на выборку данных).
    - _Безопасность:_ [SQL Injection — Портал PortSwigger Web Security](https://portswigger.net/web-security/sql-injection) (интерактивный мировой стандарт по логике SQL-инъекций).
- **Практика:**
    1. Запустите PostgreSQL внутри Docker-контейнера в вашем Arch Linux, привязав постоянное хранилище (Volume), чтобы данные не пропадали (используйте навыки из Месяца 2).
    2. Установите официальный нативный драйвер для работы Node.js с PostgreSQL: `npm install pg`.
    3. Напишите SQL-скрипт инициализации вашей базы данных. Создайте руками через терминал PostgreSQL (`psql`) две связанные таблицы: таблицу `users` (id, email, password) и таблицу `todos` (id, title, completed, user_id). Поле `user_id` должно быть внешним ключом (`FOREIGN KEY`), ссылающимся на `users.id` с каскадным удалением `ON DELETE CASCADE`.
    4. **Внедрение безопасности:** Перепишите ваш слой `TaskRepository` с работы с json-файлами на прямые SQL-запросы к PostgreSQL через модуль `pg`. **Категорически запрещено использовать конкатенацию строк!** Пишите строго параметризованные запросы:
        
        javascript

        ```
        const query = 'INSERT INTO todos (title, completed, user_id) VALUES ($1, $2, $3) RETURNING *';

        const result = await db.query(query, values);
        ```

## Неделя 20: Связь Фронтенда с Бэкендом, CORS и базовая авторизация

- **Теория бэкенда:**
    - Как объединить написанные вами на Месяце 4 глобальные стейт-менеджеры (Pinia / Zustand) с вашим новым сервером на Node.js.
    - Что такое политика браузера **Same-Origin Policy (Политика одного источника)**.
    - Разбор заголовков **CORS (Cross-Origin Resource Sharing)**. Почему браузер блокирует запросы от вашего React/Vue приложения, запущенного на порту `5173`, к серверу Express на порту `5000`. Как сервер должен отправлять заголовок `Access-Control-Allow-Origin` для авторизации запросов.
- **Теория безопасности:**
    - **Небезопасные CORS-политики:** Почему использование wildcard-значения `Access-Control-Allow-Origin: *` (разрешить запросы абсолютно всем сайтам в интернете) является грубейшим нарушением безопасности в продакшене. Злоумышленники могут создать фишинговый сайт, который от лица залогиненного пользователя сможет делать скрытые запросы к вашему API ToDo-листа. Белый список разрешенных доменов (White-listing) — стандарт защиты.
- **Источники для изучения:**

## Неделя 22: ООП и Принципы SOLID на сервере (Внедрение зависимостей)

- **Теория бэкенда:**
    - Применение **Объектно-Ориентированного Программирования** на стороне сервера. Замена разрозненных функций-контроллеров и сервисов на полноценные классы.
    - Использование модификаторов доступа `public`, `private`, `protected` для защиты внутренних методов.
    - Глубокая интеграция **Принципов SOLID** в архитектуру Node.js:
        - **S** (Single Responsibility) — Контроллер занимается только HTTP-протоколом, Сервис — только логикой приложения.
        - **D** (Dependency Inversion / Инверсия зависимостей) — Главный паттерн бэкенда. Класс `TaskService` не должен жестко создавать внутри себя объект `TaskRepository` через `new`. Он должен принимать репозиторий через конструктор в виде абстрактного интерфейса (`Dependency Injection`).
- **Теория безопасности:**
    - **Loose Coupling (Слабая связанность):** За счет инверсии зависимостей логика проверки прав пользователя и логика работы с базой данных полностью разделены. Это исключает появление скрытых уязвимостей, когда при модификации метода сохранения в БД разработчик мог случайно закомментировать или пропустить валидацию прав доступа (Broken Object Level Authorization — BOLA).
- **Источники для изучения:**
    - _Архитектура:_ [Внедрение зависимостей (Dependency Injection) в Node.js — Хабр](https://habr.com/ru/articles/483202/).
    - _Паттерны:_ Архитектурные паттерны: Чистая архитектура и SOLID на бэкенде — Refactoring.Guru.
- **Практика:**
    1. **Тотальный рефакторинг на классы:** Превратите все ваши функции-контроллеры, сервисы и репозитории в классы TypeScript.
    2. Реализуйте паттерн **Dependency Inversion**: создайте интерфейс `ITaskRepository`. Класс `TaskService` должен принимать в конструктор объект типа `ITaskRepository`.
    3. Передайте экземпляр `TaskRepository` в конструктор `TaskService` вручную на этапе инициализации сервера в файле `app.ts`. Это позволит вам на следующей неделе мгновенно подменить репозиторий с чистого SQL на ORM Prisma, не изменив ни одной строчки кода в самом сервисе бизнес-логики.

## Неделя 23: Интеграция современной ORM Prisma и защита от инъекций

- **Теория бэкенда:**

## Неделя 24: Криптография и JWT-авторизация в защищенных HttpOnly куках

- **Теория бэкенда:**
    - Архитектура безопасной аутентификации. Почему нельзя хранить пароли в чистом виде (использование `bcrypt` для хэширования).
    - Глубокий разбор **JWT (JSON Web Token)**. Продвинутая сессионная схема: использование двух токенов — короткоживущего **Access Token** (живет 15 минут, используется для авторизации запросов к API) и долгоживущего **Refresh Token** (живет 30 дней, хранится в базе данных, используется для автоматического выпуска нового Access токена без повторного ввода логина/пароля).
    - Создание защищенного Middleware аутентификации для проверки токенов Express-сервером.
- **Теория безопасности:**
    - **Защита токенов от кражи (XSS vs CSRF):** Если фронтенд хранит JWT в `localStorage`, вредоносный скрипт (XSS) украдет его одной строчкой кода. Самое безопасное решение — отправлять Refresh-токен с бэкенда в браузер через HTTP-заголовки `Set-Cookie` с флагами **`HttpOnly`** (JS-код полностью слеп к этой куке, её нельзя украсть через XSS) и **`Secure`** (передача только по зашифрованному HTTPS). Защита от **CSRF (Cross-Site Request Forgery)** атак с помощью флага куки `SameSite=Strict/Lax`.
- **Источники для изучения:**
    - _Статья:_ JWT авторизация: Access/Refresh токены, HttpOnly Cookies и безопасность — Хабр.
    - _Безопасность:_ [OWASP JSON Web Token Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_for_Java_Cheat_Sheet.html) (индустриальный стандарт работы с JWT-токенами).
- **Практика:**
    1. Установите пакеты работы с куками и токенами: `npm install jsonwebtoken bcrypt cookie-parser` и их типы `@types/...`. Подключите `cookie-parser` в Express.
    2. Напишите роут регистрации `POST /api/auth/register` (хэширование пароля через `bcrypt.hash(password, 10)`) и входа `POST /api/auth/login`. При успешном входе генерируйте два токена.
    3. Настройте отправку Refresh-токена в куки браузера:
        
        typescript
        
        ```
        res.cookie('refreshToken', refreshToken, {
            httpOnly: true,
            secure: process.env.NODE_ENV === 'production', // true на сервере
            sameSite: 'lax',
            maxAge: 30 * 24 * 60 * 60 * 1000 // 30 дней
        });
        ```
        
        Используйте код с осторожностью.
        
    4. Напишите `authMiddleware.ts`, которое извлекает Access токен из заголовка запроса, валидирует его и прикрепляет `req.user` к текущему потоку. Защитите этим middleware все роуты ToDo CRUD, гарантируя, что пользователь получает доступ только к своим записям. Протестируйте авторизацию в связке с вашим Zustand/Pinia фронтендом из Месяца 4.

- **Теория бэкенда:**
    - Криптография в Python: хэширование паролей с помощью библиотеки `passlib` и алгоритма `bcrypt`.
    - Реализация схемы двух токенов (Access / Refresh) на Python. Использование библиотеки `python-jose` для генерации, подписи и валидации JWT-токенов.
    - Настройка функций FastAPI для чтения и записи куки-файлов в HTTP-ответах (`Response`).
    - Написание функций-зависимостей (`Depends`) для авторизации: проверка токена перед допуском пользователя к CRUD-операциям его задач.
- **Теория безопасности:**
    - **Broken Object Level Authorization (BOLA / Нарушение авторизации на уровне объектов):** Критическая уязвимость API. Если хакер авторизован как Пользователь А, но делает запрос `PATCH /api/tasks/55` (где 55 — ID задачи Пользователя Б), сервер не должен разрешать это действие. Каждый роут обязан строго сверять `user_id` запрашиваемой задачи с `user_id` из JWT-токена.
- **Источники для изучения:**
    - _Гайд:_ [Безопасность и JWT авторизация в FastAPI — Официальный туториал](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/).
    - _Безопасность:_ OWASP Top 10: API1:2023 Broken Object Level Authorization (главная уязвимость современных API интерфейсов).
- **Практика:**
    1. Установите криптографические библиотеки: `pip install passlib[bcrypt] python-jose[cryptography] pyjwt`.
    2. Напишите роуты `POST /api/auth/register` (хэширование паролей) и `POST /api/auth/login`. Настройте выдачу токенов: Refresh-токен должен записываться в защищенную куку с флагами `httponly=True`, `secure=True`, `samesite="lax"`.
    3. Напишите функцию-зависимость `get_current_user`, которая достает токен, верифицирует его и возвращает объект пользователя. Защитите ей CRUD роуты ToDo-листа. Настройте жесткую проверку: база данных должна отдавать задачи только там, где `Task.user_id == current_user.id`, полностью исключив уязвимость BOLA.
    4. Настройте CORS в FastAPI с помощью `CORSMiddleware` под порт вашего фронтенда. Запустите фронтенд на React/Vue (из Месяца 4) и переключите базовый URL запросов с Node.js сервера на Python сервер (`http://127.0.0.1:8000`). Убедитесь, что ваше приложение продолжает работать без изменений интерфейса.

# МЕСЯЦ 8: Полная оркестрация Fullstack-приложения (Multi-stage Docker, Nginx Production) и Деплой на VPS

**Главный ментальный сдвиг месяца:** Перейти от локального запуска проектов (в режиме разработки `npm run dev` или `uvicorn --reload`) к созданию изолированной, отказоустойчивой, оптимизированной и защищенной production-инфраструктуры. ## Неделя 29: Написание безопасных Dockerfile и оптимизация образов (Multi-stage Builds)

- **Теория инфраструктуры:**
    - Проблема тяжелых и небезопасных Docker-образов. Зачем тащить в продакшен компиляторы, исходный код TypeScript и утилиты разработки, если серверу нужен только готовый результат сборки.
    - Концепция **Multi-stage Builds (Многоэтапная сборка)**: использование нескольких инструкций `FROM` в одном Dockerfile. Первый этап (Builder) скачивает зависимости и собирает проект, второй этап (Runner) берет чистый легковесный образ и копирует туда _только_ готовый артефакт сборки.
- **Теория безопасности:**
    - **Разделение привилегий (Non-root user):** По умолчанию процессы в контейнере работают от имени пользователя `root`. Если злоумышленник найдет уязвимость в Node.js/Python коде и сможет выполнить системную команду, он получит права root на вашем сервере через атаку «побег из контейнера». Использование директивы `USER` внутри Dockerfile для запуска приложения от имени бесправного пользователя.
    - **Площадь атаки базового образа:** Сравнение полных Linux-образов (`ubuntu`, `node:latest`) и ультра-легковесных дистрибутивов (`node:alpine`, `python:alpine`), содержащих минимальный набор утилит, что снижает риск наличия уязвимостей в системных библиотеках (CVE).
- **Источники для изучения:**
    - _Документация:_ [Docker Docs — Многоэтапная сборка (Multi-stage Builds)](https://docs.docker.com/build/building/multi-stage/) [19].
    - _Гайд:_ Docker Security Best Practices (официальные стандарты безопасной сборки контейнеров) [19].
    - _Статья:_ Как правильно собрать Docker-образ для Node.js/TypeScript — Хабр.
- **Практика (Писать код строго руками в вашем Arch Linux):**
    1. Напишите двухэтапный `Dockerfile` для вашего фронтенда (React/Vue). На первом этапе образ `node:alpine` устанавливает пакеты и собирает статику (`npm run build`). На втором этапе используется чистый образ `nginx:alpine`, куда копируется только папка `dist/` [19].
    2. Напишите `Dockerfile` для вашего бэкенда (Node.js/TypeScript или Python/FastAPI), используя Multi-stage подход [19]. В финальном этапе обязательно создайте системного пользователя без прав root, передайте ему права на рабочую директорию через `CHOWN` и переключите контекст:
        
        dockerfile
        
        ```
        RUN addgroup -S appgroup && adduser -S appuser -G appgroup
        USER appuser
        ```
        
        Используйте код с осторожностью.
        
    3. Соберите образы локально командой `docker build`. Запустите сканер безопасности `trivy image <имя_вашего_образа>` (который вы настроили в Месяце 2) и добейтесь полного отсутствия уязвимостей уровня `CRITICAL` и `HIGH`.

## Неделя 30: Глобальная оркестрация всей системы через Docker Compose

- **Теория инфраструктуры:**
    - Архитектура многоконтейнерных микросервисных систем. Объединение изолированных компонентов приложения в единый управляемый стек.
    - Устройство конфигурационного файла `docker-compose.yml`. Описание сервисов (`services`), управление порядком запуска через `depends_on` и проверку готовности `healthcheck` (например, бэкенд не должен запускаться, пока база данных PostgreSQL полностью не поднимется и не начнет принимать соединения).
    - **Docker Volumes (Тома данных):** Разница между анонимными томами и именованными томами. Настройка именованного тома для PostgreSQL, гарантирующего, что данные ToDo-листа сохранятся на жестком диске хоста при полном удалении или обновлении контейнера.
    - **Docker Networks (Изоляция сетей):** Создание изолированных виртуальных подсетей (например, подсеть `db_net` связывает только бэкенд и базу данных, а база данных вообще не имеет прямого доступа во внешнюю сеть и закрыта от интернета).
- **Теория безопасности:**
    - **Утечка секретов (Secrets Management):** Категорический запрет на прописывание паролей БД, секретных ключей JWT и портов внутри файлов `Dockerfile` или `docker-compose.yml`. Вынесение всех конфиденциальных переменных в скрытый файл `.env`, который жестко заносится в `.gitignore` и никогда не пушится на GitHub.
- **Источники для изучения:**
    - _Документация:_ [Docker Compose CLI reference](https://docs.docker.com/compose/reference/) [19].
    - _Гайд:_ [Docker Compose Secrets Management](https://docs.docker.com/compose/use-secrets/) [19].
- **Практика:**
    1. Создайте в корне вашего репозитория файл `.env` и пропишите туда переменные: `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `JWT_SECRET`, `NODE_ENV=production`.
    2. Напишите глобальный файл `docker-compose.yml` [19]. Он должен декларативно запускать 4 контейнера:
        - `db`: Образ `postgres:alpine`. Подключен том `postgres_data` для сохранения данных. Находится строго в сети `backend_net` [19].
        - `backend`: Собирается из вашего бэкенд-Dockerfile. Читает переменные из `.env` [19]. Находится в сетях `backend_net` и `frontend_net` [19].
        - `frontend`: Собирается из вашего фронтенд-Dockerfile (содержит статику) [19]. Находится в сети `frontend_net` [19].
        - `nginx`: Единая точка входа для внешнего мира [19].
    3. Запустите стек локально одной командой `docker compose up -d --build` [19]. Проверьте статус всех контейнеров, изучите логи сборки и убедитесь, что база данных успешно инициализировалась, а бэкенд дождался её запуска.

## Неделя 31: Nginx в роли Production Reverse Proxy и конфигурация безопасности

- **Теория инфраструктуры:**
    - Архитектура развертывания Fullstack-приложения в продакшене. Роль Nginx как единого веб-сервера, принимающего весь входящий трафик на стандартном HTTP порту `80` (и в будущем HTTPS `443`).
    - Оптимизация Nginx для раздачи статического фронтенда: как директивы `try_files` позволяют правильно работать роутингу в Single Page Applications (React / Vue), перенаправляя все запросы страниц на `index.html`.
    - Конфигурация **Reverse Proxy (Обратного проксирования)**: Nginx принимает запрос на порт 80, анализирует URL, и если путь начинается с `/api/`, он прозрачно пересылает этот запрос по внутренней сети Docker в контейнер бэкенда на порт 5000 с помощью директивы `proxy_pass`.
- **Теория безопасности:**
    - **Заголовки защиты (Security Headers):** Защита пользователей вашего фронтенда на уровне заголовков веб-сервера. Настройка `Content-Security-Policy` (CSP — ограничение источников загрузки скриптов для полной ликвидации XSS), `Strict-Transport-Security` (HSTS — принудительный перевод браузера на HTTPS), `X-Frame-Options: DENY` (защита от кражи кликов в iframe — Clickjacking).
    - **Скрытие баннеров (Server Banner Grabbing):** Отключение вывода точной версии Nginx во всех HTTP-ответах, чтобы автоматические сканеры уязвимостей хакеров не могли определить версию сервера.
- **Источники для изучения:**
    - _Документация:_ [Nginx Reverse Proxy Guide](https://docs.nginx.com/nginx/admin-guide/web-server/reverse-proxy/).
    - _Рекомендации:_ [OWASP Secure Headers Project](https://owasp.org/www-project-secure-headers/) (мировой стандарт настройки заголовков безопасности веб-серверов).
    - _Инструмент тестирования:_ [Security Headers Scanner](https://securityheaders.com/) (сервис, по которому вы будете проверять качество защиты вашего сервера).
- **Практика:**
    1. Напишите production-файл конфигурации `nginx.conf` для вашего контейнера Nginx в Docker Compose.
    2. Внутри блока `server {}` пропишите директиву скрытия версии: `server_tokens off;`. Добавьте блок заголовков безопасности:
        
        nginx
        
        ```
        add_header X-Frame-Options "DENY" always;
        add_header X-Content-Type-Options "nosniff" always;
        add_header Referrer-Policy "no-referrer" always;
        ```
        
        Используйте код с осторожностью.
        
    3. Настройте два блока локаций `location`:
        - `location /` — должен смотреть в папку со скомпилированным фронтендом и раздавать статику (`root /usr/share/nginx/html; try_files $uri $uri/ /index.html;`).
        - `location /api/` — должен проксировать запросы на бэкенд: `proxy_pass http://backend:5000;`. Настройте передачу реального IP-адреса пользователя бэкенду через заголовки `proxy_set_header X-Real-IP $remote_addr;`, чтобы на бэкенде работал Rate Limiting.

## Неделя 32: Аренда VPS, настройка Linux (Ubuntu/Debian) и боевой Деплой приложения

- **Теория инфраструктуры:**
    - Что такое виртуальный выделенный сервер (**VPS/VDS**) и как устроена облачная инфраструктура.
    - Администрирование Linux-серверов: работа по защищенному криптографическому протоколу **SSH** (Secure Shell) через терминал. Генерация пар SSH-ключей (публичный и приватный) для беспарольного входа.
    - Базовая настройка межсетевого экрана (**Firewall**) в Linux для жесткого закрытия всех портов, кроме необходимых (`80` для HTTP, `443` для HTTPS, и измененный нестандартный порт для SSH).
- **Теория безопасности:**
    - **SSH Hardening (Укрепление SSH):** Вход на сервер по стандартному паролю — легкая мишень для брутфорс-ботов. Безопасный стандарт: полное отключение авторизации по паролю в конфигурации `/etc/ssh/sshd_config` (`PasswordAuthentication no`), отключение входа для пользователя root (`PermitRootLogin no`) и смена стандартного порта `22` на любой случайный порт (например, `2284`), чтобы скрыться от массовых сканеров интернета.
- **Источники для изучения:**
    - _Гайд:_ [Initial Server Setup with Ubuntu — DigitalOcean Tutorial](https://www.digitalocean.com/community/tutorials/initial-server-setup-with-ubuntu).
    - _Безопасность:_ SSH Security Hardening Guide — Хабр.
- **Практика:**
    1. Арендуйте самый дешевый Linux VPS (Ubuntu или Debian) у любого хостинга. Сгенерируйте на вашем Arch Linux пару SSH-ключей через команду `ssh-keygen`. Скопируйте публичный ключ на сервер.
    2. Подключитесь к вашему серверу через терминал по SSH. Проведите процедуру Hardening: создайте нового системного пользователя с правами `sudo`, настройте файл `sshd_config` (отключите вход по паролю, отключите root-вход, измените порт SSH) и перезапустите службу `sudo systemctl restart ssh`. Настройте Firewall (утилита `ufw`): разрешите ваш новый SSH-порт, а также порты 80 и 443, после чего включите его (`sudo ufw enable`).
    3. Установите на чистый VPS сервер Git и Docker: `sudo apt update && sudo apt install docker.io docker-compose-v2 git`.
    4. Клонируйте ваш приватный репозиторий с GitHub на сервер. Создайте на сервере файл `.env` с боевыми паролями. Запустите всю вашу Fullstack-систему в фоновом продакшен-режиме:
        
        bash
        
        ```
        sudo docker compose up -d --build
        ```
        
        Используйте код с осторожностью.
        
    5. **Финальный триумф:** Откройте браузер на вашем компьютере, введите в адресную строку публичный IP-адрес вашего арендованного VPS-сервера. Перед вами откроется ваш ToDo-лист. Зарегистрируйте пользователя (пароль захешируется в bcrypt), войдите в систему (сервер выдаст JWT куку с флагами HttpOnly/Secure), создайте и удалите задачи (запросы улетят через Nginx Reverse Proxy на бэкенд Node.js/Python, который обработает их через валидацию Zod/Pydantic и сохранит в PostgreSQL с помощью безопасных параметризованных запросов ORM Prisma/SQLAlchemy).
