# Лекция 34.4: Node.js и npm: основы для фронтенд-разработчика

В этой лекции мы изучим инфраструктурный фундамент современного фронтенда — среду выполнения **Node.js** и пакетный менеджер **npm**. Мы разберём, зачем фронтенд-разработчику запускать JavaScript вне браузера, научимся проектировать манифест проекта **`package.json`**, управлять зависимостями и детерминированными сборками через **`package-lock.json`** и **`npm ci`**, освоим правила семантического версионирования **SemVer**, безопасность цепи поставок (**Supply Chain Security**) и интеграцию Node.js в **CI/CD** пайплайны.

> ℹ️ *Примечание:* Внутреннее устройство архитектуры Node.js (V8 биндинги, Libuv, фазы Event Loop) подробно изучается в **Лекции 194**. Данная лекция сфокусирована на фундаментальных практических инструментах экосистемы Node.js, необходимых для фронтенд-разработки начиная с самых первых проектов.

> ℹ️ *Примечание:* в примерах ниже используется пакет `sass` как пример консольного (CLI) инструмента. Сам синтаксис SCSS изучается в **Лекции 34.5**; пока достаточно знать, что `sass` превращает файлы `.scss` в обычный `.css`.

## 💡 Глоссарий ключевых терминов лекции

> 📌 **1. Node.js (Runtime Environment)**
> * **Что это:** Асинхронная среда выполнения JavaScript с открытым исходным кодом, построенная на движке V8 (Chrome). Позволяет исполнять JS-код вне браузера — на сервере, в командной строке или в виде локальных CLI-инструментов сборки.

> 📌 **2. npm (Node Package Manager)**
> * **Что это:** Стандартный пакетный менеджер для экосистемы Node.js и крупнейший в мире реестр готовых open-source библиотек (npm registry). Состоит из CLI-утилиты командной строки и онлайн-хранилища пакетов.

> 📌 **3. `package.json` (Project Manifest)**
> * **Что это:** Главный конфигурационный JSON-файл проекта. Содержит метаданные (название, версия), список внешних зависимостей (`dependencies`, `devDependencies`) и пользовательские CLI-скрипты автоматизации (`scripts`).

> 📌 **4. `package-lock.json` & `npm ci`**
> * **Что это:** **`package-lock.json`** — файл строгой фиксации графа зависимостей с точными версиями и хэшами целостности. **`npm ci` (Clean Install)** — команда быстрой и детерминированной установки пакетов строго по lock-файлу в CI/CD окружениях.

> 📌 **5. SemVer (Semantic Versioning)**
> * **Что это:** Стандарт версионирования программного обеспечения в формате `MAJOR.MINOR.PATCH` (например, `2.4.1`), где мажорная версия означает ломающие изменения (Breaking Changes), минорная — новый функционал с обратной совместимостью, а патч — багфиксы.

> 📌 **6. Supply Chain Security & `npm audit`**
> * **Что это:** Безопасность цепи поставок программного обеспечения. **`npm audit`** — встроенный инструмент автоматического анализа дерева зависимостей на наличие известных уязвимостей (используется база GitHub Advisory Database, в которую входят и записи CVE).

## Подглава 34.4.1: Зачем Node.js фронтенд-разработчику?

Исторически JavaScript исполнялся исключительно внутри браузера для оживления веб-страниц. Однако с появлением **Node.js** в 2009 году фронтенд-разработка пережила революцию. 

Сегодня фронтендер использует Node.js на своём рабочем компьютере **не для написания серверного кода**, а как **платформу для запуска профессионального инструментария разработки**:

```text
+-----------------------------------------------------------------------+
|                Рабочее окружение фронтендера (Node.js)                |
|                                                                       |
|  +-------------------+  +-------------------+  +-------------------+  |
|  |      Сборщики     |  |   Транспиляторы   |  |   Препроцессоры   |  |
|  |  (Vite, Webpack)  |  | (Babel, SWC, TSC) |  |  (Dart Sass/SCSS) |  |
|  +-------------------+  +-------------------+  +-------------------+  |
|            |                      |                      |            |
|            v                      v                      v            |
|  +-------------------+  +-------------------+  +-------------------+  |
|  | Линтеры/Форматтеры|  |    Тест-раннеры   |  |   SSR-фреймворки  |  |
|  | (ESLint, Prettier)|  |   (Vitest, Jest)  |  | (Nuxt 3, Next.js) |  |
|  +-------------------+  +-------------------+  +-------------------+  |
+-----------------------------------------------------------------------+
                                    |
                                    v (Сборка и оптимизация)
+-----------------------------------------------------------------------+
|               Готовые бандлы для браузера (HTML/CSS/JS)               |
+-----------------------------------------------------------------------+
```

### Запуск JavaScript вне браузера: `node file.js`
Самый простой способ увидеть, что Node.js — это просто среда выполнения JS: создайте файл `hello.js` и запустите его из терминала.

```js
// hello.js
console.log("Привет из Node.js!");
```

```bash
node hello.js    # Выведет в терминал: Привет из Node.js!
```

> ℹ️ В Node.js нет браузерных объектов `window` и `document`, потому что нет ни страницы, ни вкладки. Зато есть доступ к файлам, сети и командной строке компьютера.

### Главные задачи Node.js во фронтенде:
1. **Локальный веб-сервер разработки (Dev Server):** запуск серверов с поддержкой горячей перезагрузки модулей (**HMR — Hot Module Replacement**), мгновенно отражающей изменения в коде без перезагрузки вкладки.
2. **Компиляция и сборка:** преобразование препроцессоров (SCSS → CSS), транспиляция современного JS/TS под старые браузеры, минификация и сжатие ресурсов.
3. **Управление качеством кода:** автоматическая проверка стилей (ESLint, Stylelint) и форматирование (Prettier) перед коммитом в Git.
4. **Запуск автоматических тестов:** прогон модульных и интеграционных тестов через CLI в изолированном окружении.

### Установка Node.js LTS: установщик и менеджеры версий (`nvm` / `fnm`)
Основные каналы релизов Node.js:
* **LTS (Long Term Support):** версия с долгосрочной поддержкой: исправления ошибок и патчи безопасности выходят около 30 месяцев. Для коммерческой разработки и продакшена используйте только LTS (Active или Maintenance).
* **Current:** самая новая версия с новейшими возможностями; срок её поддержки короткий.

> ℹ️ Схема выпусков Node.js меняется (с 2026 года планируется один мажорный релиз в год, и каждый становится LTS). Актуальную таблицу версий смотрите на `nodejs.org/en/about/previous-releases`.

Есть два способа установки:
* **Официальный установщик** (`.msi` / `.pkg` с сайта nodejs.org) — самый простой вариант, чтобы быстро начать и попробовать `node` и `npm`.
* **Менеджер версий** (`nvm` / `fnm`) — рекомендуемый вариант для постоянной работы.

#### Почему для работы лучше менеджер версий:
Системная установка (установщик или `apt install nodejs`) ставит одну версию Node.js на весь компьютер. Это приводит к двум неудобствам:
1. Старому проекту может понадобиться другая версия (например, Node.js 22, когда установлена Node.js 24), и переключиться между ними сложно.
2. В Linux при установке глобальных пакетов часто требуется `sudo` (конфликты прав доступа).

Менеджеры версий ставят Node.js в пользовательскую директорию без прав администратора и позволяют мгновенно переключаться между версиями.

```bash
# nvm (Linux/macOS; для Windows используйте fnm или nvm-windows):
nvm install --lts         # Установить последнюю LTS-версию
nvm use --lts             # Переключиться на неё
nvm ls                    # Список установленных версий

# fnm (Windows / Linux / macOS):
fnm install --lts         # Установить последнюю LTS-версию
fnm ls                    # Список установленных версий

# Проверка версий в терминале (номера зависят от установленной версии):
node -v                   # Например: v24.x.x
npm -v                    # Например: 11.x.x
```

## Подглава 34.4.2: Манифест проекта `package.json` и команда `npm init`

Каждый современный фронтенд-проект, использующий Node.js, начинается с файла манифеста **`package.json`**. Он располагается в корневой директории репозитория и выполняет роль паспорта проекта.

### Создание `package.json`:
Для инициализации манифеста в пустой папке проекта выполните в терминале:

```bash
# Интерактивная инициализация (задаёт вопросы о названии, версии, авторе):
npm init

# Быстрая инициализация с дефолтными значениями (флаг -y / --yes):
npm init -y
```

### Анатомия стандартного `package.json`:

```json
{
  "name": "todo-app",
  "version": "1.0.0",
  "description": "Адаптивное Todo App на Vanilla JS и SCSS",
  "type": "module",
  "private": true,
  "scripts": {
    "dev": "sass --watch src/scss/main.scss dist/css/style.css",
    "build:css": "sass src/scss/main.scss dist/css/style.css --style=compressed",
    "format:check": "prettier --check .",
    "format": "prettier --write ."
  },
  "dependencies": {
    "normalize.css": "^8.0.1"
  },
  "devDependencies": {
    "prettier": "^3.3.3",
    "sass": "^1.80.6"
  }
}
```

### Ключевые поля манифеста:
* **`name` & `version`:** уникальное имя проекта и его текущая версия по SemVer.
* **`type`:** если указано `"module"`, Node.js трактует `.js` файлы в проекте как **ES-модули** (`import/export`). Если поле отсутствует, используется классическая система CommonJS (`require/module.exports`).
* **`private: true`:** предотвращает случайную публикацию частного коммерческого проекта в публичный реестр npm registry.
* **`scripts`:** словарь пользовательских CLI-команд. Запускаются в терминале через `npm run <script-name>` (например, `npm run dev` или `npm run build:css`).
* **`dependencies`:** внешние библиотеки, необходимые для работы приложения в продакшене.
* **`devDependencies`:** библиотеки, необходимые **только на этапе разработки и сборки** (препроцессоры, линтеры, сборщики, тесты).

## Подглава 34.4.3: Управление зависимостями и директория `node_modules`

Пакетный менеджер **npm** автоматически скачивает внешние библиотеки из центрального реестра `registry.npmjs.org` и размещает их в вашем проекте.

### Флаги установки пакетов:

```bash
# 1. Установка рабочей зависимости (dependencies):
npm install normalize.css
npm i normalize.css             # Сокращённая запись

# 2. Установка зависимости разработки (devDependencies):
npm install --save-dev sass
npm i -D sass                   # Сокращённая запись (промышленный стандарт)

# 3. Удаление зависимости из проекта:
npm uninstall sass
npm rm sass                     # Сокращённая запись
```

### Директория `node_modules` и правило `.gitignore`:
При первой установке любого пакета в корне проекта создаётся папка **`node_modules`**. В неё разворачиваются не только запрошенные вами библиотеки, но и все их косвенные транзитивные зависимости.

```text
my-project/
├── node_modules/         <-- 🚨 СОТНИ МЕГАБАЙТ СКАЧАННЫХ БИБЛИОТЕК
│   ├── sass/
│   ├── prettier/
│   └── ... (тысячи подпапок)
├── src/
│   └── scss/
├── .gitignore            <-- ОБЯЗАТЕЛЬНО СОДЕРЖИТ node_modules/
├── package.json
└── package-lock.json
```

#### 🚨 КРИТИЧЕСКОЕ ПРАВИЛО GIT:
Папка `node_modules` может весить от 100 МБ до 1 ГБ и содержать десятки тысяч мелких файлов. **ЕЁ КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО КОММИТИТЬ В GIT-РЕПОЗИТОРИЙ!**

Файл **`.gitignore`** в корне проекта обязательно должен содержать строку `node_modules/`:

```text
# .gitignore
node_modules/
dist/
.env
```

Любой разработчик, скачавший ваш репозиторий без `node_modules`, разворачивает полное окружение одной базовой командой:
```bash
npm install
```

### Выполнение бинарных утилит через `npx`:
В `devDependencies` мы часто устанавливаем CLI-инструменты (например, `sass`, `prettier`, `typescript`). Чтобы запустить локально установленную утилиту без глобальной установки на ПК, используется команда **`npx`** (запускает исполняемый файл из npm-пакета):

```bash
# npx ищет локальный исполняемый файл внутри node_modules/.bin/ и запускает его:
npx prettier --write .
npx sass src/scss/main.scss dist/css/style.css
```

> ⚠️ Если пакета нет в `node_modules`, `npx` предложит скачать его во временную папку и запустить самую свежую версию. Поэтому сначала установите нужные инструменты в проект (`npm i -D prettier`), чтобы все разработчики работали с одной и той же версией.

## Подглава 34.4.4: `package-lock.json`, детерминированные сборки и `npm ci`

При вызове `npm install` создаётся и обновляется важнейший файл — **`package-lock.json`**.

### Проблема рассинхронизации версий:
В `package.json` версии записываются с символами гибких диапазонов, например `"sass": "^1.80.0"`. Если бы lock-файла не было, один разработчик, установивший пакет сегодня, получил бы версию `1.80.6`, а второй, вызвавший `npm install` через месяц, когда вышла версия `1.85.0`, получил бы другую. Их приложения собирались бы на разных версиях библиотеки. Это приводит к неуловимым багам: *«на моей машине всё работало»*.

```text
package.json (Декларативные желания):
  "sass": "^1.80.0"   -->  "Разрешено ставить любую версию от 1.80.0 до < 2.0.0"

package-lock.json (Точная фиксация версий):
  "node_modules/sass": {
    "version": "1.80.6",
    "resolved": "https://registry.npmjs.org/sass/-/sass-1.80.6.tgz",
    "integrity": "sha512-D/C3B3sL3POfS..."
  }
```

### Зачем нужен `package-lock.json`:
1. **Детерминизм:** фиксирует точное дерево всех прямых и транзитивных версий пакетов вплоть до каждого билда.
2. **Безопасность целостности:** содержит криптографические хэши `sha512` (`integrity`), по которым npm проверяет, что скачанный архив совпадает с зафиксированным (то есть не был подменён).
3. **Ускорение установки:** кэширует структуру связей, избавляя npm от повторного вычисления графа зависимостей.

> 🔒 **ПРАВИЛО:** Файл `package-lock.json` **ОБЯЗАТЕЛЬНО должен коммититься в Git-репозиторий** наравне с `package.json`!

### Профессиональная команда `npm ci` (Clean Install):
В автоматизированных системах (CI/CD пайплайны GitHub Actions, GitLab CI) или при разворачивании свежего проекта не следует использовать `npm install`: он может изменить lock-файл и не гарантирует воспроизводимость. Вместо этого используется команда **`npm ci`** (она требует, чтобы `package-lock.json` уже был в репозитории).

#### Сравнительный анализ `npm install` vs `npm ci`:

| Характеристика | `npm install` | `npm ci` (Clean Install) |
| :--- | :--- | :--- |
| **Назначение** | Локальная разработка и добавление новых пакетов. | Сборка в CI/CD и чистая установка на ПК. |
| **Поведение с `node_modules`** | Дозаписывает / обновляет существующую папку. | **Полностью удаляет** `node_modules` перед стартом. |
| **Изменение `package-lock`** | Может изменить `package-lock.json` (например, при добавлении пакета или если `package.json` не совпадает с lock-файлом). Версии, уже зафиксированные в lock-файле, сами по себе не обновляются. | **Никогда** не изменяет lock-файл. |
| **При расхождении версий** | Пересчитывает и перезаписывает lock-файл. | **Падает с ошибкой (Exit code 1)**, останавливая сборку. |
| **Скорость выполнения** | Обычно медленнее (может заново вычислять дерево зависимостей). | Обычно быстрее (берёт готовое дерево из lock-файла). |

```bash
# Команда чистой детерминированной установки для CI/CD:
npm ci
```

### Использование `npm ci` в GitHub Actions (`.github/workflows/ci.yml`):

```yaml
name: Frontend CI Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - name: Чтение исходного кода из Git
        uses: actions/checkout@v6

      - name: Настройка Node.js окружения
        uses: actions/setup-node@v6
        with:
          node-version: 24 # Укажите актуальную LTS-версию (см. nodejs.org)
          cache: 'npm' # Кэширование глобального npm-кэша для ускорения

      - name: Детерминированная установка зависимостей
        run: npm ci

      - name: Компиляция SCSS стилей
        run: npm run build:css

      - name: Проверка форматирования кода
        run: npm run format:check
```

## Подглава 34.4.5: Семантическое версионирование (SemVer) и безопасность зависимостей

Все пакеты в npm подчиняются стандарту **SemVer (Semantic Versioning 2.0.0)**.

```text
       ВЕРСИЯ ПАКЕТА:  2 . 4 . 1
                       |   |   |
                       |   |   +---> PATCH (Багфиксы, патчи безопасности)
                       |   +-------> MINOR (Новый функционал с обратной совместимостью)
                       +-----------> MAJOR (Ломающие изменения / Breaking Changes)
```

### Символы диапазонов версий в `package.json`:

* **`^2.4.1` (Caret / Карет - По умолчанию):** разрешает автоматическое обновление до любых **минорных версий и патчей** в пределах мажорной версии `2` (2.4.1 ≤ версия < 3.0.0).
  * *Особый случай:* для версий `0.x` карет строже: `^0.2.3` разрешает только `0.2.x` (до `< 0.3.0`), потому что до версии `1.0.0` любой минор может ломать совместимость.
* **`~2.4.1` (Tilde / Тильда):** разрешает автоматическое обновление **только патчей** (2.4.1 ≤ версия < 2.5.0).
* **`2.4.1` (Exact / Точная версия):** строгая фиксация. Устанавливается только эта версия.

### Безопасность зависимостей: Supply Chain Security & `npm audit`
Современные веб-приложения включают в себя сотни транзитивных библиотек. Злоумышленники могут захватить аккаунт автора популярной утилиты или создать пакет со сходным именем (**Typosquatting**, например подмена `lodash` на пакет с почти таким же названием) и внедрить вредоносный код.

Для контроля безопасности в npm встроен сканер уязвимостей:

```bash
# 1. Проверка проекта на известные уязвимости (база GitHub Advisory Database):
npm audit

# 2. Автоматическое исправление уязвимостей (только обновления в допустимых диапазонах версий, без MAJOR):
npm audit fix

# 3. Принудительное исправление с возможностью обновления MAJOR версий:
npm audit fix --force
```

**Как снижать риски зависимостей:**
* Коммитьте `package-lock.json` и устанавливайте в CI через `npm ci`: так версии и хэши пакетов не изменятся незаметно.
* Перед установкой нового пакета проверьте его название (нет ли опечатки), популярность, дату последнего обновления и репозиторий.
* Не добавляйте библиотеку ради одной мелкой функции: каждая зависимость тянет за собой десятки транзитивных.
* Помните, что у пакетов бывают скрипты установки (`postinstall`), которые выполняются на вашем компьютере.

### Обзор альтернативных пакетных менеджеров: `pnpm` и `yarn`
Хотя `npm` поставляется вместе с Node.js по умолчанию, в современной индустрии широко распространены альтернативы:

1. **`pnpm` (Performant npm):** эффективнейший менеджер пакетов. Хранит все версии библиотек в едином глобальном контентно-адресуемом хранилище на ПК, а в папку `node_modules` проекта прокидывает жесткие ссылки (**Hard Links / Symlinks**). Это экономит место на диске и, как правило, ускоряет установку.
2. **`yarn`:** изначально создан в Facebook (Meta); современные версии (Yarn Berry) развивает сообщество. Поддерживает монорепозитории (Workspaces) и режим Plug'n'Play, в котором вместо папки `node_modules` используется специальный файл поиска пакетов.

## Подсказки и решения к практическим задачам

### Решение задачи 1:
* `library-a` (`^2.3.4`): скачает **`2.4.0`** (разрешены минорные обновления и патчи в рамках версии 2.x.x, но версия 3.0.0 запрещена, так как это Major).
* `library-b` (`~1.12.0`): скачает **`1.12.1`** (разрешены только патчи в рамках версии 1.12.x, минорный релиз 1.13.0 заблокирован).
* `library-c` (`4.0.1`): скачает строго **`4.0.1`** (без символов диапазона фиксируется точная версия).

### Решение задачи 2:
1. **Причина падения:** Команда `npm ci` проверяет строгое соответствие между `package.json` и `package-lock.json`. Поскольку пакет был добавлен в `package.json`, но отсутствовал в lock-файле, `npm ci` зафиксировал нарушение детерминизма сборки и сбросил процесс.
2. **Алгоритм исправления:** Разработчику необходимо локально выполнить `npm install` (чтобы корректно обновить и синхронизировать `package-lock.json`), выполнить `git add package.json package-lock.json`, закоммитить изменения и запушить их в репозиторий.

### Решение задачи 3:
```bash
# 1. Удаление node_modules из индекса Git (файлы на диске останутся):
git rm -r --cached node_modules

# 2. Создание/дополнение .gitignore:
echo "node_modules/" >> .gitignore

# 3. Фиксация изменений в Git:
git add .gitignore
git commit -m "fix: remove node_modules from git index and update .gitignore"

# 4. Запуск локально установленного Prettier через npx:
npx prettier --check .
```

> ⚠️ Удаление из индекса убирает `node_modules` только из новых коммитов. Если «тяжёлый» коммит уже запушен, в истории Git он остаётся. Для очистки истории нужны отдельные инструменты (например, `git filter-repo`). Команда `npx prettier` использует установленный в проекте Prettier; если его там нет, `npx` скачает временную копию.

### Решение задачи 4:
Оптимизированный и исправленный фрагмент:

```yaml
    steps:
      - uses: actions/checkout@v6

      - name: Setup Node.js with npm caching
        uses: actions/setup-node@v6
        with:
          node-version: 24
          cache: 'npm'

      - name: Clean Install Dependencies
        run: npm ci

      - name: Build Styles via npm script
        run: npm run build:css
```
*Устранённые недостатки:*
1. `npm install` заменён на детерминированный `npm ci`.
2. Добавлен шаг `actions/setup-node` с настройкой кэширования npm.
3. Прямой запуск бинарника `sass` заменён на npm-скрипт `npm run build:css`: голая команда `sass` на чистом сервере не найдётся (пакет не установлен глобально и не лежит в `PATH`), а npm-скрипт сам находит утилиту в `node_modules/.bin`.

### Решение задачи 5:
1. Выполнить `npm audit` и внимательно изучить отчёт: какие именно пакеты содержат уязвимости и являются ли они `devDependencies` или рабочей `dependency`.
2. Выяснить, кто тянет уязвимый пакет (`npm ls <имя-пакета>`), и оценить риск: уязвимость в `devDependencies` (инструмент сборки) обычно менее опасна, чем в рабочей зависимости (`npm audit --omit=dev` покажет только рабочие).
3. Выполнить `npm audit fix` (безопасное автоматическое обновление в рамках допустимых диапазонов версий).
4. **Опасность `--force`:** `npm audit fix --force` автоматически обновляет библиотеки до мажорных версий (`MAJOR`). Это приводит к ломающим изменениям (**Breaking Changes**), нарушению совместимости API и поломке приложения. Если уязвимость требует мажорного обновления, его следует выполнять вручную с последующим тестированием всего функционала.
