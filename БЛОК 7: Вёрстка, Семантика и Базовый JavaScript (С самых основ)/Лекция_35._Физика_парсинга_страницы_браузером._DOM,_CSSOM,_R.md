# Лекция 35: Физика парсинга страницы браузером. DOM, CSSOM, Render Tree, Layout, Paint, Composite

Эта лекция раскрывает физику работы браузерного движка (Blink / WebKit / Gecko) от момента получения первого байта HTML-ответа по сети до финального вывода пикселей на экран с частотой 60/120 кадров в секунду (FPS). Мы разберём весь конвейер **Critical Rendering Path (CRP)**, поймём причины тормозов и подёргиваний интерфейса (jank) и научимся наблюдать и диагностировать рендеринг во вкладках **Performance** и **Layers** в Chrome DevTools.

> 🧭 **Место лекции в курсе.**
> * **Опираемся на:** Лекции 34.1–34.2 (CSS, Box Model, `display`, Flexbox/Grid) и Лекцию 34.3 (DevTools: Elements, Styles, Computed, Network).
> * **Новое в DevTools:** вкладки **Performance** и **Layers** вы открываете впервые. Подробный разбор Performance и Memory будет в Лекции 122.1.
> * **JavaScript начнётся только с Лекции 36.** Поэтому подглава 35.5 (Layout Thrashing) и задачи со звёздочкой ★ — «взгляд вперёд»: сейчас достаточно понять идею, а код вы напишете сами позже.
> * **Куда ведут связи:** подключение скриптов (`async` / `defer`) — Лекция 36; Event Loop и место отрисовки в нём — Лекция 97; свойства `offsetWidth`, `getBoundingClientRect()` — Лекции 104–106; метрики FCP / LCP / CLS (Core Web Vitals) — Лекция 174.

## 💡 Глоссарий ключевых терминов лекции

> 📌 **1. Critical Rendering Path (CRP, Критический путь рендеринга)**
> * **Что это:** Последовательность шагов, которые выполняет браузер, чтобы превратить HTML, CSS и JavaScript в видимые пиксели. Схема: байты HTML → **DOM**; текст CSS → **CSSOM**; DOM + CSSOM → **Render Tree** → **Layout** → **Paint** → **Composite**.

> 📌 **2. DOM (Document Object Model) и CSSOM (CSS Object Model)**
> * **DOM** — древовидная объектная модель HTML-документа: каждому тегу, фрагменту текста и комментарию соответствует объект-узел в памяти.
> * **CSSOM** — объектная модель CSS: все правила из таблиц стилей, разобранные в структуру, по которой браузер определяет итоговые стили каждого элемента (с учётом каскада и наследования). Браузер строит DOM и CSSOM отдельно друг от друга, а затем объединяет их.

> 📌 **3. Render Tree (Дерево рендеринга)**
> * **Что это:** Результат объединения DOM и CSSOM: дерево только тех объектов, которые участвуют в отображении, вместе с их итоговыми стилями. Узлы с `display: none` в него **не попадают**, а элементы с `visibility: hidden` или `opacity: 0` — **попадают** (они занимают место на странице).

> 📌 **4. Layout / Reflow (Расчёт геометрии, перекомпоновка)**
> * **Что это:** Этап, на котором браузер вычисляет точные размеры (width, height) и положение (x, y) каждого объекта Render Tree в пикселях. Расчёт ведётся для всего документа, а не только для видимой части; размеры окна (Viewport) нужны, чтобы вычислить `%`, `vw` и медиазапросы.

> 📌 **5. Paint / Repaint (Отрисовка) и Raster (Растеризация)**
> * **Paint** — составление для каждого слоя списка команд рисования («залить прямоугольник цветом», «вывести этот текст этим шрифтом», «нарисовать тень»). **Raster** — превращение этих команд в пиксели (битмапы). В Chrome растеризация часто выполняется на GPU.

> 📌 **6. Composite / Compositing (Композитинг, сборка слоёв)**
> * **Что это:** Финальный шаг: браузер собирает готовые слои (Compositing Layers) в итоговый кадр. Выполняется отдельным потоком (поток композитора) с участием GPU. Именно поэтому анимации `transform` и `opacity` могут идти плавно, не вызывая Layout и Paint.

> 📌 **7. Layout Thrashing (Принудительный синхронный Layout)**
> * **Что это:** Ошибка производительности в JavaScript: код в цикле поочерёдно меняет DOM и тут же читает геометрию (`offsetWidth`, `scrollTop`), из-за чего браузер вынужден пересчитывать Layout много раз за один кадр вместо одного.

> 📌 **8. Главный поток (Main Thread) и поток композитора (Compositor Thread)**
> * **Что это:** На главном потоке выполняются JavaScript, разбор HTML/CSS, расчёт стилей, Layout и Paint. Поток композитора собирает слои в кадр и умеет сам обрабатывать прокрутку и некоторые анимации. Пока главный поток занят, страница «не отвечает» на клики, но композитор может продолжать прокрутку и анимации `transform` / `opacity`.

> 📌 **9. Кадр (Frame) и бюджет кадра**
> * **Что это:** Одно обновление картинки на экране. При 60 Гц на кадр отводится около 16,7 мс (при 120 Гц — около 8,3 мс). Часть этого времени забирает сам браузер, поэтому на ваш код реально остаётся порядка 10 мс. Не успели — кадр пропущен, и пользователь видит рывки.

## Подглава 35.1: От байтов к DOM и CSSOM

Превращение текстового файла в дерево объектов происходит по цепочке: байты → символы → токены → узлы → дерево.

```text
[ Сетевые байты ] (0x3C, 0x68, 0x74...)
       │
       ▼ (Декодирование по кодировке, например UTF-8)
[ Символы ] ("<html><head>...")
       │
       ▼ (Токенизация — работа HTML-парсера)
[ Токены ] (StartTag: html, StartTag: head, EndTag: head...)
       │
       ▼ (Создание объектов-узлов)
[ Узлы (Nodes) ] (HTMLHtmlElement, HTMLHeadElement...)
       │
       ▼ (Связывание родитель — потомок)
[ DOM-дерево ] (Объектная модель документа в ОЗУ)
```

### 1. Построение DOM (Document Object Model)
1. **Преобразование байтов в символы:** браузер *декодирует* полученные байты в текст. Кодировку он берёт из заголовка ответа `Content-Type: text/html; charset=utf-8` (он главный), а если её там нет — из BOM-метки или из `<meta charset="UTF-8">` в начале документа.
2. **Токенизация:** парсер по правилам спецификации HTML5 разбивает текст на токены (`StartTag`, `EndTag`, `Character`, `Comment`).
3. **Создание узлов (Nodes):** токены превращаются в объекты нужного класса (`HTMLDivElement`, `Text`, `Comment`).
4. **Построение дерева:** узлы связываются отношениями «родитель — потомок».

> ⚠️ **Особенность 1: парсер потоковый.** Браузер начинает строить DOM, не дожидаясь, пока весь HTML докачается по сети. Показать что-либо на экране он сможет, когда будет готов и CSSOM (см. ниже).

> ⚠️ **Особенность 2: DOM — это не копия исходного HTML.** HTML-парсер никогда не «падает» с ошибкой: он исправляет неправильную разметку по строгим правилам. Например, он сам добавит недостающие `<html>`, `<head>`, `<body>`, закроет незакрытый `<p>` и вставит `<tbody>` в таблицу, где его не было. Проверьте сами (вы уже умеете пользоваться вкладкой **Elements**, Лекция 34.3):
> ```html
> <table>
>   <tr><td>Ячейка</td></tr>
> </table>
> <p>Абзац без закрывающего тега
> ```
> Сравните исходный текст (`Ctrl+U`, «Просмотр кода страницы») и вкладку **Elements**: во втором случае вы увидите `<tbody>` и закрытый `</p>`. **Вкладка Elements показывает DOM, а не исходный файл.**

> ⚠️ **Особенность 3: скрипты останавливают парсер.** Встретив обычный тег `<script>`, парсер приостанавливает построение DOM: скрипт может изменить документ, поэтому его нужно сначала выполнить. А перед выполнением скрипта браузер дожидается загрузки и разбора CSS, который подключён выше. Как управлять этим поведением (`defer`, `async`) — в Лекции 36.

### 2. Построение CSSOM (CSS Object Model)
Встретив `<link rel="stylesheet" href="...">`, браузер скачивает CSS (параллельно продолжая разбор HTML) и строит CSSOM. Допустим, есть такая разметка и стили:

```html
<body>
  <main>
    <div class="card">
      <p>Текст карточки</p>
    </div>
  </main>
</body>
```

```css
body { font-size: 16px; }
main { width: 100%; }
.card { background: #fff; }
.card p { color: #333; }
```

Браузер определяет итоговые стили каждого элемента: начинает со стилей браузера по умолчанию (**User Agent Stylesheet**), накладывает ваши правила и передаёт потомкам наследуемые свойства (`font-size`, `color`, `font-family`...). Свойства вроде `width` и `background` не наследуются.

```text
        [ Стили браузера по умолчанию (User Agent Stylesheet) ]
                              │
                              ▼
                         [ body ]
                    font-size: 16px
                              │
                              ▼
                         [ main ]
          width: 100%;  font-size: 16px  ← унаследовано
                              │
                              ▼
                        [ .card ]
         background: #fff;  font-size: 16px  ← унаследовано
                              │
                              ▼
                       [ .card p ]
      color: #333;  font-size: 16px  ← унаследовано
```

> ℹ️ Это учебная модель. Реальные движки хранят правила в оптимизированном виде и вычисляют стиль каждого элемента отдельно, но результат (какие итоговые значения получит элемент) именно такой.

> 🛑 **CSS блокирует рендеринг (Render-Blocking).** В отличие от HTML, CSSOM нельзя использовать «частично»: любое следующее правило может переопределить уже прочитанное. Поэтому браузер не рисует страницу, пока не скачает и не разберёт CSS, который к ней применяется. Важные уточнения:
> * Разбор HTML (построение DOM) при этом **продолжается** — блокируется именно отрисовка.
> * Таблицы стилей, не подходящие к текущему устройству (например, `<link rel="stylesheet" href="print.css" media="print">`), отрисовку не блокируют.
> * CSS также задерживает выполнение скриптов, стоящих после него (см. «Особенность 3»).

## Подглава 35.2: Слияние в Render Tree

**Render Tree (Дерево рендеринга)** — это результат объединения DOM и CSSOM. Браузер обходит DOM, подбирает к каждому узлу его итоговые стили (в DevTools этот шаг называется **Recalculate Style**) и оставляет в дереве только то, что должно быть нарисовано.

Пример разметки и стилей:

```html
<body>
  <div class="box">Видимый блок</div>
  <p class="hidden">Скрытый абзац</p>
</body>
```

```css
body    { font-size: 16px; }
.hidden { display: none; }
```

```text
            DOM-дерево                                CSSOM (стили)
  html                                          body    { font-size: 16px; }
  ├── head  (title, meta, ...)                  .hidden { display: none;   }
  └── body
      ├── div.box
      └── p.hidden
                          │
                          ▼  (обход DOM + подбор стилей каждому узлу)
                      Render Tree
  Корень Render Tree
  └── html
      └── body
          └── div.box        ✔ попал
  (p.hidden — НЕ попал: display: none)
  (head и всё внутри — НЕ попали: в стилях браузера у них display: none)
```

### Правила формирования Render Tree:
1. У Render Tree есть собственный корень (во внутренних названиях движков — `LayoutView`, в WebKit — `RenderView`). От него идёт `html`, затем `body` и остальные видимые узлы.
2. Браузер обходит DOM от корня:
   * Узел со стилем **`display: none`** исключается из Render Tree **вместе со всеми своими потомками**. Потомок не может «вернуть себя» обратно, даже если у него другое значение `display`.
   * Элементы **`visibility: hidden`** и **`opacity: 0`** в Render Tree **попадают**: они невидимы, но занимают место на странице.
   * Служебные элементы `<head>`, `<meta>`, `<title>`, `<script>`, `<style>` в Render Tree не попадают: в стилях браузера по умолчанию у них `display: none`.
   * Псевдоэлементы **`::before`** и **`::after`** создают узлы в Render Tree, хотя в DOM их нет. Условие: у них задано свойство `content` (любое значение, кроме `none`; даже пустая строка `content: ""` создаёт блок).
3. Соответствие между DOM и Render Tree не «один в один»: у одного элемента может появиться несколько объектов (например, маркер у `<li>`), а текст превращается в отдельные строки внутри блоков.

| Что задано в CSS | Попадёт в Render Tree? | Занимает место? | Реагирует на клики? |
| :--- | :---: | :---: | :---: |
| `display: none` | ❌ нет | ❌ нет | ❌ нет |
| `visibility: hidden` | ✅ да | ✅ да | ❌ нет |
| `opacity: 0` | ✅ да | ✅ да | ✅ да |

## Подглава 35.3: Layout (Reflow), Paint (Repaint) и Composite

Дальше браузер превращает Render Tree в кадр на экране. Это три основных шага.

```text
┌────────────────────────┐     ┌────────────────────────┐     ┌────────────────────────┐
│         LAYOUT         │ ──> │     PAINT + RASTER     │ ──> │       COMPOSITE        │
│        (Reflow)        │     │       (Repaint)        │     │     (сборка слоёв)     │
└────────────────────────┘     └────────────────────────┘     └────────────────────────┘
  Геометрия:                     Команды рисования              Слои → итоговый кадр
  x, y, width, height            → пиксели                      (поток композитора)
```

### 1. Layout (Reflow / Перекомпоновка)
Браузер проходит по Render Tree и вычисляет точный размер и положение каждого объекта.
* Учитываются `width`, `height`, `margin`, `padding`, `display`, Flexbox / Grid (всё то, что вы изучали в Лекциях 34.1–34.2). Относительные единицы (`rem`, `%`, `vw`) переводятся в конкретные пиксели.
* Изменение геометрии одного элемента может вызвать цепную реакцию: пересчитываются его потомки, соседи и родители, размеры которых от него зависят.

### 2. Paint (Repaint / Перерисовка) и Raster
Браузер составляет список команд рисования (**Paint Records**) для каждого слоя: заливка фона, рамки, текст, тени. Порядок наложения определяется правилами контекста наложения (Stacking Context) и свойством `z-index`. Затем команды растеризуются, то есть превращаются в пиксели (часто на GPU).

### 3. Composite (Компоновка слоёв)
Страница может состоять из нескольких независимых **слоёв (Compositing Layers)**. Браузер собирает готовые слои в итоговый кадр, учитывая их порядок, смещение, прозрачность и трансформации. Этим занимается поток композитора.

> 📘 **Три новых CSS-возможности для этой лекции** (в Лекциях 34.x их не было; сейчас их достаточно воспринимать как готовые заготовки):
> * `transform: translateX(100px)` — сдвиг элемента; `transform: scale(1.1)` — масштаб. Элемент **рисуется** иначе, но его место в раскладке **остаётся прежним**, соседи не сдвигаются.
> * `opacity: 0.5` — прозрачность от `0` (невидим) до `1` (полностью виден).
> * `will-change: transform` — подсказка браузеру: «этот элемент скоро будут анимировать», чтобы он заранее вынес его в отдельный слой.

### Что запускает каждое изменение

Чем раньше в конвейере вы вмешиваетесь, тем больше работы приходится повторять. **Если выполнен Layout, дальше всегда выполняются Paint и Composite** (поменялась геометрия — надо перерисовать пиксели).

| Действие с CSS | Вызываемые этапы | Нагрузка |
| :--- | :--- | :--- |
| Изменение `width`, `height`, `margin`, `padding`, `top`, `left`, `font-size` | **Layout → Paint → Composite** | 🔴 Очень высокая (главный поток) |
| Изменение `color`, `background-color`, `box-shadow`, `visibility` | **Paint → Composite** | 🟡 Средняя |
| Изменение `transform` и `opacity` у элемента **с собственным слоем** (`will-change`, активная CSS-анимация) | **Только Composite** | 🟢 Минимальная (без нагрузки на главный поток) |
| Изменение `transform` и `opacity` у элемента **без** собственного слоя | **Layout не нужен**; может потребоваться Paint → Composite | 🟡 Средняя |

> 💡 Поэтому в советах по оптимизации говорят «анимируйте `transform` и `opacity`»: эти свойства не меняют геометрию (Layout не нужен), а при наличии отдельного слоя ещё и не требуют перерисовки (Paint не нужен).

## Подглава 35.4: Наблюдаем рендеринг в Chrome DevTools

Для диагностики используются вкладки **Performance** и **Layers** (в Edge те же идеи; в Firefox названия другие). Названия кнопок могут слегка отличаться в вашей версии браузера: ориентируйтесь на цвета и названия событий.

### 1. Вкладка Performance (запись и разбор кадров)
1. Откройте страницу в окне **инкогнито** (расширения браузера не будут мешать записи) и нажмите `F12`.
2. Перейдите на вкладку **Performance**.
3. Нажмите **Record** (`Ctrl+E`), совершите действие на странице (прокрутка, наведение, анимация) и снова нажмите `Ctrl+E`. Чтобы записать загрузку страницы, используйте **Start profiling and reload page** (`Ctrl+Shift+E`).
4. На дорожке **Main** (главный поток) события окрашены по категориям:
   * 🟦 **Синий — Loading:** загрузка и разбор HTML (`Parse HTML`).
   * 🟨 **Жёлтый — Scripting:** выполнение JavaScript.
   * 🟪 **Фиолетовый — Rendering:** `Recalculate Style` (подбор стилей) и `Layout`.
   * 🟩 **Зелёный — Painting:** `Paint` и `Composite Layers`.
5. Щёлкните по событию: на вкладке **Summary** внизу появятся подробности. Слишком долгие задачи (дольше 50 мс) помечаются красным.

```text
Дорожка Main (главный поток), время идёт слева направо ─────────────►
┌───────────┬───────────────────┬──────────────┬───────────┬──────────────────┐
│ Scripting │ Recalculate Style │    Layout    │   Paint   │ Composite Layers │
│ (жёлтый)  │   (фиолетовый)    │ (фиолетовый) │ (зелёный) │    (зелёный)     │
└───────────┴───────────────────┴──────────────┴───────────┴──────────────────┘
```

> ℹ️ Сама **растеризация и композитинг** идут в других потоках: в записи для них есть отдельные дорожки (Compositor, Raster, GPU). На дорожке Main вы видите только то, что делает главный поток. Если анимация выполняется композитором, дорожка Main во время неё остаётся почти пустой — это хороший признак.
>
> В записи также есть дорожки **Frames** (кадры) и **Animations**: анимации, которые не удалось отдать композитору, помечаются красным треугольником.

### 2. Вкладка Layers (инспекция слоёв)
Чтобы открыть панель: нажмите `Ctrl+Shift+P` в DevTools, введите **Show Layers** и нажмите Enter (или меню ⋮ → **More tools** → **Layers**).
* Панель показывает 3D-модель слоёв страницы: её можно вращать мышью.
* Если выбрать слой, внизу в **Details** виден размер, оценка памяти, число перерисовок (Paint count) и **Compositing Reasons**, то есть причины, по которым браузер выделил слой.
* Типичные причины появления отдельного слоя: `will-change: transform`, 3D-трансформации (`transform: translateZ(0)`), активная CSS-анимация `transform` / `opacity`, элементы `<video>` и `<canvas>`.

> ⚠️ **Важно:** начиная с Chrome 124 в панели Layers показывается предупреждение, что она может быть удалена из-за малой востребованности (пока она работает). Запасные варианты: вкладка **Layers** внутри записи Performance (выделите кадр на дорожке Frames), параметр **Layer borders** во вкладке Rendering (см. ниже), а в Edge — инструмент **3D View → Composited Layers**.

### 3. Вкладка Rendering: быстрые «рентгены» (дополнительно)
Откройте её командой `Ctrl+Shift+P` → **Show Rendering**. Самые полезные галочки:
* **Paint flashing:** области, которые перерисовываются, вспыхивают зелёным.
* **Layer borders:** границы слоёв (оранжевые / оливковые) и плиток растеризации (голубые).
* **Frame rendering stats:** счётчик кадров в углу страницы, пропущенные кадры отмечаются красным.
* **Layout Shift Regions:** области «прыжков» вёрстки подсвечиваются фиолетовым (эта метрика называется CLS, Лекция 174).

### 4. Мини-лаборатория: `left` против `transform`
Создайте файл `lab.html` (напишите его руками) и откройте в Chrome. На странице два одинаковых квадрата с одинаковой анимацией, но первый движется через `left`, а второй через `transform`.

```html
<!DOCTYPE html>
<html lang="ru">
<head>
  <meta charset="UTF-8">
  <title>Лаборатория рендеринга</title>
  <style>
    body { margin: 20px; font-family: sans-serif; }
    .track { position: relative; width: 560px; height: 80px; margin-bottom: 20px; background: #eee; }
    .box { position: absolute; top: 15px; left: 0; width: 50px; height: 50px; background: #4a90d9; }

    /* A: сдвиг через left — меняет геометрию (Layout) каждый кадр */
    .box-a { animation: move-a 2s linear infinite alternate; }
    @keyframes move-a { to { left: 510px; } }

    /* B: сдвиг через transform — геометрия не меняется */
    .box-b { animation: move-b 2s linear infinite alternate; }

  </style>
</head>
<body>
  <p>A: анимация через <code>left</code></p>
  <div class="track"><div class="box box-a"></div></div>

```

Что делать и что вы должны увидеть:
1. Включите **Paint flashing**: вокруг квадрата A постоянно мигает зелёное, у квадрата B (после первой вспышки) почти нет.
2. Включите **Layer borders**: у квадрата B есть собственная рамка слоя, у A её нет.
3. На вкладке **Performance** запишите 3–4 секунды. Во время анимации A на дорожке Main в каждом кадре видны фиолетовые (`Recalculate Style`, `Layout`) и зелёные (`Paint`) события; во время анимации B главный поток почти пуст.
4. Откройте **Layers**, выберите слой квадрата B и найдите в Details его **Compositing Reasons**.

> Как хороший итог лаборатории запишите свои наблюдения в 3–4 строки: что вы увидели у A, что у B и почему. Если у вас что-то выглядит иначе (разные версии браузеров показывают детали по-разному), это нормально — сравните и объясните расхождение.

## Подглава 35.5: Layout Thrashing (взгляд вперёд, в сторону JavaScript)

> 🔭 Эта подглава использует JavaScript, который вы начнёте изучать с Лекции 36. Сейчас важно понять **идею**; сам код вы разберёте после Лекций 47 (стрелочные функции), 99–106 (работа с DOM и геометрией элементов) и 97 (Event Loop).

Обычно браузер ленив: если вы меняете стили из JavaScript, он откладывает пересчёт Layout до момента, когда нужно рисовать кадр, и делает его **один раз** для всех накопленных изменений. Но если после изменения вы *прочитали* геометрию (например, `offsetWidth`), браузер не может отдать устаревшее значение и вынужден пересчитать Layout **немедленно**. Это называется *принудительным синхронным Layout (forced reflow)*. Если «изменил → прочитал → изменил → прочитал» происходит в цикле, Layout пересчитывается на каждой итерации. Это и есть **Layout Thrashing**.

### Чтения, которые вынуждают браузер пересчитать Layout:
* Размеры: `offsetWidth`, `offsetHeight`, `clientWidth`, `clientHeight`.
* Положение и прокрутка: `offsetTop`, `offsetLeft`, `scrollTop`, `scrollLeft`, `scrollWidth`, `scrollHeight`.
* Координаты: `getBoundingClientRect()`.
* Вычисляемые стили, зависящие от геометрии: например, `getComputedStyle(el).width` или `.height`.

### ❌ Плохой код (Layout Thrashing):

```javascript
function resizeAllCardsBad() {
  const cards = document.querySelectorAll('.card');
  for (let i = 0; i < cards.length; i++) {
    // 1. Чтение геометрии. После записи на прошлой итерации браузер вынужден
    //    пересчитать Layout прямо сейчас!
    const currentWidth = cards[i].offsetWidth;
    // 2. Запись в DOM: геометрия снова становится «устаревшей»
    cards[i].style.width = (currentWidth + 10) + 'px';
  }
}
```

### ✅ Хороший код (сначала всё читаем, потом всё пишем):

```javascript
function resizeAllCardsGood() {
  const cards = Array.from(document.querySelectorAll('.card'));

  // Фаза 1: только чтение. Layout считается один раз.
  const widths = cards.map(card => card.offsetWidth);

  // Фаза 2: только запись. Layout откладывается до отрисовки кадра.
  cards.forEach((card, index) => {
    card.style.width = (widths[index] + 10) + 'px';
  });
}
```

### `requestAnimationFrame`: когда менять DOM
Функция `requestAnimationFrame(callback)` просит браузер вызвать `callback` **непосредственно перед отрисовкой следующего кадра**. Это правильное место для записи изменений в DOM при анимации из JavaScript: они попадают ровно в тот кадр, в который будут показаны, и не выполняются чаще, чем нужно. Она не заменяет разделение чтения и записи, а дополняет его.

```javascript
const element = document.querySelector('.box');

function updateAnimation() {
  requestAnimationFrame(() => {
    // Безопасное изменение прямо перед отрисовкой кадра
    element.style.transform = 'translateX(100px)';
  });
}
```

> 💡 Для простых анимаций лучше обходиться чистым CSS (`transition`, `@keyframes`, как в нашей лаборатории): тогда анимацию ведёт сам браузер, и JavaScript вообще не нужен.

## Подглава 35.6: Чек-лист оптимизации Critical Rendering Path

### 📋 Чек-лист фронтенд-инженера:
1. **Не раздувайте CSSOM:** не подключайте в `<head>` гигантские неиспользуемые стили. Стили для печати и других условий выносите в отдельные файлы с атрибутом `media`.
2. **Анимируйте только `transform` и `opacity`:** они не меняют геометрию, а у элемента с собственным слоем обрабатываются на этапе Composite, без Layout и Paint.
3. **Используйте `will-change: transform` с умом:** он выносит элемент в отдельный слой, но каждый слой занимает память (в том числе видеопамять) — не вешайте его на всё подряд.
4. **Избегайте Layout Thrashing:** не чередуйте в цикле запись в DOM и чтение геометрии; сначала читайте всё, потом пишите.
5. **Проверяйте догадки в DevTools, а не на глаз:** Performance покажет, что реально грузит главный поток, а Paint flashing и Layer borders — что перерисовывается и какие слои есть.
6. **Помните про бюджет кадра:** около 16,7 мс при 60 Гц, из которых на ваш код остаётся порядка 10 мс.

### Решение задачи 1:
1. `color: red;` ──> **Paint → Composite** (геометрия не меняется, нужно только перерисовать пиксели).
2. `margin-left: 20px;` ──> **Layout → Paint → Composite** (меняется геометрия: сдвигается сам элемент и могут сдвинуться связанные с ним элементы, например следующие за ним соседи).
3. `opacity: 0.5;` ──> Layout **не нужен** (геометрия не меняется). **Без своего слоя** браузеру может потребоваться перерисовка (Paint → Composite); **со своим слоем** (`will-change: opacity` или активная анимация): **только Composite**.
4. `transform: scale(1.1);` ──> Layout **не нужен** (соседи не сдвигаются, место в раскладке прежнее). **Без своего слоя** может потребоваться Paint → Composite; **со своим слоем:** **только Composite**.

### Решение задачи 2:
* `.box-1` и вложенный `span` ──> **НЕ попадут** в Render Tree (`display: none` исключает элемент вместе со всеми потомками).
* `.box-2` и его `span` ──> **Попадут** (`visibility: hidden` скрывает элемент, но он занимает место и участвует в Layout).
* `.box-3` и его `span` ──> **Попадут** (полностью прозрачный элемент тоже занимает место).
* `.box-4` и его `span` ──> **Попадут**; кроме них, в Render Tree появится узел для **псевдоэлемента `.box-4::before`** с текстом «Новость», хотя в DOM его нет.
* Элемент `<style>` ──> **НЕ попадёт** (в стилях браузера у него `display: none`; то же относится ко всему `<head>`).

### Решение задачи 3:
1. Анимация A: на Main в каждом кадре повторяются фиолетовые события (`Recalculate Style`, `Layout`) и зелёные (`Paint`). Анимация B: главный поток почти пуст, анимацию ведёт композитор.
2. Да: причина связана с активной анимацией `transform` (формулировки в Details могут отличаться в разных версиях). Квадрат A отдельного слоя не имеет.
3. Не изменится: `margin-left`, как и `left`, меняет геометрию, поэтому каждый кадр снова вызывает Layout → Paint → Composite.

### Решение задачи 4:
Подход A (`height`) при каждом кадре анимации вызывает цепочку **Layout → Paint → Composite**, причём Layout затрагивает весь контент под меню, что на слабых смартфонах приводит к пропуску кадров. Подход B (`transform`) не затрагивает геометрию, а при отдельном слое выполняется на этапе **Composite**, и анимация идёт плавно, даже если главный поток занят.

Недостатки подхода B: `scaleY` *растягивает и сплющивает* содержимое (текст и иконки искажаются во время анимации), а место под меню в раскладке не освобождается и не занимается (соседние блоки не сдвигаются). Поэтому для меню часто используют сдвиг `translateY` в сочетании с `opacity`, а не `scaleY`.

### Решение задачи 5 ★:
Исходная функция в каждой итерации сначала читает `block.offsetHeight`, а потом (иногда) пишет `height`, поэтому чтение на следующей итерации вынуждает пересчитать Layout. Нужно отделить чтение от записи, **сохранив условие** (блоки, уже достаточно высокие, не менять):

```javascript
function alignHeights() {
  const blocks = Array.from(document.querySelectorAll('.sidebar-block'));
  const maxHeight = document.querySelector('.main-content').offsetHeight;

  // Фаза чтения: собираем все высоты (Layout считается один раз)
  const heights = blocks.map(block => block.offsetHeight);

  // Фаза записи: только изменения DOM, без чтений
  blocks.forEach((block, i) => {
    if (heights[i] < maxHeight) {
      block.style.height = maxHeight + 'px';
    }
  });
}
```

> ⚠️ Частая ошибка — «упростить» функцию и убрать условие `if`: тогда блок, который был выше `maxHeight`, ошибочно уменьшится. Оптимизация не должна менять поведение.

### Решение задачи 6 ★:
```javascript
function animateMove(element, distance, duration) {
  let startTime = null;

  function step(timestamp) {
    if (startTime === null) startTime = timestamp;
    const progress = Math.min((timestamp - startTime) / duration, 1);

    // transform не вызывает Layout
    element.style.transform = `translateX(${progress * distance}px)`;

    if (progress < 1) {
      requestAnimationFrame(step);
    }
  }

  requestAnimationFrame(step);
}
```
