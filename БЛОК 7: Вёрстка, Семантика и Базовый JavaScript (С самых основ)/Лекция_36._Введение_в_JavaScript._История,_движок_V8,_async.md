## 💡 Глоссарий ключевых терминов лекции

> 📌 **1. JavaScript & ECMAScript (ECMA-262)**
> * **Что это:** **JavaScript** — мультипарадигменный динамически типизированный язык программирования. Это единственный язык, который браузеры выполняют «из коробки»; он же используется на сервере (Node.js). **ECMAScript (ES)** — официальная спецификация (стандарт), описывающая синтаксис, семантику и базовые API языка. Разработкой спецификации занимается комитет **TC39**.

> 📌 **2. Движок V8 (V8 Engine)**
> * **Что это:** Высокопроизводительный движок JavaScript и WebAssembly с открытым исходным кодом, написанный на C++. Используется в браузерах Google Chrome и Chromium (и основанных на нём), а также в Node.js, Deno и Electron.

> 📌 **3. JIT-компиляция (Just-In-Time Compilation)**
> * **Что это:** Технология выполнения кода, объединяющая интерпретацию и компиляцию «на лету». В V8 интерпретатор **Ignition** быстро генерирует и запускает байт-код, а JIT-компилятор **TurboFan** компилирует «горячие» (часто вызываемые) участки кода в оптимизированные машинные инструкции процессора.

> 📌 **4. Атрибут `defer`**
> * **Что это:** Атрибут тега `<script src="...">`. Браузер скачивает скрипт в фоне параллельно с разбором HTML и выполняет его **после** того, как HTML полностью разобран и DOM-дерево построено (но до события `DOMContentLoaded`), с сохранением порядка скриптов в документе.

> 📌 **5. Атрибут `async`**
> * **Что это:** Атрибут тега `<script src="...">`. Скрипт скачивается в фоне, но исполняется **сразу же после завершения скачивания** (приостанавливая разбор HTML, если тот ещё не закончен). Порядок исполнения нескольких `async`-скриптов не гарантируется (кто быстрее скачался, тот и запустился).

> 📌 **6. Строгий режим (`"use strict"`)**
> * **Что это:** Режим выполнения JavaScript, введённый в ES5. Он запрещает устаревшие и небезопасные возможности языка, превращает «тихие» ошибки (которые в обычном режиме молча игнорируются) в явные ошибки (`TypeError`, `ReferenceError`, `SyntaxError`) и запрещает создание случайных глобальных переменных.

## Подглава 36.1: История JavaScript и стандартизация ECMAScript

### 1. Рождение языка и «Война браузеров»
Язык **JavaScript** был создан в **мае 1995 года** Бренданом Эйхом (Brendan Eich) в компании Netscape примерно за **10 дней**. Изначально проект носил рабочие названия *Mocha* и *LiveScript*, но был переименован в *JavaScript* из маркетинговых соображений на волне популярности языка Java от Sun Microsystems. Несмотря на похожее название, **JavaScript и Java — два разных языка**.

Во второй половине 1990-х началась первая «война браузеров» между Netscape Navigator и Microsoft Internet Explorer. Microsoft создала собственную версию языка — **JScript** (появилась в IE 3), что привело к несовместимостям: один и тот же код вёл себя по-разному в разных браузерах.

### 2. Стандартизация ECMA-262 и эволюция ES6+
Для предотвращения фрагментации язык передали в международную организацию **ECMA International**. Первая спецификация **ECMA-262 (ECMAScript 1)** вышла в 1997 году.

```text
[1995] LiveScript / JS --> [1997] ES1 --> [1999] ES3 --> [2009] ES5
                                                              |
                                                              v
[Ежегодный цикл] <---- [2016 и далее] ES2016, ES2017, ... <---- [2015] ES6 / ES2015
 (процесс TC39)                                               (революционный релиз!)
```

* **ES3 (1999):** регулярные выражения, `try/catch`, базовые методы строк.
* **ES5 (2009):** режим `"use strict"`, JSON API, методы массивов (`forEach`, `map`, `filter`, `reduce`), геттеры и сеттеры.
* **ES6 / ES2015 (революционный прорыв):** блочная область видимости (`let`, `const`), стрелочные функции (`() => {}`), классы (`class`), модули (`import`/`export`), промисы (`Promise`), шаблонные строки, деструктуризация и `Symbol`.

Начиная с 2015 года комитет **TC39** перешёл на ежегодный цикл релизов (ES2016, ES2017 и так далее). Каждое предложение по изменению языка проходит 5 стадий **TC39 Process**:
* **Stage 0 (Strawman):** идея или черновик.
* **Stage 1 (Proposal):** формальное предложение с описанием проблемы и решения.
* **Stage 2 (Draft):** описан точный синтаксис и написан первоначальный текст спецификации.
* **Stage 3 (Candidate):** спецификация в целом готова; ждёт реализации в движках и отзывов разработчиков.
* **Stage 4 (Finished):** есть как минимум две совместимые реализации в браузерах/движках и пройдены тесты (Test262); предложение войдёт в ближайший годовой стандарт ECMAScript.

## Подглава 36.2: Движок V8 под капотом — от JS-кода до машинных инструкций

Движок **V8** от компании Google — это высокопроизводительная среда исполнения JavaScript, написанная на C++. Он не «читает» код строчка за строчкой напрямую: сначала V8 разбирает исходный текст и переводит его в **байт-код**, который сразу начинает исполняться, а самые «горячие» участки программы затем компилирует в **машинный код** процессора.

```text
+-----------------+      +---------------+      +-------------------------+
| Исходный JS-код | ---> | Scanner +     | ---> |  AST (Абстрактное       |
| (текст)         |      | Parser        |      |  Синтаксическое Дерево) |
+-----------------+      +---------------+      +-------------------------+
                                                             |
                                                             v
+------------------------+                      +-------------------------+
| Машинный код процессора| <------------------- | Ignition (Интерпретатор)|
| (x86_64 / ARM64)       |  [TurboFan JIT]      | Генерация байт-кода     |
+------------------------+                      +-------------------------+
            |                                                ^
            |------------ [ Deoptimization ] ----------------|
```

### Архитектурные компоненты V8:

1. **Parser & AST Generator:**
   * **Scanner (лексер):** превращает поток символов кода в токены (`let`, идентификатор, `=`, число).
   * **Parser:** строит **Абстрактное Синтаксическое Дерево (AST — Abstract Syntax Tree)** и проверяет синтаксическую корректность программы. Для ускорения запуска V8 разбирает функции «лениво»: полностью — только когда функцию впервые вызывают.

2. **Интерпретатор Ignition:**
   * Быстро генерирует и выполняет компактный **байт-код** (Bytecode).
   * Во время работы собирает статистику о типах данных, проходивших через каждую функцию (*Type Feedback / Profiling*).

3. **Оптимизирующий JIT-компилятор TurboFan:**
   * Если функция вызывается многократно (становится «горячей» — *Hot Function*), V8 передаёт её байт-код и накопленную статистику типов в **TurboFan**.
   * TurboFan компилирует код в быстрый **машинный код процессора** (`x86_64` или `ARM64`), делая **спекулятивные** оптимизации: «раз до сих пор сюда приходили только числа, будем считать, что так будет и дальше» (приёмы — Inlining, Escape Analysis и др.).

   > ℹ️ **Для любопытных:** в современных версиях V8 между Ignition и TurboFan есть ещё два промежуточных уровня: **Sparkplug** (быстрый базовый компилятор) и **Maglev** (компилятор среднего уровня). Общая идея та же: чем «горячее» код, тем сильнее он оптимизируется. В этой лекции для простоты мы рассматриваем два уровня.

4. **Деоптимизация (Deoptimization):**
   * Если предположение нарушилось (например, функция много раз принимала `number`, а затем ей передали `string`), проверка внутри оптимизированного кода «не проходит».
   * V8 выполняет **деоптимизацию** — отбрасывает оптимизированный машинный код и возвращается к выполнению байт-кода в Ignition. Позже, накопив новую статистику, V8 может оптимизировать функцию заново (уже с учётом обоих типов).

5. **Сборщик мусора Orinoco (Garbage Collector):**
   * Работает по гипотезе поколений (Generational Hypothesis): большинство объектов «умирают молодыми».
   * **Scavenger (New Space, «молодое» поколение):** быстрая параллельная очистка короткоживущих объектов.
   * **Mark-Sweep-Compact (Old Space, «старое» поколение):** очистка и дефрагментация долгоживущих объектов; значительная часть работы выполняется инкрементально и параллельно в фоновых потоках, чтобы не «замораживать» страницу.
   * Подробнее о V8 и сборке мусора — в Лекции 96.

## Подглава 36.3: Способы подключения скриптов к HTML (`async`, `defer`)

### 0. Как вообще добавить JavaScript на страницу
JavaScript подключается тегом `<script>`. Есть два способа:

```html
<!-- 1. Встроенный (inline) скрипт: код прямо в HTML -->
<script>
  console.log("Привет из встроенного скрипта!");
</script>

<!-- 2. Внешний файл: код лежит в app.js -->
<script src="app.js"></script>
```

* Тег `<script>` **нельзя** закрывать «на месте» (`<script src="app.js" />` не работает): нужен закрывающий тег `</script>`.
* Если у тега указан `src`, код внутри самого тега игнорируется.
* Результаты `console.log()` смотрим во вкладке **Console** в DevTools (Лекция 34.3).
* Атрибуты `async` и `defer`, о которых пойдёт речь ниже, работают **только для внешних скриптов** (с `src`).

### Проблема обычного скрипта
По умолчанию, когда браузер встречает классический тег `<script src="app.js"></script>`, разбор HTML-документа полностью останавливается (**Parser-Blocking**). Браузер вынужден дождаться скачивания файла и выполнения кода и только потом продолжает разбирать страницу. (Современные браузеры при этом заранее «заглядывают вперёд» по HTML и начинают скачивать найденные файлы, но выполнять и разбирать страницу дальше нельзя, пока скрипт не отработает.)

```text
HTML Parsing:  [========]                [=====================>]
Script Download:        [========]
Script Execute:                  [======]
                                 ^ (Задержка рендеринга!)
```

### 1. Синхронное подключение `<script src="...">`
* **Поведение:** останавливает HTML-парсер, скачивает файл, выполняет код, возобновляет HTML-парсер.
* **Недостаток:** блокирует появление элементов на экране («белый экран» при медленной сети).
* **Старый приём:** размещение тега `<script>` в самом низу перед закрывающим `</body>`, чтобы страница успела отрисоваться. Он работает, но современный способ — `defer` в `<head>`: скрипт начинает скачиваться раньше.
* **Когда это уместно:** когда код **должен** выполниться до отрисовки страницы (пример — в Задаче 4).

### 2. Атрибут `defer` (отложенное выполнение)
```html
<script defer src="app.js"></script>
```
```text
HTML Parsing:  [========================================>]
Script Download:        [========]
Script Execute:                                 [======] (после разбора HTML, до DOMContentLoaded)
```
* **Параллельное скачивание:** скачивается в фоне, не останавливая разбор HTML.
* **Момент исполнения:** запускается **после** того, как HTML полностью разобран и DOM построен, но **до** события `DOMContentLoaded` (это событие мы изучим в Лекции 116).
* **Порядок выполнения:** несколько скриптов с `defer` выполняются **строго в том порядке, в котором они записаны в HTML** (даже если маленький файл скачался быстрее большого).
* **Удобство:** внутри такого скрипта можно сразу искать элементы страницы (DOM уже есть).
* **Важно:** `defer` работает только для скриптов с `src`. Скрипты `type="module"` (Лекция 98) ведут себя как `defer` по умолчанию.

### 3. Атрибут `async` (асинхронное выполнение)
```html
<script async src="analytics.js"></script>
```
```text
HTML Parsing:  [========]        [===============>]
Script Download:        [========]
Script Execute:                  [======] (сразу по скачивании!)
```
* **Параллельное скачивание:** скачивается в фоне, не блокируя разбор HTML.
* **Момент исполнения:** **сразу же, как только скачался**. Если HTML ещё разбирается, в момент выполнения парсер приостанавливается.
* **Порядок выполнения:** **не гарантируется**. Файл, скачавшийся первым, выполнится первым.
* **Связь с DOM:** `async`-скрипт может выполниться и до построения DOM, и после; событие `DOMContentLoaded` его **не ждёт**. Поэтому такой скрипт не должен рассчитывать ни на наличие элементов страницы, ни на другие скрипты.
* **Назначение:** независимые сторонние скрипты (Google Analytics, Яндекс.Метрика, рекламные пиксели).

### Сравнительная таблица способов подключения:

| Характеристика | Обычный `<script>` | `<script defer>` | `<script async>` |
| :--- | :--- | :--- | :--- |
| **Блокирует разбор HTML во время скачивания?** | **Да** ❌ | Нет | Нет |
| **Блокирует разбор HTML во время выполнения?** | **Да** ❌ | Нет (выполняется после разбора) | **Да** (если разбор ещё идёт) |
| **Сохраняет порядок выполнения файлов?** | **Да** | **Да** | **Нет** (кто быстрее скачался) |
| **Ждёт построения DOM-дерева?** | Нет (видит только то, что выше по документу) | **Да** | Нет |
| **Сфера применения** | Небольшой код, который обязан выполниться до отрисовки страницы | **Основной код приложения (UI)** | Независимые счётчики и аналитика |

## Подглава 36.4: Строгий режим ("use strict")

Директива `"use strict";` активирует **строгий режим (Strict Mode)** выполнения JavaScript. Он был введён в ES5 для исправления исторических недостатков языка: часть ошибок, которые раньше молча игнорировались, теперь приводят к исключениям.

### 1. Как включить `"use strict"`
* **Для всего файла:** строка `"use strict";` должна быть **первой инструкцией** в самом верху `.js` файла (перед ней допускаются только комментарии). Если поставить её не первой, она станет обычной строкой и никакого эффекта не окажет — и никакой ошибки вы не увидите.
* **Для одной функции:** первой инструкцией в теле функции.
* **Автоматически:** строгий режим **всегда включён** внутри ES-модулей (`import`/`export`) и внутри тела классов (`class`).

```javascript
"use strict";

// Весь код файла выполняется в строгом режиме
function myApp() {
  // ...
}
```

### 2. Главные правила и запреты в `"use strict"`:

#### А. Запрет неявного создания глобальных переменных
В обычном режиме присвоение значения необъявленной переменной создавало глобальную переменную (в браузере — свойство `window`). В `"use strict"` возникает `ReferenceError`.
```javascript
// Без "use strict": x станет window.x = 10;
// В "use strict":
"use strict";
x = 10; // Uncaught ReferenceError: x is not defined
```

#### Б. Контекст `this` в обычных функциях по умолчанию равен `undefined`
В обычном режиме при вызове простой функции `this` ссылался на глобальный объект (`window`). В `"use strict"` он равен `undefined`, что защищает от случайной порчи глобального состояния. (Как работает `this`, мы подробно изучим в Лекции 50.)
```javascript
"use strict";
function showThis() {
  console.log(this);
}
showThis(); // undefined (в обычном режиме вывело бы window!)
```

#### В. Ошибки при записи в свойства «только для чтения»
Запись в неизменяемые свойства (в том числе в замороженный объект `Object.freeze`) вызывает `TypeError`, а не молча игнорируется. (Флаги свойств и `Object.defineProperty` изучим в Лекции 75.)
```javascript
"use strict";
const obj = {};
Object.defineProperty(obj, "readOnlyProp", { value: 42, writable: false });

obj.readOnlyProp = 100; // Uncaught TypeError: Cannot assign to read only property 'readOnlyProp' of object
```

#### Г. Запрет одинаковых имён параметров функции
```javascript
"use strict";
// Uncaught SyntaxError: Duplicate parameter name not allowed in this context
function sum(a, a, c) {
  return a + a + c;
}
```

#### Д. Запрет восьмеричных литералов с нулём и оператора `with`
```javascript
"use strict";
let num = 010;         // Uncaught SyntaxError: Octal literals are not allowed in strict mode
let validOctal = 0o10; // Валидный синтаксис ES6 (равно 8)
// with (obj) { ... }  // SyntaxError: Strict mode code may not include a with statement
```

#### Е. Запрет `delete` для переменных
```javascript
"use strict";
let value = 5;
delete value; // Uncaught SyntaxError: Delete of an unqualified identifier in strict mode.
```
(`delete` предназначен для удаления свойств объектов: `delete user.age`.)

> ⚠️ **Разница между `SyntaxError` и остальными ошибками.** `SyntaxError` — это ошибка **разбора** кода: она возникает до выполнения программы, и **весь файл целиком не запустится**. А `ReferenceError` и `TypeError` возникают уже во время работы, в момент выполнения «проблемной» строки.

## Подглава 36.5: Полноценный практический пример (подключение скриптов и строгий режим)

Ниже представлен автономный демонстрационный проект, показывающий работу строгого режима и порядок выполнения `async`- и `defer`-скриптов. Положите три файла в одну папку и откройте `index.html` в браузере, а затем откройте DevTools → Console (Лекция 34.3).

### Файл `index.html`:
```html
<!DOCTYPE html>
<html lang="ru">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Лекция 36 — Введение в JavaScript</title>

  <style>
    /* pre-wrap: чтобы символы переноса строки \n в тексте отображались на странице */
    .log-box { white-space: pre-wrap; font-family: monospace; margin-top: 1rem; }
  </style>

  <!-- 1. Асинхронный независимый счётчик -->
  <script async src="analytics.js"></script>

  <!-- 2. Основной скрипт приложения (ждёт, пока DOM будет построен) -->

  <header class="header">

```

### Файл `analytics.js`:
```javascript
// Независимый скрипт: не обращается ни к DOM, ни к другим скриптам.
// Выполнится сразу после скачивания — до или после app.js, порядок не гарантирован
console.log("[analytics.js] выполнен, document.readyState =", document.readyState);
```

### Файл `app.js`:
```javascript
"use strict";

// Скрипт с defer выполняется, когда HTML уже разобран и DOM построен,
// поэтому элементы можно искать сразу — ждать событие DOMContentLoaded не нужно
console.log("[app.js] выполнен, document.readyState =", document.readyState); // "interactive"

const btnEl = document.getElementById("btn-action");
const logEl = document.getElementById("output-log");

logEl.textContent = '✅ Приложение инициализировано в строгом режиме ("use strict").\n';

btnEl.addEventListener("click", () => {
  runStrictChecks(logEl);
});

/**
 * Функция проверки правил строгого режима
 */
function runStrictChecks(logElement) {
  logElement.textContent += "\n--- Запуск тестов ---\n";

  // 1. Проверка контекста this
  function testThisContext() {
    return this;
  }
  const currentThis = testThisContext();
  logElement.textContent += `1. Контекст this без вызова от объекта: ${String(currentThis)} (ожидалось: undefined)\n`;

  // 2. Перехват ошибки при записи в необъявленную переменную
  try {
    undeclaredVar = 42; // в строгом режиме это ReferenceError
  } catch (err) {
    logElement.textContent += `2. Запись в необъявленную переменную перехвачена: ${err.name} — ${err.message}\n`;
  }
}
```

> Конструкции `try/catch`, шаблонные строки (`` `...${}...` ``) и стрелочные функции мы разберём позже (Лекции 86, 55, 47). Обратите внимание на сообщения в консоли: порядок строк `[analytics.js]` и `[app.js]` может меняться от запуска к запуску, а `document.readyState` в `app.js` всегда равен `"interactive"` (HTML разобран, DOM готов).

### Решение задачи 1:
**Гарантировано:**
1. `script1.js` (обычный) выполнится **первым**: он останавливает разбор HTML, и ни один из остальных скриптов не начнёт выполняться раньше него.
2. `script3.js` и `script4.js` (`defer`) выполнятся **строго по очереди**: сначала `script3.js`, затем `script4.js`; оба — **после** полного разбора HTML и построения DOM и **до** события `DOMContentLoaded`.

**Не гарантировано:** `script2.js` (`async`) выполнится сразу, как только скачается, но не раньше `script1.js`. Он может выполниться во время разбора HTML (приостановив его), после построения DOM или даже раньше/позже `defer`-скриптов; `DOMContentLoaded` его не ждёт. Поэтому такой скрипт не должен зависеть ни от DOM, ни от остальных файлов.

### Решение задачи 2:
В строгом режиме ошибки возникнут в таком порядке:
1. Сразу при разборе файла: `delete user;` — это `SyntaxError: Delete of an unqualified identifier in strict mode` (оператор `delete` нельзя применять к переменным и параметрам). Так как это ошибка **разбора**, не запустится **весь файл**, а не только эта функция.
2. Только после исправления первой ошибки и вызова функции: `userName = user.name;` вызовет `ReferenceError: userName is not defined` (переменная не объявлена через `let`/`const`).

**Исправленный вариант:**
```javascript
"use strict";

function processUserData(user) {
  const userName = user.name;
  return userName;
}
```

### Решение задачи 3:
```javascript
function calculateTotal(a, b) {
  return a + b;
}

for (let i = 0; i < 1000000; i++) {
  calculateTotal(10, 20); // всегда числа
}

calculateTotal("10", "20"); // строки: результат "1020" (конкатенация!)
```
Что происходит внутри V8:
1. Пока функцию вызывают с числами, Ignition собирает статистику: на входе всегда `number` и `number`.
2. Когда функция становится «горячей», TurboFan компилирует её в быстрый машинный код, рассчитанный именно на числа.
3. При вызове со строками проверка типов внутри оптимизированного кода не проходит и срабатывает **деоптимизация**: оптимизированный код отбрасывается, а выполнение возвращается к байт-коду в Ignition (он медленнее). Позже V8 может оптимизировать функцию заново — уже с учётом того, что она получает и числа, и строки.

Точное число вызовов, после которого V8 оптимизирует функцию, зависит от версии движка. Посмотреть оптимизации и деоптимизации можно в Node.js:
```bash
node --trace-opt --trace-deopt file.js
```

### Решение задачи 4:
1. `theme-toggle.js`: **обычный `<script>` без атрибутов** в `<head>` (ещё лучше — очень маленький inline-скрипт). Он должен выполниться **до** того, как браузер отрисует страницу, иначе пользователь увидит «мигание» неверной темы (светлая тема на долю секунды, затем тёмная).
2. `main-app.js`: **`<script defer src="main-app.js"></script>`** в `<head>` (не блокирует разбор HTML, сохраняет порядок, выполняется после построения DOM).
3. `ad-pixel.js`: **`<script async src="ad-pixel.js"></script>`** в `<head>` (не блокирует страницу, независим от остального кода).

### Решение задачи 5:
* В **обычном режиме** присваивание `config.version = newVer` «молча» игнорируется (объект заморожен). Функция вернёт старое значение `"1.0.0"`.
* В **строгом режиме (`"use strict"`)** возникнет `TypeError: Cannot assign to read only property 'version' of object '#<Object>'`.

**Исправление:** не изменять замороженный объект, а возвращать новый (оператор `...` — spread, Лекция 67):
```javascript
"use strict";

function updateVersion(oldConfig, newVer) {
  return { ...oldConfig, version: newVer };
}

const config = Object.freeze({ version: "1.0.0" });
const newConfig = updateVersion(config, "2.0.0");
console.log(newConfig.version); // "2.0.0"
```

### Решение задачи 6:
```javascript
"use strict";

function getGlobalEnvironment() {
  // typeof безопасен для необъявленных переменных: вернёт "undefined" вместо ReferenceError
  if (typeof window !== "undefined" && typeof window.document !== "undefined") {
    return "Browser Environment";
  }
  if (typeof process !== "undefined" && process.versions && process.versions.node) {
    return "Node.js Environment";
  }
  return "Unknown Environment";
}

console.log(getGlobalEnvironment());
```
Обратите внимание: прямое обращение к `window` в Node.js вызвало бы `ReferenceError`, а `typeof window` — нет (оператор `typeof` разберём в Лекции 38). Учтите также, что Deno и Bun поддерживают совместимость с Node.js, и такая проверка может принять их за Node.js.
